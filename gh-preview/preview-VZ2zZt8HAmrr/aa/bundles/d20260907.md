# 🎁 AIの長い仕事が途中で失敗したとき用 復旧チェックリスト

AIに任せた長い作業（リサーチ、資料作成、データ整理、記事の下書きなど）が途中で失敗・脱線したときに、最初からやり直さずに「壊れた所だけ」を直して再開するための手順書です。論文でいう「実行時状態管理（状態記録・失敗箇所の特定・復旧）」を、エンジニアでない人の業務に落としたものです。

**受け取り方**: このファイルをそのままコピー、またはダウンロードしてご利用ください。

**使い方**: 失敗に気づいた時点で上から順に埋めます。各ステップの「指示例」はそのままAIに貼れます。次からは、作業を始める前にステップ0を仕込んでおくと、この手順がずっと楽になります。

```text
【AIの長い仕事が途中で失敗したとき用 復旧チェックリスト】

■ ステップ0：次回のために先に仕込む（今から始める人向け）
□ 作業を「集める→作る→確かめる」など3〜5個の工程に分けたか
□ 各工程の終わりに、出力を短くメモ（箇条書き5行以内）で残すよう頼んだか
□ 「工程がひとつ終わるたびに、ここまでの結果と次の工程名を1行で報告して」と伝えたか
→ YES: これで失敗しても「どの工程まで正しかったか」が残る
指示例: これから複数工程の作業をお願いします。各工程の終わりに「完了した工程名／成果の要点3行／次の工程名」だけを報告してから次に進んでください。

■ ステップ1：まず止める・広げない
□ 失敗・脱線に気づいた
□ そのままAIに続きを頼んでいない（間違いの上に積み増さない）
→ YES: 一度会話を止めて、下の切り分けに移る
指示例: いったん作業を止めてください。今の続きは書かないで、ここまでの状態だけ教えてください。

■ ステップ2：どこまでが正しかったかを確定する
□ 直近で「ここは合っている」と確認できた工程はどれか
□ その工程の出力（メモ・成果物）は手元に残っているか
□ 残っていない場合、AIに「工程◯の出力だけをもう一度そのまま出して」と頼んだか
→ YES: そこが「戻る地点」。ここより後だけを作り直す
指示例: 工程1〜3のうち、根拠まで確認できているのはどこまでですか。確認できている最後の工程の成果を、そのまま省略せず出してください。

■ ステップ3：失敗の原因を1つに絞る
□ 失敗は「情報が足りなかった」タイプか
□ 「工程の順番・分け方が悪かった」タイプか
□ 「AIが途中の指示を取り違えた・忘れた」タイプか
→ YES（情報不足）: 不足していた情報を足して、戻る地点から再開
→ YES（順番が悪い）: 工程の分け方を修正してから再開
→ YES（取り違え）: 戻る地点の出力を「確定情報」として新しい会話に貼り直して再開
指示例: 今回うまくいかなかった原因は、(a)情報不足 (b)工程の分け方 (c)指示の取り違え のどれに近いですか。理由も一言添えてください。

■ ステップ4：作り直す範囲を決める（全部やり直さない）
□ 戻る地点から先の工程を書き出したか
□ そのうち、今回の失敗の影響を受けたのはどれか
□ 影響を受けていない工程の成果は、そのまま流用すると決めたか
→ YES: 影響を受けた工程だけを作り直す対象にする
指示例: 戻る地点は工程◯です。その出力を「確定」として扱い、工程◯以降だけをやり直してください。工程◯より前の内容は変更しないでください。

■ ステップ5：チェックは別の役にやらせる
□ 作り直した成果を、作ったのと同じ会話でそのまま自己採点させていないか
□ 別のセッション（または別のAI役）に、成果物だけを渡してチェックさせたか
→ YES: 「自分の判断」を「正しい証拠」と取り違える事故を防げる
指示例: （別の会話で）これは私が別途作った成果物です。作成の経緯は知らない前提で、事実の誤り・抜け・前の工程との矛盾だけを指摘してください。

■ ステップ6：再発防止を1行だけ残す
□ 今回の失敗を、ステップ0のどの項目に足せば防げたかを1行でメモしたか
→ YES: 次の長い作業のとき、その1行を最初の指示に入れる
指示例: 今回の失敗を次回防ぐための注意を、作業開始時の指示に足す形で1文にしてください。

■ 判定
□ 戻る地点が決まり、作り直す範囲が「一部の工程」に絞れた
→ YES: そのまま部分的な作り直しへ進む
→ NO（どこまで正しいか分からない）: 状態が全く残っていない状態。今回は最初からやり直し、次回は必ずステップ0を仕込む
```

**ポイント**: 「最初からやり直す」を選ぶ前に、必ずステップ2（どこまで正しかったか）を試すこと。1回でも「戻る地点」を作れれば、次回から復旧が一気に楽になります。

## 5つの合言葉・早わかり（これだけで会話にはついていける）

| 合言葉 | 一言でいうと | 論文の試験のたとえ |
|---|---|---|
| プロンプトエンジニアリング | AIへの「指示の言い回し」を設計する | 解答のヒントをもらう |
| コンテキストエンジニアリング | AIに「渡す情報・資料」を設計する | 資料の持ち込み可の試験 |
| ハーネスエンジニアリング | AIがつながる「道具・記憶・スキル」を設計する | 電卓や検索も使ってよい試験 |
| ループエンジニアリング | 「計画→実行→確認→やり直し」の反復を設計する | 提出してフィードバックをもらい直す |
| グラフエンジニアリング | 「タスク・AI・状態のつなぎ方」を点と線で設計する | チームで協力して解く |
| （次段階）オントロジーエンジニアリング | 用語・目的・採点基準をチームで揃える | 共通のルールブックを持つ |

新しい合言葉は、古い合言葉を置き換えない。**上に積み重なる**。グラフの中の1点も、中身はループで、そのループは良いプロンプトでできている。
