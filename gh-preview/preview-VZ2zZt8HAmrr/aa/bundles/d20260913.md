## 1. 前提ブロックを固定する土台指示

```text
期待できるメリット: 2回目以降の会話で、前提部分がキャッシュ読み取り（75%引き）で再利用され、同じ作業の総額が下がる。
使う場面: そのプロジェクトで初めて指示を出すとき。以降の全セッションの土台になる。
前提・状況: プロジェクト固有のルール・用語・フォーマットが決まっている。
指示: これから毎回、私の依頼の前に「前提ブロック」を置きます。前提ブロックの中身（プロジェクト概要／用語集／出力フォーマット／禁止事項）は一字一句・順番を変えずに毎回先頭へ貼ります。あなたは前提ブロックを要約したり言い換えたりせず、そのまま読んでください。前提ブロックの後ろに、その回だけの依頼を書きます。
出力形式・制約: 前提ブロックの内容に変更提案があるときは、依頼への回答とは別に「前提ブロック改訂案」という見出しで最後にまとめる。本文中で勝手に変えない。
つまずきどころ: 前提の途中に日付や作業番号など「毎回変わる値」を入れると、そこでキャッシュが切れる。変わる値は前提ブロックの外（依頼側）へ出す。
```

## 2. 前提を1ファイルに集約する

```text
期待できるメリット: 前提が1ファイルに固まり、順番・文面のブレが物理的に起きなくなる。キャッシュ境界が安定する。
使う場面: 前提が複数の指示に散らばっていて、毎回コピペし直しているとき。
前提・状況: Claude Code なら CLAUDE.md、Codex なら AGENTS.md がリポジトリにある。
指示: いまチャットで渡している前提（ルール・用語・フォーマット・禁止事項）を、CLAUDE.md（Codex は AGENTS.md）の冒頭に「# 前提（毎回読む・編集しない）」という見出しで移してください。移したあとは、各セッションで私がこのファイルを最初に読ませます。あなたはこのブロックを要約せず全文読み、以降の判断の基準にしてください。
出力形式・制約: 移動後、元の指示文から重複する前提を削り、依頼だけが残るようにする。削った箇所の一覧を提示する。
つまずきどころ: このファイルを頻繁に書き換えると、書き換えるたびにキャッシュが作り直しになる。前提の更新は週1回などにまとめる。
```

## 3. 変わる部分を末尾に寄せる

```text
期待できるメリット: 固定部分（前提＋資料）が先頭にまとまり、そこがキャッシュされる。毎回変わる依頼だけが末尾になり、無駄な再計算が減る。
使う場面: 長い資料や過去ログを毎回添付して質問しているとき。
前提・状況: 添付する資料は毎回ほぼ同じ。質問だけが変わる。
指示: これからの会話は「固定部分 → 可変部分」の順で送ります。固定部分＝前提ブロック＋添付資料（順番も中身も毎回同じ）。可変部分＝今日の質問。あなたは固定部分を毎回同じものとして扱い、差分だけに注目して回答してください。
出力形式・制約: 回答の冒頭で「固定部分に前回との差分あり／なし」を1行で申告してから本題に入る。
つまずきどころ: 資料の並び順を日によって変えると、そこでキャッシュが無効になる。資料はファイル名の昇順など機械的な順で固定する。
```

## 4. セッション開始の定型プリアンブル

```text
期待できるメリット: 毎セッションの1通目が完全に同一文になり、その部分がキャッシュ対象として安定する。
使う場面: 1日に何度もセッションを立ち上げ直す使い方のとき。
前提・状況: 作業の入り口の指示（役割・進め方・確認のルール）がだいたい決まっている。
指示: 私が各セッションの最初に送る「定型プリアンブル」を作ってください。内容は、あなたの役割／作業の進め方（小さく分けて提案してから実行）／勝手にやらないこと（本番データの変更・外部送信・大きなリファクタ）／報告の形式。これを固定文にして、私は毎回コピペで送ります。
出力形式・制約: 200〜400字。日付・タスク名など可変要素を一切含めない。可変要素は2通目以降で渡す。
つまずきどころ: プリアンブルに「今日は」などの書き出しを入れると毎回変わってしまう。時制を含めない書き方にする。
```

## 5. キャッシュの効きを点検する（Claude Code）

```text
期待できるメリット: キャッシュ読み取りが実際に発生しているかを数字で確認でき、効いていない原因に早く気づける。
使う場面: 「安くなるはずなのに体感が変わらない」とき。数セッション回したあと。
前提・状況: Claude Code で数回やり取りした直後。
指示: /cost の出力を読んで、(1) キャッシュ読み取りトークンが全体の何割か、(2) キャッシュ書き込み（初回作成）ばかりで読み取りが伸びていないか、(3) 伸びていない場合に考えられる原因（前提文の変化・資料の並び替え・可変要素の混入）を、私の直近のやり取りを踏まえて指摘してください。
出力形式・制約: 「読み取り率○％／評価（良い・要改善）／原因の候補3つ／今日の直し方1つ」の順で、合計10行以内。
つまずきどころ: 1〜2ターンだけでは読み取りは伸びない。同じ前提で5ターン以上回してから見る。
```

## 7. 「窓をまたぐノート」を有効化する（Codex・実験的）

```text
期待できるメリット: コンテキストが埋まっても要約圧縮（compaction）で細部を失わず、過去の窓も検索できる。長い調査・デバッグで「なぜ失敗したか」の記録が残る。
使う場面: 1セッションが長くなり、途中で要約が走って文脈が薄くなる作業のとき。
前提・状況: Codex CLI 0.153 系。config.toml を編集できる。これは実験的機能で、数週間後に Astra で既定になる予定。
指示: config.toml に「コンテキスト窓をまたぐノート保持」を有効にする実験フラグを追加する手順を教えてください。追加後、長い作業では (1) 判断の理由、(2) 試して失敗した方法とその理由、(3) 次にやること、をノートに書き残しながら進めてください。窓が切り替わっても、このノートを引き継いで作業を続けてください。
出力形式・制約: まず config の編集手順、次に「ノートに何を書くか」のルール5項目。
つまずきどころ: 実験フラグ名は changelog で最新を確認する（バージョンで変わることがある）。有効化してもノートに何も書かせない指示だと効果が出ない。
```

## 9. 長い資料の読み込み順を固定する

```text
期待できるメリット: 仕様書・過去ログなど大きな資料が「毎回同じ順・同じ中身」で先頭に入り、その塊がキャッシュされる。質問のたびに読み直すコストが消える。
使う場面: 同じ仕様書や設計メモに対して、何日にもわたって質問を重ねるとき。
前提・状況: 参照資料が複数ファイルある。
指示: 参照資料を読み込む順番を固定します。順番は［ファイル名の昇順 / 私が指定した固定リスト］でお願いします。私は毎回この順で資料を貼ります。あなたは資料の順番や内容が同じである限り、それを既知のものとして扱い、差分がある場合だけ「資料に変更あり」と申告してください。
出力形式・制約: セッションの最初の応答で「資料○件を既知として読み込み。前回との差分：あり（該当ファイル名）／なし」を1行。
つまずきどころ: 資料の一部だけ最新版に差し替えると、その位置以降のキャッシュが切れる。差し替えるなら資料リストの末尾に「追補」として足す。
```

## 10. 週次バッチを前提固定テンプレにする

```text
期待できるメリット: 毎週回す定型作業（レポート生成・集計・要約）の前提が完全に固定され、週を追うごとにキャッシュ読み取りが伸びて単価が下がる。
使う場面: 毎週・毎日など決まった周期で同じ種類の作業をAIに投げているとき。
前提・状況: 作業の入力（データの置き場所・期間の指定方法）と出力フォーマットが決まっている。
指示: この週次作業を「固定テンプレ＋今週分の差し込み」に分けてください。固定テンプレ＝目的・入力の取り方・加工手順・出力フォーマット・チェック項目（毎週一字一句同じ）。差し込み＝対象期間と、今週だけの例外指示。固定テンプレを確定させて提示してください。以降、私は固定テンプレ＋差し込みの形で毎週送ります。
出力形式・制約: 固定テンプレは番号つき手順。可変値は差し込み側にしか置かない（テンプレ内に日付・週番号を書かない）。
つまずきどころ: 「先週のレポートを参照して」と本文で書くと参照先が毎週変わる。参照する過去分は差し込み側で資料として添付し、テンプレは参照方法だけ書く。
```

**ポイント**: キャッシュ読み取りが効くのは「前提が前回と同一」のときだけです。効きを確かめたいときは、同じ前提で5ターン以上回してから 5・6 の点検指示を使ってください。出力は必ずレビューしてから確定してください。
