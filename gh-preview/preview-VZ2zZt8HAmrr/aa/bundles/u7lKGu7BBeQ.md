# 🎁 モデル選定チェックリスト（Sol / Terra / Luna × エフォート × 速度）

GPT-5.6のSol・Terra・Lunaと推論エフォート（努力設定）・速度モードを、タスクの難易度に応じてどう組み合わせるかの早見チェックリストです。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: タスクを始める前にこのチェックリストを上から確認し、最初に条件が当てはまったモデル・エフォートから試してください。

```text
【GPT-5.6 モデル選定チェックリスト】

■ 原則：計画は賢いモデル、実行は安いモデル
□ 設計判断・仕様決めのような「賢さ」が要る部分だけ上位モデル（Sol High等）に任せる
□ 実装・反復・大量処理のような「量」をこなす部分は下位モデル（Luna等）に渡す
  （迷ったらこの原則に立ち返ると判断がぶれない）

■ ステップ0：そもそもワーク/Codexを開く必要があるか？
□ 定義の確認・ちょっとした言い換えなど「簡単な質問」か？
  → YES: ワーク/Codexを開かず、通常のチャットで済ませる（一番安い）

■ ステップ1：タスクの性質を確認する
□ 大量データの一括処理・単純な分類・速度重視のタスクか？
  → YES: Luna（高エフォート設定）から試す
□ 日常業務（下書き作成・要約・一般的なコーディング）か？
  → YES: Terra（標準エフォート）から試す
□ 複雑な意思決定・高価値な成果物・長時間の自律タスクか？
  → YES: Sol を検討する

■ ステップ2：グレードを上げる前に、エフォートを上げてみる
□ Terraで力不足を感じたら、まず「Terra Ultra」を試す
  （Sol Extra Highを検討する前に、Terra Ultraで足りないか確認する）
□ Lunaで力不足を感じたら、まず「Luna 高エフォート」を試す
  （Sol Highより下のグレードを検討する前に、高エフォートのLunaで足りないか確認する）

■ ステップ3：Solを使う場合の判断
□ Sol Ultra（マルチエージェント・最上位設定）は、コスト増に見合う価値があるかを個別に確認する
  （Sol Ultraの追加コストは、Sol Maxほどの価値がないことが多いという指摘がある）

■ ステップ4：試算のダブルチェック
□ 「モデルを1段階下げてエフォートを上げる」場合と
  「モデルはそのままでエフォートも標準」の場合を、
  実際のタスクで両方試算してから決める
  （単純な単価計算だけでは、どちらが安いか分からないことがある）

■ ステップ5：精度が必要なタスクは例外扱いにする
□ 実世界のコード修正・重要な意思決定など「間違えられない」タスクは
  コスパ最優先の判断から外し、実績のあるモデル・グレードを使う

■ ステップ6：速度を上げたいときはFast modeより先にEffortを見直す
□ 応答が遅いと感じたら、まずEffortを1段階下げられないか検討する
  （Fast modeはクレジット消費がStandardの2.5倍。GPT-5.6は自走力が高く、
  Fast modeと組み合わせると1メッセージで利用枠を大きく消費することがある）

■ ステップ7：subagentの暴走を事前に防ぐ
□ グローバルのAGENTS.mdに「指示がない限りsubagentを自律生成しない」旨を
  1行加えているか確認する
  （Solは親と同じモデル・エフォートでsubagentを生成する挙動があり、
  対策なしだと利用枠を想定外に消費しやすい）

■ ステップ8：作業前に利用枠のリセット状況を確認する
□ 重い作業に取りかかる前に、利用制限の一時緩和・リセットの
  公式アナウンスが出ていないか確認する
  （リセット直後の枠が多いタイミングに重い作業を寄せると、
  体感のコストパフォーマンスが変わる）
```

**ポイント**: このチェックリストは公式ベンチマーク（Artificial Analysis Coding Agent Index等）をもとにした目安です。タスクの性質によって最適解は変わるため、重要な用途では必ず実タスクで精度を確認してから本番運用してください。


### 2. Outcome-Firstプロンプトテンプレート（プロンプト集）

# 🎁 Outcome-Firstプロンプトテンプレート

手順を細かく書く「手順書型」から、成果と完了条件だけを書く「Outcome-First型」に切り替えるためのシステムプロンプトの型です。トークン削減とコスト削減の両方に効きます。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 各項目の〔　〕を自分のタスクに合わせて書き換えてから、システムプロンプトとして使ってください。既存の長いプロンプトを見直す場合は、まず今のプロンプトをこの型に当てはめ直し、当てはまらない指示（重複ルール・モデルが既にこなせる手順・振る舞いを変えない例示）を削ってください。

```text
【Outcome-Firstプロンプトの型】

# 成果定義
このタスクで達成すべきことは〔具体的な成果物・状態〕です。

# 完了条件（ここまでやれば終わり、という基準）
- 〔条件1：何を満たせば完了と言えるか〕
- 〔条件2〕
- 〔条件3〕

# 制約・安全要件（ALWAYS / NEVERは、ここだけに限定する）
- ALWAYS: 〔本当に外せない不変条件のみ。安全要件・権限の制約など〕
- NEVER: 〔本当に外せない禁止事項のみ〕

# 自律性の境界（承認が必要な操作を1箇所で定義する）
- 次の操作は、実行前に必ずユーザーに確認する: 〔外部への書き込み・破壊的操作・不可逆な操作など〕
- 上記以外の安全な操作（調査・下書き作成・ローカルでの試行など）は、都度の確認なしで進めてよい

# 経路はモデルに委ねる
上記の成果・完了条件・制約を満たす範囲で、具体的な手順・進め方はあなたの判断で決めてよい。
やり方を逐一指示しない。

---
チェック観点（プロンプトを書いた後に、この型に沿っているか自己点検する）:
- 重複しているルールはないか
- モデルが既にこなせる手順まで書いていないか
- 振る舞いを変えない不要な例示を入れていないか
- 指示同士が矛盾していないか（矛盾は指示の欠落より不安定さを生む）
```

**ポイント**: 出力はレビューしてから確定する。特に自律性の境界（承認が必要な操作）は、書き込み・削除・送信など取り返しのつかない操作を必ず含めること。


### 3. トークン切れ引き継ぎ書テンプレート（テンプレート）

# 🎁 トークン切れ引き継ぎ書テンプレート

GPT-5.6/Codexの利用枠（5時間・週次）が切れても、Claude Codeなど別のAIツールにそのまま貼り付けて続きから再開できる「引き継ぎ書」の型です。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 長引きそうなタスクだと感じた時点で、各項目の〔　〕を埋めながら書き進めてください。利用枠が切れた／別のツールに移りたくなったタイミングで、そのまま貼り付けて「この続きから再開してください」と伝えるだけで引き継げます。

```text
【トークン切れ引き継ぎ書】

# 目的（このタスクで最終的に達成したいこと）
〔1〜2文で、成果物・完了条件を書く〕

# ここまでの進捗
- 〔完了したこと1〕
- 〔完了したこと2〕
- 〔現在どこで止まっているか〕

# 次にやること（優先順）
1. 〔直近でやるべきこと〕
2. 〔その次〕

# 決定済みの事項（やり直さなくていいこと）
- 〔採用した設計・方針とその理由〕
- 〔検討したが不採用にした選択肢と理由〕

# 触ったファイル・参照した情報
- 〔ファイルパス／URL／ドキュメント名〕

# 避けるべきこと・注意点
- 〔ハマった落とし穴・繰り返さない失敗〕
- 〔変更してはいけない箇所〕

# 引き継ぎ先への一言
このドキュメントを読んだら、上記の続きから作業を再開してください。
不明点があれば、作業を進める前に確認してください。
```

**ポイント**: 「切れてから慌てて書く」のではなく、タスクを始める時点でこの型を頭に置いておくと、途中経過のメモがそのまま引き継ぎ書になる。移行先が変わっても（Claude Code・別のChatGPTセッションなど）同じ型で通用する。
