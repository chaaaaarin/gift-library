# 🎁 貼るだけでAstraの「裏の分身」と無駄読みを止める Codex節約プロンプト厳選10

**使い方**: 1本ずつ Codex のチャットに貼ります。1（止める）と 3（子を軽くする）はどちらか片方で十分です。4〜7は最初に1回やれば済む見直し、8〜10は毎回の依頼で使う型です。設定を変える前に、どのプロンプトもバックアップを取らせる形にしてあります。

## 1. サブエージェントを止める（バックアップつき）

```text
期待できるメリット: 裏で子のAIが何体も動く状態を止められる。子は親と同じモデル・同じ強さで動くため、Astra で子が並ぶと1回の依頼の消費がふくらむ。止めれば、軽い作業で子が走ることがなくなる。
使う場面: 短い修正や資料づくりしか頼んでいないのに、枠の減りが速いと感じるとき。並列で進める必要がある作業をほとんどしていないとき。
前提・状況: ローカルの Codex（デスクトップアプリのローカル作業・CLI・IDE）を ChatGPT アカウントで使っている。

指示:
Codex の設定ファイル ~/.codex/config.toml を編集して、サブエージェント（マルチエージェント機能）を止めてください。
1. 編集する前に、同じフォルダに config.toml.bak という名前でバックアップを作る
2. [agents] に enabled = false を設定する（見出しが無ければ末尾に追加）
3. [features] に multi_agent = false を設定する（見出しが無ければ末尾に追加）
4. 既存の設定は1行も消さない。同じ見出し・同じキーを2回書かない
5. 変更前と変更後の該当行だけを見せ、反映に再起動が要るかを1行で教える
この作業そのものでも、サブエージェントは使わないでください。

出力形式・制約: 変更前／変更後の該当行だけを並べる。ファイル全体は表示しない。
つまずきどころ: 会社のアカウント（Business・Enterprise）では、管理者の設定が優先されて手元の変更が効かないことがある。効かないときは管理者に確認する。大量のファイル調査を並列で進めたい日は、2 で元に戻す。
```

## 2. 止めたサブエージェントを元に戻す

```text
期待できるメリット: 大量のファイル調査やテストのように「分けた方が速い」作業の日だけ、元の並列の働き方に戻せる。バックアップと差分を確かめてから戻すので、ほかの設定を壊さない。
使う場面: 1 で止めたあと、並列で進めたい大きな作業が来たとき。
前提・状況: 1 のプロンプトで config.toml.bak が作られている。

指示:
~/.codex/config.toml の [agents] の enabled と、[features] の multi_agent を true に戻してください。
戻す前に config.toml と config.toml.bak を比べ、この2行以外にも違いがあれば、書き換えずにその内容を私に報告して止まってください。
違いがこの2行だけなら、true に戻したうえで、戻した2行を見せてください。
この作業そのものでは、サブエージェントは使わないでください。

出力形式・制約: 「差分はこの2行だけだった／ほかにも差分があった（内容）」を先に1行で書き、そのあとに戻した行を示す。
つまずきどころ: 戻したまま放置すると、元の消費に戻る。並列の作業が終わったら 1 をもう一度貼る。
```

## 3. 止めずに「子を軽く・少なく」する

```text
期待できるメリット: サブエージェントの良さ（メインの会話がログで散らからない・分けて速く進む）は残したまま、子が Astra のまま動くのをやめられる。GPT-5.6 Terra の出力は100万トークンあたり300クレジットで、Astra の1,250クレジットより単価が低い。同時に動く子の数にも上限をかけられる。
使う場面: 並列で進めたい作業はときどきあるので、完全には止めたくないとき。
前提・状況: ローカルの Codex を使っていて、1 の設定（止める）はしていない。

指示:
~/.codex/config.toml の [agents] に、次の3つを設定してください。
- default_subagent_model = "gpt-5.6-terra"
- default_subagent_reasoning_effort = "low"
- max_concurrent_threads_per_session = 2
編集する前に config.toml.bak を作り、既存の設定は消さないでください。同じ見出し・同じキーを2回書かないでください。
最後に、この設定で「私が依頼文でモデルや強さを指定した場合はどちらが優先されるか」を1行で教えてください。

出力形式・制約: 追加・変更した行だけを見せる。優先順位の説明は1行。
つまずきどころ: 依頼文で「Astra で子を作って」のように明示すると、依頼文の指定が優先される。子に難しい判断をさせたい作業では、その依頼だけモデルを指定する。
```

## 5. 既定の強さを「低」にして、Fast を付けっぱなしにしない

```text
期待できるメリット: 毎回の依頼が軽い強さから始まり、Fast mode の付けっぱなしがなくなる。Astra の Fast mode は通常の2.5倍のクレジットを使う。強さを下げても Astra の力が落ちるわけではなく、Astra の低い強さが Sol の高い強さを上回る場面もある。
使う場面: 強さを Extra High や Max にしたまま、軽い依頼まで流しているとき。Fast をいつ付けたか覚えていないとき。
前提・状況: ローカルの Codex を使っている。

指示:
~/.codex/config.toml を次のように直してください。
1. 編集する前に config.toml.bak を作る
2. model_reasoning_effort = "low" にする（ファイルの先頭側、見出しより上に置く）
3. service_tier = "fast" が書かれていれば、その行を消す
4. 既存のほかの設定は消さない。同じキーを2回書かない
最後に、今の既定の強さと、Fast が既定でオンかオフかを1行ずつ教えてください。

出力形式・制約: 変更した行と、確認結果の2行だけを返す。
つまずきどころ: 原因の分からないバグや設計の相談は、低い強さだと足りないことがある。その1件だけ依頼画面で強さを上げ、終わったら戻す。Fast が必要なときは、その場で /fast on にして、終わったら /fast off。
```

## 6. つないでいる MCP サーバーを棚卸しする

```text
期待できるメリット: 使っていない MCP サーバーを止めて、毎回のメッセージに足される説明の量を減らせる。MCP サーバーは、つなぐたびにメッセージの文脈が増え、枠を多く使う。設定を消さずに「止めるだけ」にするので、必要になったらすぐ戻せる。

指示:
~/.codex/config.toml に登録されている MCP サーバーを一覧にしてください。

まだ何も書き換えないでください。

出力形式・制約: 一覧は表にする。必要そうかどうかの判断には、根拠を1行ずつ添える。推測の場合は「推測」と書く。

```

## 7. 長くなった AGENTS.md をフォルダ別に分ける

```text
期待できるメリット: どの依頼にも毎回上乗せされる AGENTS.md の読み込み量を減らせる。大きなリポジトリでは、特定のフォルダでしか使わないルールをそのフォルダの AGENTS.md に移すと、関係ない作業では読み込まれなくなる。

指示:
ルートの AGENTS.md を読み、書かれているルールを次の3つに分けてください。

(b) 特定のフォルダの作業でしか使わないルール（どのフォルダか）
(c) もう使っていない・ほかと重複しているルール
```

### 3. Astraの枠が急に減ったときに、原因を5分で突き止めるチェックリスト（チェックリスト）
# 「今日はなぜか枠がすぐ溶ける」と感じたときに上から順に確かめると、モデル・強さ・分身・Fast・読み込み量のどこで食っているかが分かり、直す設定までそのままたどり着けます。慌てて Astra をやめたり、取っておいたリセットを使ったりせずに済みます。

# 🎁 Astraの枠が急に減ったときに、原因を5分で突き止めるチェックリスト

「今日はなぜか枠がすぐ溶ける」と感じたときに上から順に確かめると、モデル・強さ・分身・Fast・読み込み量のどこで食っているかが分かり、直す設定までそのままたどり着けます。慌てて Astra をやめたり、取っておいたリセットを使ったりせずに済みます。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 枠の減りがおかしいと感じたら、ステップ1から順に確認します。当てはまった項目の「→ YES」をやったら、次の同じくらいの作業で減り方を比べてください。一度に全部を変えると、どれが効いたか分からなくなります。

```text
【Astraの枠が急に減ったときの原因チェックリスト】

■ ステップ1：どの上限に当たっているかを確かめる
□ アプリの「設定 → 使用状況」（CLI なら /usage）で、5時間の上限と週の上限のどちらが減っているか見たか
→ NO: まず見る。どちらの上限かで、見直す範囲が変わる
→ YES（5時間の上限だけ）: 今日の使い方の問題。ステップ2から順に確認する
→ YES（週の上限も大きく減っている）: 数日分の使い方のクセの問題。ステップ2〜6をすべて確認する
（モデルを切り替えても、共有の枠そのものは戻らない）

■ ステップ2：モデルと強さを確かめる
□ 言い換え・抽出・短い修正のような軽い作業まで、Astra に頼んでいないか
→ YES: 定型の作業は Luna、ふだんの作業は Terra に振る
（Plus の5時間あたりの目安: Astra 5〜45通／Terra 25〜200通／Luna 250〜2,000通）
□ 強さが Extra High や Max のままになっていないか
→ YES: Light（CLI は low）から始め、結果を見てから上げる
指示例: ~/.codex/config.toml の model_reasoning_effort を "low" にしてください。編集前に config.toml.bak を作ってください。

■ ステップ3：分身（サブエージェント）を確かめる
□ モデルの選択が Ultra になっていないか
→ YES: 並列に分けられる大きな作業以外では Ultra を外す（Ultra はサブエージェントで作業を分けて進める）
□ 作業中に子のAIのスレッドが増えていないか（アプリの表示、CLI なら /subagents で確認）
→ YES（並列は要らない）: config.toml の [agents] に enabled = false を設定して止める
→ YES（並列はときどき要る）: [agents] に default_subagent_model = "gpt-5.6-terra" と default_subagent_reasoning_effort = "low" を設定して、子を軽くする
指示例: ~/.codex/config.toml の [agents] に enabled = false を設定してください。編集前にバックアップを作り、既存の設定は消さないでください。
□ AGENTS.md やスキルに「並列で進める」「エージェントに分ける」といった指示が書かれていないか
→ YES: その指示を、本当に並列が要る作業のときだけに限定する書き方に直す
指示例: AGENTS.md とスキルの説明から、サブエージェントや並列作業を指示している文を全部洗い出して表にしてください。まだ書き換えないでください。

■ ステップ4：Fast mode を確かめる
□ Fast mode が付いたままになっていないか（CLI なら /fast status）
→ YES: /fast off にする。Astra の Fast mode は通常の2.5倍のクレジットを使う
→ 速さが必要な作業のときだけ /fast on にして、終わったら戻す

■ ステップ5：読み込ませている量を確かめる
□ フォルダごと、過去のログごと渡していないか
→ YES: 関連するファイルだけに絞る。期間があるなら日付も絞る
□ 使っていない MCP サーバーがつながったままになっていないか
→ YES: 使わないサーバーは止める（設定は残したまま enabled = false）
□ AGENTS.md が長くなりすぎていないか
→ YES: 特定フォルダでしか使わないルールは、そのフォルダの AGENTS.md に移す
□ 1つの会話を長く続けすぎていないか（CLI の /status で残りのコンテキストを見る）
→ YES: 区切りのよいところで /compact か /new にする
□ 答えの形と長さを依頼文で決めているか
→ NO: 「A4 1枚・見出し3つ・前置き不要」のように、形と長さを先に書く

■ ステップ6：やり直しの回数を確かめる
□ 同じ依頼を3回以上やり直していないか
→ YES: 強さを上げる前に、指示・渡した資料・権限が足りているかを見直す（強さを上げても、足りない情報は補えない）
→ それでも通らない1件だけ、強さを一段上げる

■ ステップ7：直したあとに確かめる
□ 次に同じくらいの作業をしたとき、使用状況の減り方を前と比べたか
→ YES（減り方が落ち着いた）: 効いた設定をメモして、そのまま固定する
→ NO: 1つずつ変えて比べる。まとめて変えると、何が効いたか分からない
□ 会社のアカウント（Business・Enterprise）で、設定を変えても効かなかったか
→ YES: 管理者の設定が優先されている可能性がある。管理者に確認する
```

**ポイント**: いちばん先に見るのはステップ3（分身）とステップ4（Fast）です。この2つは、気づかないうちにオンになっていても画面上で目立たず、1回の依頼の消費をまとめて押し上げます。
