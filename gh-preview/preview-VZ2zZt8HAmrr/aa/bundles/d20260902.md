### 1. AIエージェント対応 着手チェックリスト（チェックリスト）
# 自分のサイトをAIエージェント対応（WebMCP／Site tools）にすべきか、するなら何から出すかを、上から順に読むだけで判断できる実践チェックリストです。セキュリティで確認すべきことまで入っています。

# 🎁 AIエージェント対応 着手チェックリスト

自分のサイトをAIエージェント対応（WebMCP／Site tools）にすべきか、するなら何から出すかを、上から順に読むだけで判断できる実践チェックリストです。セキュリティで確認すべきことまで入っています。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 上から順に □ を埋めていきます。「→ YES」に書かれた行動をその場で取ってください。`指示例:` はそのままAIに貼れます。

```text
【AIエージェント対応 着手チェックリスト】

■ ステップ1：そもそも対応する意味があるかを判定する

□ サイトに「人が繰り返し行う操作」があるか（検索・絞り込み・下書き・登録・比較）
  → YES: 対応する価値が高い。ステップ2へ進む
  → NO : 読み物中心のサイトなら、今は見送ってよい（記事は今でもAIが読める）

□ その操作を、人とAIが「同じ画面を見ながら」やる場面があるか
  → YES: WebMCPが向く。ステップ2へ
  → NO : 裏側でデータを渡すだけなら、MCPサーバーの方が向く（タブを開く必要がない）

□ 訪問者がログインして使うサイトか
  → YES: 効果が大きい。ログイン済みセッションをそのままAIが使える
  → NO : 公開情報だけなら効果は限定的。優先度を下げてよい

□ 自分（または社内）がChatGPTデスクトップアプリを使える環境か
  → YES: 動作確認ができる。ステップ2へ
  → NO : 検証手段がない状態で作らない。まずChromeのフラグで試せる環境を用意する
  指示例: Chromeで chrome://flags/#enable-webmcp-testing を有効にして再起動する手順を教えてください。

□ ワークスペースが Enterprise / Edu ではないか
  → YES（該当しない）: 進んでよい
  → NO （該当する）  : Site toolsは使えない。個人アカウントで検証環境を分ける


■ ステップ2：最初に出す操作を1つだけ決める

□ 「サイトで最もよく使われている操作」を1つ挙げられるか
  → YES: それを最初のツールにする。いきなり10個作らない
  指示例: このサイトのアクセスログから、最も使われている機能を上位5つ挙げてください。

□ その操作は「読むだけ」で完結するか（検索・一覧・詳細表示）
  → YES: 最初の1本に最適。取り返しがつかない操作がないので安全
  → NO : 書き込みや購入を含むなら、後回しにする（ステップ4の確認設計が先）

□ その操作に必要な入力が3つ以内か
  → YES: 説明文を書きやすい。着手してよい
  → NO : 入力が多い操作は、先に小さく分ける（絞り込みと並べ替えを別ツールにする等）

□ 操作の結果が、画面にも反映されるか
  → YES: 人とAIが同じ結果を見られる。WebMCPの価値が出る
  → NO : 画面に出ないなら、出るように直してから対応する


■ ステップ3：説明文（description）を書く

□ 操作の名前が、機能名ではなく「やること」になっているか
  → YES: そのままでよい（例: search_products、create_draft）
  → NO : 社内用語や画面名をやめて、動詞＋対象に直す

□ 説明文だけを読んで、初めて見る人が「いつ使う操作か」判断できるか
  → YES: 十分。次へ
  → NO : 「何をするか」に加えて「どんなときに使うか」を1文足す
  指示例: 次のツール説明文を、初見の人が「いつ使うか」まで判断できる文に書き直してください。

□ 似た操作が2つ以上あるとき、選び分けの基準が説明文に書いてあるか
  → YES: 十分
  → NO : 「Aは〜のとき、Bは〜のとき」を各説明文に書く（AIが取り違える最大の原因）

□ 入力の各項目に、単位・形式・例が書いてあるか
  → YES: 十分（例: 価格は税込・円、日付はYYYY-MM-DD）
  → NO : 書く。ここが曖昧だと、正しく呼ばれても結果がずれる

□ 読むだけの操作に「読み取り専用」の印を付けたか
  → YES: 安全に扱われる
  → NO : 付ける（annotations の readOnlyHint）


■ ステップ4：安全側の設計を決める

□ 取り消しが難しい操作（決済・送信・確定・削除）を最初のツールに含めていないか
  → YES（含めていない）: 進んでよい
  → NO （含めている）  : 外す。まず読むだけの操作で運用を固めてからにする

□ 書き込み系を出す場合、実行前に人の確認が入る設計になっているか
  → YES: 進んでよい
  → NO : 確認ステップを挟む。金額・法的責任が発生する操作は特に

□ ツールの説明文や返り値に、外部から投稿された文章が混ざる経路がないか
  → YES（混ざらない）: 進んでよい
  → NO （混ざる）    : そこが攻撃の入口になる。外部由来の文字列は返り値から外すか、
                       信頼できない内容である印を付ける

□ 他社サイトに自分のツールを見せる必要があるか
  → NO : 既定のまま（同一オリジンのみ）でよい。触らない
  → YES: 許可するオリジンを明示的に指定する。全許可にしない

□ ログインが必要な操作で、権限のない人が呼べてしまう経路がないか
  → YES（ない）: 進んでよい
  → NO         : ツール側でも権限チェックを行う（画面側の制御だけに頼らない）


■ ステップ5：出したあと、AI本人に直させる

□ 実際にAIに使わせて、最後まで完了したか
  → YES: ステップ6へ
  → NO : どこで止まったかを記録する。止まった箇所が説明文の直し先

□ AIが「どのツールを使うか」を毎回迷っていないか
  → YES（迷っていない）: 十分
  → NO : 説明文の選び分け基準が足りない。ステップ3の3項目に戻る

□ AIに使いにくい点を聞いたか
  → YES: 出てきた指摘を直す
  指示例: いま使ったツール群について、説明が曖昧だった点・分割した方がよい点・
          足りない入力項目を、優先度順に挙げてください。

□ 人が画面で行った変更を、AIが正しく認識できているか
  → YES: 十分
  → NO : 画面の状態とツールの返り値がずれている。同じデータを見るように直す


■ ステップ6：運用に乗せる

□ 対応した操作を、サイトの案内ページに書いたか
  → YES: 十分（訪問者が「AIで使える」と気づける）
  → NO : 書く。ツールは訪問しないと見つけられないので、告知しないと誰も使わない

□ 仕様変更を追う担当を決めたか
  → YES: 十分
  → NO : 決める。WebMCPはまだ提案段階の標準で、変わる可能性がある

□ 次に出すツールを1つ決めたか
  → YES: 1本ずつ増やす。まとめて作らない
  → NO : ステップ2に戻って、次によく使われる操作を選ぶ


■ 判定の目安

ステップ1で「YES」が3つ以上 → 今期の着手候補
ステップ1で「YES」が2つ以下 → 半年後に再判定でよい
ステップ4で「NO」が1つでも残っている → 公開しない。設計を直してから出す
```

**ポイント**: いちばん多い失敗は「ツールを10個まとめて作る」ことです。最初は読むだけの操作を1本だけ出し、AIに使わせて説明文を直す——このサイクルを回してから増やしてください。


### 2. サイト操作を任せる依頼文 厳選10（プロンプト集）
# ログインが必要で毎月・毎年つい後回しにしている手続きを、ChatGPT Workにそのまま任せるための依頼文を10本に絞りました。1本ごとに、使う場面・前提・そのまま貼れる本文・出力形式・期待できる結果・つまずきどころまで書いてあります。

# 🎁 サイト操作を任せる依頼文 厳選10

ログインが必要で毎月・毎年つい後回しにしている手続きを、ChatGPT Workにそのまま任せるための依頼文を10本に絞りました。1本ごとに、使う場面・前提・そのまま貼れる本文・出力形式・期待できる結果・つまずきどころまで書いてあります。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: ChatGPT Work を開き、使いたい番号の「指示」ブロックをそのまま貼ります。〈 〉の中は自分の状況に置き換えてください。ログインを求められたら、表示された安全な入力欄に自分で入力します。

```text
【サイト操作を任せる依頼文 厳選10】

────────────────────────────────
01. 公共料金のプランを比較して、乗り換え候補を出す
────────────────────────────────
使う場面: 電気・ガスの請求が上がってきて「そろそろ見直したいけど面倒」と思っているとき。
月に一度、明細が届いたタイミングで開くのが向いています。

前提: 電力会社・ガス会社のマイページにログインできる状態（IDとパスワードは自分で入力します）。

指示:
〈電力会社名〉のマイページにログインして、直近12か月分の使用量（kWh）と請求額を月ごとに取り出して。
そのうえで、同じ会社の他プランに変えた場合の年間金額を、今の実使用量で計算し直して比較して。
プラン変更の申し込みはしないで。比較結果を出すところまでで止めて。

出力形式: 「月／使用量kWh／請求額」の表と、「現行プラン／候補プランA／候補プランB」の年間試算表の2つ。
最後に「乗り換えると年間いくら変わるか」を1行で。基本料金・燃料費調整額・再エネ賦課金の扱いが
プランで違う場合は、その差も注記して。

期待できる結果: 明細を12枚開いて電卓を叩く作業（30〜40分）が、確認だけで終わります。

つまずきどころ: 会社によっては明細のダウンロードがPDFのみのことがあります。
その場合は「PDFを開いて数字を読み取って」と一言足してください。

────────────────────────────────
02. 加入している保険で、その治療が給付対象か調べる
────────────────────────────────
使う場面: 家族が入院した・通院した後、給付金の請求ができるか分からないまま放置しているとき。

前提: 保険会社のマイページにログインできる状態。契約している保険の名称が分かること。

指示:
〈保険会社名〉のマイページにログインして、私が契約している保険の契約内容と特約の一覧を確認して。
そのうえで「〈治療内容・入院日数・手術の有無〉」が給付の対象になるかを、約款の該当箇所を示しながら判断して。
請求手続きの申し込みはしないで。対象かどうかの判断と、必要書類の洗い出しまでで止めて。

出力形式: 「①対象になりそうか（なる／ならない／要確認）②根拠にした約款の条項名 ③必要な書類の一覧
④提出期限」の4項目。判断が割れる部分は「要確認」にして、何を保険会社に聞けばいいかを質問文の形で書いて。

期待できる結果: 「請求できるか分からないから放置」が、その日のうちに「書類を集めるだけ」に変わります。

つまずきどころ: 約款がPDFで数百ページある場合、読み込みに時間がかかります。
「特約の一覧を先に出して、関係しそうな特約だけ約款を読んで」と順番を指定すると速くなります。

────────────────────────────────
03. サブスクの棚卸しをして、解約候補を出す
────────────────────────────────
使う場面: クレジットカードの明細に見覚えのない定額課金が並んでいて、何がいくらか把握できていないとき。

前提: カード会社またはネット銀行のマイページにログインできる状態。

指示:
〈カード会社名〉のマイページにログインして、直近6か月の明細から毎月ほぼ同額で繰り返し引き落とされている
支払いを全部抜き出して。サービス名・月額・初回課金月・6か月の合計額を一覧にして。
解約の手続きはしないで。一覧を出すところまでで止めて。

出力形式: 月額の高い順に並べた表（サービス名／月額／初回課金月／6か月合計）。
そのうえで「直近3か月で1度も値上がりも変動もないもの」に印を付けて、
最後に「6か月合計の総額」と「上位3件を解約した場合の年間削減額」を書いて。

期待できる結果: 明細を6か月分見比べる作業がなくなり、解約する・しないの判断だけが手元に残ります。

つまずきどころ: 決済代行会社を経由していると、明細の表記がサービス名と一致しません。
「表記が不明なものは、その文字列で検索して何のサービスか調べて」と足してください。

────────────────────────────────
04. 役所・窓口の空き枠を探して、予約内容を用意する
────────────────────────────────
使う場面: 免許更新・パスポート・各種証明書の窓口予約を取りたいが、空き枠を探すのが面倒なとき。

前提: 予約サイトのアカウント（自治体によっては不要）。自分の空いている日時が分かること。

指示:
〈自治体名・予約サイト名〉を開いて、〈手続き名〉の予約枠を探して。
〈9月10日〜9月30日の平日午前〉で空いている枠を全部リストにして。
予約の確定はしないで。候補を出して、私が選んだら入力内容の準備まで進めて。

出力形式: 「日付／時間帯／会場／残枠数」の表。近い順ではなく、私の希望条件に合う順に並べて。
候補がゼロだった場合は、条件をどう緩めれば取れそうか（別会場・別時間帯）を3案出して。

期待できる結果: カレンダーと予約サイトを往復する15分が、候補表を見て選ぶだけになります。

つまずきどころ: 自治体の予約サイトは自動アクセスを弾くことがあります。
止まった場合は、ブラウザの操作を引き継いで自分で1画面進めてから、続きを任せてください。

────────────────────────────────
05. 請求書を突き合わせて、会計ソフト登録の下準備をする
────────────────────────────────
使う場面: 月末、メールに届いた請求書PDFを会計ソフトに1件ずつ入力している時間をなくしたいとき。

前提: メールが接続済みであること。会計ソフトのマイページにログインできる状態。

指示:
〈対象月〉に受信したメールから、請求書・領収書の添付ファイルを全部集めて。
それぞれについて、発行元・請求日・支払期日・税抜金額・消費税額・税込金額・インボイス登録番号の有無を読み取って。
そのうえで〈会計ソフト名〉にログインして、同じ月に既に登録済みの取引と突き合わせて、
未登録のものだけを抜き出して。登録の実行はしないで。差分の一覧を出すところまでで止めて。

出力形式: 「未登録」の表（発行元／請求日／支払期日／税込金額／登録番号の有無）と、
「登録済みだが金額が一致しないもの」の表の2つ。金額が読み取れなかったものは別枠で列挙して。

期待できる結果: 突き合わせ作業（1時間前後）が、差分の確認と入力だけになります。

つまずきどころ: スキャン画像の請求書は読み取り精度が落ちます。
「読み取りに自信がないものは、確度低として別枠に出して」と足しておくと事故が減ります。

────────────────────────────────
06. 出張の候補便と宿を比較表にする
────────────────────────────────
使う場面: 出張が決まったが、便と宿の組み合わせを比べるのが面倒で先送りしているとき。

前提: 予約サイトのアカウント（会員価格を見たい場合）。会社の旅費規程が分かること。

指示:
〈出発地〉から〈目的地〉へ、〈日付〉に移動して〈日付〉に戻る出張の候補を出して。
往路は〈現地10時着まで〉、復路は〈18時以降発〉の条件で、交通手段（新幹線／飛行機）ごとに3案ずつ。
宿は〈駅から徒歩10分以内・1泊1万円以内〉で3件。予約や購入は絶対にしないで。比較表までで止めて。

出力形式: 「往路／復路／宿」の3ブロック。それぞれ「出発時刻・到着時刻・所要時間・金額・キャンセル条件」を表で。
最後に「合計金額が安い組み合わせ」「移動時間が短い組み合わせ」の2案を提示して。

期待できる結果: 3サイトを行き来する30分が、表を見て決める3分になります。

つまずきどころ: 「予約しないで」を書き忘れると、確認を求められて止まるだけとはいえ手間が増えます。
金額が動く操作を含む依頼には、毎回この一文を入れる癖をつけてください。

────────────────────────────────
07. 期限のある手続きを棚卸しして、必要書類を用意する
────────────────────────────────
使う場面: 車検・免許・パスポート・各種資格の更新時期がバラバラで、気づいたら期限間近になっているとき。

前提: 該当するマイページや、書類の写真・PDFが手元にあること。

指示:
私の〈自動車検査証／運転免許証／パスポート／〇〇資格〉の有効期限を確認して、
今日から1年以内に期限が来るものを全部リストにして。
それぞれについて、更新に必要な書類・費用・受付が始まる時期・手続きできる場所を調べて。
申し込みはしないで。準備リストを作るところまでで止めて。

出力形式: 期限が近い順の表（対象／有効期限／受付開始日／必要書類／費用／場所）。
そのうえで「今すぐ着手すべきもの」「3か月後に着手すればいいもの」の2つに仕分けして。

期待できる結果: 「そろそろだった気がする」が、日付の入った準備リストになります。

つまずきどころ: 書類の写真から日付を読み取らせる場合、有効期限と発行日を取り違えることがあります。
出てきた日付は必ず現物と1回突き合わせてください。

────────────────────────────────
08. 返品・交換の手続きを、集荷手配まで進める
────────────────────────────────
使う場面: ネットで買ったものを返品したいが、手順を調べるのが面倒で期限を過ぎそうなとき。

前提: 購入したショップのアカウントにログインできる状態。注文番号が分かること。

指示:
〈ショップ名〉にログインして、注文番号〈番号〉の返品可否と期限を確認して。
返品できる場合は、返品理由を〈理由〉として申請フォームの入力内容を用意して。
そのうえで集荷の希望日時を〈日付・時間帯〉として、配送業者の集荷申し込み内容も準備して。
最終送信の前に必ず内容を私に見せて。私が確認するまで送信はしないで。

出力形式: 「①返品可否と期限 ②返送方法（元払い／着払い／コンビニ持込）③申請フォームの入力内容
④集荷の申し込み内容 ⑤返金の時期と方法」の5項目。送信ボタンを押す直前の状態で止めて報告して。

期待できる結果: 返品ページを探す・規約を読む・伝票を用意する、の3工程が確認だけになります。

つまずきどころ: 返品期限を過ぎている場合でも手続きを進めようとすることがあります。
「期限を過ぎていたらそこで止めて報告して」と最初に条件を書いておくと確実です。

────────────────────────────────
09. 条件に合う物件・中古品を探して、候補を保存する
────────────────────────────────
使う場面: 引っ越しや買い替えの検討中で、条件に合うものを毎日見るのが続かないとき。

前提: 検索サイトのアカウント（お気に入り保存に必要な場合）。譲れない条件が言語化できていること。

指示:
〈サイト名〉で〈エリア〉の〈物件種別／商品カテゴリ〉を、
必須条件〈家賃10万円以内・駅徒歩10分以内・2階以上〉、あれば嬉しい条件〈独立洗面台・宅配ボックス〉で検索して。
必須条件を全部満たすものだけを候補として、お気に入りに保存して。
問い合わせや申し込みはしないで。保存と一覧化までで止めて。

出力形式: 「物件名／家賃＋管理費／駅徒歩／階数／満たしているあれば嬉しい条件の数」の表を、
最後の列の多い順に並べて。必須条件をギリギリ満たさないが惜しいものは、別枠で3件まで理由付きで。

期待できる結果: 毎日サイトを見る習慣がなくても、候補が溜まった状態から検討を始められます。

つまずきどころ: 「あれば嬉しい条件」を必須として扱ってしまい、候補がゼロになることがあります。
必須と任意は、この依頼文のように必ず言葉で分けて書いてください。

────────────────────────────────
10. ポイント・マイルの期限を調べて、使い道を出す
────────────────────────────────
使う場面: 気づいたらポイントが失効している、を毎年繰り返しているとき。

前提: ポイントサービスのマイページにログインできる状態。

指示:
〈サービス名〉にログインして、現在の保有ポイント数と、失効予定のポイントを期限ごとに一覧にして。
そのうえで、3か月以内に失効する分について、そのサービス内で交換できるものを
「1ポイントあたりの価値」が高い順に5つ挙げて。交換の実行はしないで。候補を出すまでで止めて。

出力形式: 「①保有ポイント総数 ②失効予定の表（期限／ポイント数）③交換候補の表（交換先／必要ポイント／
1ポイントあたりの円換算／注意点）」の3項目。期間限定ポイントと通常ポイントは必ず分けて表示して。

期待できる結果: 年に数千円分こぼしていた失効が、期限前のリマインドと候補提示で止まります。

つまずきどころ: 期間限定ポイントと通常ポイントを混ぜて集計されることがあります。
出てきた数字は、マイページの表示と1回だけ突き合わせてください。

────────────────────────────────
共通の注意（全部の依頼文に効きます）
────────────────────────────────
□ 「〜の実行はしないで。〜までで止めて」を必ず入れる
  → 金額・契約・送信が動く操作は、確認前に進ませない

□ ログインは、表示された安全な入力欄に自分で打つ
  → チャット欄にIDやパスワードを貼らない

□ 設定のアクセス権限は「常に確認」のままにしておく
  → 慣れるまでは1サイトずつ自分で承認する

□ 結果は必ず出典（どのページを見たか）とセットで受け取る
  → 「参照したページのURLも一緒に出して」と足す

□ 終わったら、使わないサイトのログイン状態は消す
  → 設定 > クラウドブラウザ > ブラウザデータ から消去する
```

**ポイント**: どの依頼文も「〜はしないで。〜までで止めて」で終わらせてあります。この一文があるかどうかで、任せたときの安心感がまったく変わります。自分で新しい依頼文を作るときも、必ずこの形で締めてください。
