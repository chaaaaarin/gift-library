### 3. integration層（exec/SDK/App-Server）選択 判断シート（判断シート）

# 🎁 integration層（exec/SDK/App-Server）選択 判断シート

自社のユースケースに合った統合方式を5ステップで判定するチェックシートです。

**受け取り方**: 下のコードブロックをコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 上から順に□に沿って読み進め、該当したらYES/NOの指示に従ってください。

```text
【integration層(exec/SDK/App-Server)選択 判断シート】

■ ステップ1：対話が必要か判定する
□ ユーザーとの対話（進捗確認・途中変更）は不要で、1回投げたら結果だけ受け取れればよい
→ YES: codex exec が候補。ステップ4へ
□ 何らかの対話性・継続性が必要
→ NO: ステップ2へ

■ ステップ2：自社UIに組み込むか判定する
□ 既存のダッシュボード・管理画面の中にエージェントを常駐させ、承認フローもUIで完結させたい
→ YES: Codex App-Server が候補。ステップ4へ
□ UIは最小限でよく、自社プログラムから開始・再開できれば十分
→ NO: ステップ3へ

■ ステップ3：SDKで足りるか確認する
□ JSON-RPCを自分で組みたくない、TypeScriptのライブラリインターフェースで十分
→ YES: Codex SDK が候補（指示例: 「Codex SDKで、タスクの開始・進捗取得・再開を行う最小ラッパーを実装して」）

■ ステップ4：承認が必要なアクションの有無を確認する
□ 実際のデータ変更・外部通知・金銭が絡む操作が含まれる
→ YES: 承認フロー（人間の確認ステップ）を必ず設計に含める
指示例: 「このワークフローの中で、実行前に人間の承認が必須なアクションを洗い出して」
□ 読み取り・調査のみで完結する
→ NO: 承認フローは省略可（ただし監査ログは残す）

■ ステップ5：統合コストを見積もる
□ codex exec: 統合コスト低い。コマンド一発で試せる
□ Codex SDK: 統合コスト中。ライブラリ組み込みのみ
□ Codex App-Server: 統合コストやや高い。JSON-RPCバインディング構築が必要
→ 迷ったら、まずexecで最小規模の試験導入をしてから、必要に応じてSDK・App-Serverへ引き上げる（指示例: 「この業務を、まずcodex execで試験導入する最小プランを作って」）

（判定基準の一次情報: developers.openai.com/blog/codex-as-a-platform、openai.com/index/unlocking-the-codex-harness/）
```

**ポイント**: 迷ったら常に「まずexecで最小規模の試験導入」に倒すのが安全です。
