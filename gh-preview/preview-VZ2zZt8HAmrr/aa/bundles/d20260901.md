# 🎁 Kiro or Codex 選択判断シート

「同じGPT-5.6を、Kiroで使うべきかCodexのままでいいか」を、タスクの性質・予算・チーム規模から判定するためのシートです。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 新しいコーディングタスクに着手する前に、このシートに沿って上から順に判定してください。

```text
【Kiro or Codex 選択判断シート】

■ ステップ1：タスクの仕様がどこまで固まっているか
□ 作りたいものの要件（何を・誰のために・なぜ）を、着手前にある程度言語化できるか
□ 実装より先に、設計や手順を整理してから進めたいタイプの作業か
→ YES: Kiroの仕様駆動フローが向く。ステップ2に進む
→ NO(要件がまだ曖昧で、対話しながら固めたい): Codexのまま対話ベースで進める方が早い

■ ステップ2：タスクの長さと段階の数を確認する
□ 1回の作業が長時間・複数ステップ（要件→設計→複数タスク→テスト）にわたるか
□ 途中で何度もレビュー・差し戻しが発生しそうな規模か
→ YES: Kiroの「タスクに分割して段階ごとに確認する」仕組みが効きやすい
→ NO(短時間で完結する軽い修正・調査タスク): Codexで十分。Kiroに移す手間の方が大きい
指示例: 「このタスクを要件・設計・実行タスクの3段階に分けるとしたら、それぞれどのくらいのボリュームになるか見積もって」

■ ステップ3：料金体系との相性を確認する
□ 月によってタスク量が大きく変動し、使った分だけ払うクレジット制の方が合っているか
□ それとも5時間ごとの利用上限のリズムで管理する方が自分の作業ペースに合っているか
→ クレジット制が合う: Kiro（Pro以上、$20/月〜）を検討する
→ 利用上限制が合う: Codex（Plus、¥3,000/月〜）を継続する
□ どちらのプランでも、GPT-5.6のSol/Terra/Lunaのうちどれを使うかでコスト効率が大きく変わることを忘れていないか
→ YES(重いタスクにSol/Terraを使い、軽い作業はLunaに回す想定ができている): ステップ4に進む
→ NO: 先にタスクの重さとモデルの対応を整理してから金額を比較する

■ ステップ4：使いたいモデルの範囲を確認する
□ 今後もOpenAI以外のモデル（Claude・オープンウェイト等）を同じツールで試したい可能性があるか
→ YES: 複数モデルを選べるKiroの方が将来的な選択肢が広い
→ NO(OpenAIのモデルだけで完結する見込み): Codexのままで機能的な不足はない
指示例: 「このタスクをKiroとCodexそれぞれで進めた場合の、想定コストと作業の進めやすさを比較して」

■ ステップ5：判断を確定する
□ ステップ1〜4の答えが「Kiroが向く」に3つ以上寄っているか
→ YES: このタスクはKiroの仕様駆動フローで進める
→ NO: このタスクはCodexで進める。「乗り換え」ではなく「タスクごとの使い分け」として運用する
```

**ポイント**: 「Codexより優れている」という一次情報の裏付けは無いため、全タスクを一律でKiroに寄せる判断はしない。タスクごとにこのシートで判定し、使い分けを前提にする。

# 🎁 Kiroスペック駆動 スタート指示文10選

Kiroに初めて触るときに何を打ち込めばいいか分からない、という一番のハードルを解消するための、要件→設計→タスク→実装の各段階でそのまま貼れる指示文10本です。

**受け取り方**: 下の各コードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: Kiroのチャット欄（IDE／CLI／Webいずれも可）に、該当する段階のものをそのまま貼り付けて送信してください。〔　〕内は自分の状況に置き換えてください。

## 1. 要件を言葉から仕様に変換する

使う場面: 頭の中にある「作りたいもの」を、初めてKiroに渡すとき。まだ何も整理していない段階でOK。
前提: 作りたいものについて、目的・利用者・困っていることを自分の言葉で説明できる状態。
```text
これから〔作りたいもの〕を作りたいです。目的は〔解決したい課題〕、使うのは〔利用者像〕です。
現状〔困っていること〕があります。この内容を要件（何を・誰のために・なぜ作るか）として
整理し、曖昧な点があれば箇条書きで質問してください。
```
出力形式: 要件の箇条書き＋不明点の質問リスト。期待できる結果: 自分では言語化できていなかった前提条件が質問として返ってくる。つまずきどころ: 質問に全部答えないと次の設計段階が曖昧なまま進んでしまうので、必ず一つずつ回答してから次に進む。

## 2. 要件から技術設計へ落とし込む

使う場面: 要件がひととおり固まり、実装方針を決めたいとき。
前提: 手順1で要件の整理が完了していること。
```text
先ほど整理した要件をもとに、技術設計を作ってください。使う技術構成の候補、
データの持ち方、画面や処理の分割方針を示し、判断が分かれる箇所は
「A案／B案」の形で選択肢を出してください。
```
出力形式: 設計方針の箇条書き＋選択肢がある箇所はA/B比較。期待できる結果: 実装に入る前に方向性のズレを防げる。つまずきどころ: 選択肢を提示されたら「とりあえずA案で」のように必ず自分で選び、Kiro任せで進めない。

## 3. 設計を実行可能なタスクに分割する

使う場面: 技術設計に合意したあと、実際の作業に取りかかる直前。
前提: 手順2の設計内容が確定していること。
```text
確定した設計を、1つずつ完了確認できる実行タスクに分割してください。
各タスクには「何をするか」「完了の判断基準」をセットで書き、
依存関係がある場合は実行する順番も示してください。
```
出力形式: 番号付きタスクリスト（各項目に完了基準つき）。期待できる結果: 「どこまでやれば1タスク完了か」が明確になり、レビューのタイミングを掴みやすい。つまずきどころ: 完了基準が曖昧なタスクが混ざっていたら、その場で聞き返して具体化させる。

## 4. タスクを1件ずつ実装させる

使う場面: タスク分割が終わり、実装フェーズに入るとき。
前提: 手順3のタスクリストがあること。
```text
タスクリストの1番目から順に実装してください。1タスク完了するごとに、
何を変更したか・完了基準を満たしているかを報告し、次のタスクに進む前に
私の確認を待ってください。
```
出力形式: タスクごとの変更内容報告＋完了基準チェック。期待できる結果: 全タスクを一気に進めず、段階ごとにレビューできるので手戻りが小さく済む。つまずきどころ: 「確認を待ってください」を省くと複数タスクが一気に進んでしまい、間違いに気づいたときの手戻りが大きくなる。

## 5. レビューチェックポイントで差し戻す

使う場面: 実装結果を見て、意図と違う・直したい点があるとき。
前提: 手順4で何らかの実装が返ってきていること。
```text
今の実装のうち〔具体的な箇所〕が意図と違います。理由は〔理由〕です。
この点だけを修正し、他のタスクの完了基準には影響を与えないでください。
```
出力形式: 修正差分の提示＋影響範囲の説明。期待できる結果: 局所的な修正だけで済み、他の完了済みタスクを壊さない。つまずきどころ: 「他に影響を与えないでください」を書き忘れると、無関係な箇所まで書き換えられることがある。

## 6. プロパティベーステストで正しさを確認する

使う場面: 実装が一通り終わり、通常のユニットテストだけでは不安が残るとき。
前提: 対象の機能が動く状態になっていること。
```text
〔対象の機能〕について、ユニットテストが見落としがちな境界値・異常系を
プロパティベーステスト（ファジング）で検証してください。見つかった問題は
再現条件つきで報告してください。
```
出力形式: 検出した問題点のリスト（再現条件つき）。期待できる結果: 手動では気づきにくいエッジケースの不具合を事前に発見できる。つまずきどころ: 検出された問題を全部その場で直そうとせず、優先度をつけてから対応する。

## 7. チーム標準・既存コードベースの文脈を渡す

使う場面: 個人開発ではなく、既存のチームルールやコードベースに合わせて実装してほしいとき。
前提: 参照してほしいルールファイルやディレクトリの場所が分かっていること。
```text
今回の実装では〔参照してほしいファイル／ディレクトリ〕にあるチームの
命名規則・設計方針に合わせてください。既存コードと矛盾する書き方をする場合は、
実装前に必ず確認してください。
```
出力形式: 実装前の確認事項の提示。期待できる結果: チームの既存スタイルから外れた実装を未然に防げる。つまずきどころ: 参照範囲を広く指定しすぎるとコンテキストが膨らみ、逆に処理が重くなることがあるので必要な範囲に絞る。

## 8. 長時間タスクを要約つきで引き継ぐ

使う場面: 1回のセッションで終わらない長いタスクを、翌日以降に持ち越すとき。
前提: 途中まで進んだタスクリストと実装状況があること。
```text
ここまでの進捗を、完了したタスク・未着手のタスク・次に着手すべき理由の3点で
要約してください。次回セッションでこの要約だけを渡せば再開できる形にしてください。
```
出力形式: 進捗要約（完了/未着手/次にやること）。期待できる結果: セッションをまたいでも文脈が失われず、続きから再開できる。つまずきどころ: 要約を保存せずセッションを閉じると、次回また一から状況説明が必要になる。

## 9. Codexで書いた内容をKiro向けに整理し直す

使う場面: これまでCodexで対話しながら進めていた作業を、Kiroの仕様駆動フローに乗せ直したいとき。
前提: Codex側でのやり取り履歴やメモがあること。
```text
これまでCodexで進めていた〔作業内容〕のやり取りを渡します。この内容から
要件・設計・タスクを抽出し、Kiroの仕様駆動フォーマットに整理し直してください。
```
出力形式: 要件/設計/タスクの3段構成に再整理したもの。期待できる結果: 対話ベースで進めていた作業を、構造化された形に移行できる。つまずきどころ: Codex側のやり取りが断片的すぎると抽出精度が落ちるため、要点だけでも自分でメモしておく。

## 10. コストを意識してモデルを使い分ける

使う場面: 同じKiro内で、タスクの重さに応じてSol/Terra/Lunaを使い分けたいとき。
前提: 今から着手するタスクの複雑さをおおよそ把握していること。
```text
このタスクは〔タスクの複雑さ・重要度〕です。この内容に見合ったモデル
（Sol/Terra/Lunaのいずれか）を選ぶとしたらどれが適切か、クレジット消費の
観点も含めて理由つきで提案してください。
```
出力形式: 推奨モデルとその理由（クレジット消費への言及つき）。期待できる結果: 重いタスクにLunaを使ってしまう・軽いタスクにSolを使ってクレジットを浪費する、といった無駄を防げる。つまずきどころ: 提案されたモデルを鵜呑みにせず、実際のタスクの重さと照らして最終判断は自分で行う。
