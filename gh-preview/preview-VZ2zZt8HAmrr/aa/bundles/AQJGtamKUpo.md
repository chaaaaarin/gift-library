# 🎁 Cloudflare最強度 自己診断チェックシート

自分・自社にとってCloudflare OSやEmDashへの乗り換えがどれくらい向いているかを判定するチェックシートです。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: メモアプリやAIチャットに貼り付けて、□の項目に順番に答えてください。

```text
【Cloudflare最強度 自己診断チェックシート】

■ ステップ1：今の困りごとを確認する
□ サイトの更新・保守作業に毎月何時間もかかっている
→ YES: ステップ2へ進む
□ 「管理画面にログインできない」問題を過去に経験した
→ YES: EmDashのパスキーログインが直接効く。ステップ2へ
□ 社内の繰り返し業務をAIに任せたいが、権限まわりが不安で踏み出せていない
→ YES: Cloudflare OSのGatekeeper設計が刺さる可能性が高い。ステップ2へ
指示例: 「自分の直近1ヶ月のサイト運用・繰り返し業務にかかった時間を洗い出して、合計時間を出して」

■ ステップ2：技術的な前提を確認する
□ Claude CodeやAIコーディングツールを日常的に使っている（使う予定がある）
→ YES: EmDash構築を任せやすい。ステップ3へ
□ Cloudflareのアカウントを既に持っている、または作ることに抵抗がない
→ YES: ステップ3へ
□ 独自ドメインを既に持っている、または新規取得を検討している
→ YES: ステップ3へ
指示例: 「Claude Codeで簡単なWebページを1つ作らせてみて、指示のしやすさを確認したい。手順を教えて」

■ ステップ3：組織としての向き不向きを確認する
□ 1人〜数人の個人・小規模事業である
→ YES: EmDashへの乗り換えを優先的に検討してよい
□ 数十人以上の組織で、部門ごとに繰り返し業務が多くある
→ YES: Cloudflare OSの5ステップ（集める→知識化→権限を絞る→アプリ化→展開）から着手を検討
□ 機密情報・個人情報を扱う業務が多い
→ YES: 導入前にGatekeeperの権限設計を必ず確認する
指示例: 「うちの組織構成（人数・部門）を伝えるので、Cloudflare OSを試すならどの部門から始めるべきか提案して」

■ ステップ4：総合判定
□ ステップ1〜3で「YES」が6個以上
→ YES: 積極的に試す価値が高い。まずは小さく試すところから始める
□ 「YES」が3〜5個
→ YES: 特定の業務（サイト運用 or 特定部署の繰り返し業務）に絞って試す
□ 「YES」が2個以下
→ YES: 今は様子見でよい。半年後に再チェックする
指示例: 「診断結果を伝えるので、まず何から着手すべきか3ステップで提案して」
```

**ポイント**: この診断はあくまで目安です。機密情報を扱う業務では、導入前に必ず社内のセキュリティ担当者に確認してください。

指示: この1週間の作業ログ（時刻・作業名・所要時間）を渡すので、朝一番に必ず発生している定型作業を3つ選び出して。

前提: 毎週の定例会議で議事録を取っている人向け。

出力形式: 固定パターンは「項目名／金額目安／申請頻度」の表、変動パターンは箇条書きで出力して。

# 🎁 WordPress延命 vs 卒業 判断早見表

今のWordPressサイトを、そのまま使い続けるべきか、EmDash等への乗り換えを検討すべきかを判断するための早見表です。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 自分のサイトの状況を思い浮かべながら、上から順に□へ答えてください。

```text
【WordPress延命 vs 卒業 判断早見表】

■ ステップ1：プラグインへの依存度を確認する
□ 使っているプラグインが10個を超えている
→ YES: プラグイン経由のセキュリティリスクが相対的に高い。ステップ2へ
□ 特定の業務システムと連携する独自プラグインを使っている
→ YES: 移行前に代替手段の有無を先に調べる。ステップ2へ
□ プラグインはほぼ使っておらず、基本機能だけで運用している
→ YES: 移行のハードルは低い。ステップ3へ
指示例: 「今使っているプラグイン一覧を伝えるので、それぞれ何をしているか整理して」

■ ステップ2：更新・保守の負担を確認する
□ 直近1年でログイン不能・表示崩れなどのトラブルを経験した
→ YES: 卒業を検討する優先度が高い
□ 毎月の更新作業（本体・テーマ・プラグイン）に30分以上かかっている
→ YES: 卒業した場合の時短効果が大きい
□ 更新作業は制作会社に外注していて自分では手を動かしていない
→ YES: 移行のコスト対効果を制作会社と一緒に確認する
指示例: 「直近1年のサイト保守作業でかかった時間を月別に洗い出して、年間の合計時間を出して」

■ ステップ3：会員機能・データベース機能の必要性を確認する
□ 会員登録・有料記事の出し分けなど、複雑な機能を使っている
→ YES: 移行前にEmDashのD1・R2でどこまで再現できるか検証する
□ ブログ・お知らせなど、シンプルな情報発信が中心
→ YES: 移行のハードルは低い
指示例: 「今使っている会員機能・データベース機能を一覧化して、それぞれ移行後にどう代替できそうか整理して」

■ ステップ4：総合判定
□ ステップ1〜3で「卒業を検討」に該当する項目が多い
→ YES: EmDashでの構築を試験的に1サイト作ってみる（本番切り替えは検証後）
□ 該当項目が少なく、今のWordPress運用に大きな不満がない
→ YES: 無理に移行せず、更新作業だけ自動化・簡略化する方法を検討する
指示例: 「診断結果を伝えるので、移行するとしたら何から手をつけるべきか、リスクが低い順に提案して」
```

**ポイント**: 本番サイトをいきなり切り替えず、まずは検証用のサイトを1つ作ってから判断するのが安全です。
