自作MCPサーバー 発注プロンプト100選

Claude Code などに貼るだけで、自分専用のMCPサーバー（AIに手順やデータを届けるサーバー）の設計と雛形づくりが進む発注文を100本まとめました。ファイルを配るのをやめて、URL1本で配れる状態を目指すためのものです。

スキルを配る

001手元のスキル1本を配信サーバーにする
前提: 手元の .claude/skills/ にあるSKILL.mdを1本、他の人にも使ってもらいたい。ファイルは渡したくない。
指示: そのSKILL.mdの本文をそのまま返すリモートHTTPのMCPサーバーを作って。読み込む対象はファイルパスで指定できるようにし、サーバー起動時ではなく呼び出しのたびにファイルを読み直す実装にして。
出力形式: 起動手順・接続用URL・claude mcp add のコマンド例を最後にまとめて出して。コードは1ファイルに収め、依存パッケージは最小限にして。
002複数スキルをまとめて配信する
前提: skills/ フォルダの下にスキルが複数あり、今後も増やしていく予定。増えるたびにサーバーを直したくない。
指示: 指定フォルダ配下のSKILL.mdを起動時ではなく毎回スキャンして、一覧と本文を返すMCPサーバーを作って。スキル名はフォルダ名から取り、frontmatterのdescriptionを一覧の説明に使って。
出力形式: フォルダ構成の想定図・実装コード・動作確認の手順（スキルを1つ足して反映されるか試す方法）を順に出して。
003GitHubリポジトリを配信元にする
前提: スキルの正本をGitHubの公開リポジトリで管理していて、pushしたら配信内容も切り替わってほしい。
指示: 指定リポジトリのraw URLからSKILL.mdを取得して返すMCPサーバーを作って。取得結果は短時間だけキャッシュし、キャッシュ時間は環境変数で変えられるようにして。取得失敗時は前回の内容を返し、その旨をログに残して。
出力形式: 実装コードと、キャッシュ時間の目安（何分が妥当か）の判断材料を3行で添えて。
004受け取る人ごとに配るスキルを変える
前提: 受講者のコースによって配りたいスキルが違う。URLは同じにしたいが、中身は人によって変えたい。
指示: リクエストのAuthorizationヘッダのトークンを見て、そのトークンに紐づくスキル群だけを返すMCPサーバーを作って。トークンとスキル群の対応は最初はJSONファイルで持ち、後からデータベースに差し替えられる構造にして。
出力形式: 実装コード・対応表のJSON例・トークンが無効なときのエラーレスポンス例の3点を出して。
005スキルの更新履歴を持たせる
前提: スキルを頻繁に直すので、受け取る側が「何が変わったか」を確認できるようにしたい。
指示: スキル本文に加えて、更新日時と直近の変更点を返すMCPサーバーを作って。変更点はリポジトリのコミットメッセージから取るか、専用のCHANGELOGファイルから読むかを選べるようにして。
出力形式: 2つの方式それぞれの実装と、どちらを選ぶべきかの判断基準を3行で書いて。
006配布用スキルの棚卸しツールを作る
前提: 配布予定のスキルが増えてきて、説明文が似ていて呼び分けられない懸念がある。
指示: 指定フォルダ配下の全SKILL.mdを読み、descriptionが似ているものの組み合わせと、本文中で矛盾する指示（同じ対象に別の手順を書いている箇所）を検出するMCPサーバーを作って。
出力形式: 検出結果は「重複候補」「矛盾候補」の2つの表で返して。各行に該当ファイル名と該当行番号を入れて。
007スキルの説明文だけを一覧で返す
前提: 受け取る側が「今どんなスキルが配られているか」だけをさっと見たい。本文は必要なときだけでいい。
指示: 各スキルの名前・説明文・最終更新日だけを軽量に返す一覧用の口と、名前を指定したときだけ本文を返す口の、2つを持つMCPサーバーを作って。一覧のレスポンスは1件あたり200文字以内に収めて。
出力形式: 2つの口それぞれのレスポンス例（JSON）を実際の値入りで示して。
008旧版に固定できるようにする
前提: スキルを更新したら一部の人の手順が合わなくなった。全員を最新に強制したくない。
指示: スキルにバージョン番号を持たせ、接続側が版を指定できるMCPサーバーを作って。指定が無ければ最新を返し、古い版は3世代まで保持して、それ以前は最も古い保持版を返しつつ警告文を添えて。
出力形式: 実装コードと、版の付け方（いつ番号を上げるか）のルールを箇条書き5行で添えて。
009配信をやめる手順まで作る
前提: 一度配り始めたスキルを、将来きれいに止められる状態にしておきたい。
指示: スキルに「提供終了予定日」を持たせられるMCPサーバーを作って。終了日の30日前からは本文の先頭に案内文を自動で足し、終了日を過ぎたら本文の代わりに移行先の案内だけを返すようにして。
出力形式: 実装コードと、案内文の文面テンプレート（30日前・終了後の2種類）を出して。
010配布物の中身を検査してから出す
前提: 配布するSKILL.mdに、うっかりAPIキーや個人名を書き残したまま出すのが怖い。
指示: 配信する直前に本文を検査し、APIキーらしき文字列・メールアドレス・電話番号・絶対パスが含まれていたら配信を止めて警告を返すMCPサーバーを作って。検査ルールは設定ファイルで足せるようにして。
出力形式: 実装コード・既定の検査ルール一覧・検出時のレスポンス例を出して。
011スキルに使い方の例を同梱する
前提: 受け取った人が「どう呼べばいいか分からない」と言う。説明文だけでは足りていない。
指示: SKILL.mdと同じフォルダにあるexamples/配下のファイルを読み、本文の末尾に「使用例」として自動で連結して返すMCPサーバーを作って。例が3つ以上あるときは短い2つだけを選んで足して。
出力形式: 実装コードと、examples/に置くファイルの命名規則を提案して。
012配る前にAIに読ませて品質を見る
前提: スキルを作ったが、意図した場面でちゃんと呼び出されるか自信がない。
指示: SKILL.mdのdescriptionを読んで「どんな依頼文のときに呼ばれそうか」を5例、「呼ばれてほしくないのに呼ばれそうな依頼文」を3例、生成して返すMCPサーバーを作って。
出力形式: 呼ばれる例／誤爆しそうな例を分けた表で返し、最後に説明文の改善案を1つ提案して。
013スキルを日本語と英語で出し分ける
前提: 日本語圏と英語圏の両方にスキルを配りたいが、2重管理はしたくない。
指示: SKILL.md.ja と SKILL.md.en を持ち、接続側の指定または既定設定に応じて言語を出し分けるMCPサーバーを作って。片方しか無いスキルは、あるほうを返しつつ「未翻訳」と注記して。
出力形式: 実装コードと、翻訳漏れを一覧で出す方法を添えて。
014配信内容をそのままファイルにも書き出す
前提: 配信に一本化したいが、サーバーが落ちたときに何も使えなくなるのは避けたい。
指示: 配信中の全スキルをzipにまとめて書き出す機能を持つMCPサーバーを作って。書き出しは呼び出しで実行でき、内容は配信されているものと完全に同じにして。
出力形式: 実装コードと、書き出したzipを手元に展開する手順を3行で書いて。
015スキルの本文をテンプレートから組み立てる
前提: 業務ごとにほぼ同じ形のスキルを量産したいが、人によって書き方がバラバラになる。
指示: 共通のひな型と、業務ごとの差分（対象・手順・注意点）を別ファイルで持ち、呼び出し時に合成して1つのSKILL.mdとして返すMCPサーバーを作って。
出力形式: ひな型ファイルの例・差分ファイルの例・合成結果の例を、実際の文面入りで示して。
016配布スキルの読了状況を測る
前提: 配ったスキルが実際に呼び出されているのか分からず、改善の当てがつかない。
指示: どのスキルが・いつ・どのトークンから呼ばれたかを記録するMCPサーバーを作って。記録は追記のみのファイルに書き、個人が特定できる情報はトークンのハッシュ値だけにして。
出力形式: 実装コード・記録ファイルの1行の書式・集計用の簡単な確認コマンドを出して。
017人気スキルの順位を返す
前提: 利用ログはあるが、そこから次に何を作るかの判断につながっていない。
指示: 直近30日の呼び出し回数でスキルを並べ替え、上位10件と、1度も呼ばれていないスキルの一覧を返すMCPサーバーを作って。集計期間は指定できるようにして。
出力形式: 集計結果の表と、「未使用スキルをどう扱うか」の判断基準を3行で添えて。
018配信サーバーの健康状態を返す
前提: 配信サーバーが不調でも、受け取る側から見ると「AIが賢くない」に見えてしまい原因が分からない。
指示: 配信できているスキル数・最後に更新を検知した時刻・直近1時間のエラー件数を返す確認用の口を持つMCPサーバーを作って。異常があれば人間が読める短い説明文も添えて。
出力形式: レスポンス例（正常時・異常時の2種類）を実際の値入りで示して。

社内ナレッジを配る

019社内規定をAIに読ませる形で配る
前提: 経費規定・就業規則などのPDFやWord文書があり、社員が毎回探すのに時間がかかっている。
指示: 指定フォルダの文書を読み込み、質問に関係する条項だけを抜き出して返すMCPサーバーを作って。抜き出した箇所には必ず出典（ファイル名と見出し）を添え、書かれていないことは推測せず「規定に記載なし」と返して。
出力形式: 実装コードと、文書を追加したときの反映手順を3行で書いて。
020手順書を「今どこか」つきで返す
前提: 業務手順書が長く、途中まで進めた人が「次に何をするか」を毎回探し直している。
指示: 手順書を段階ごとに分割して持ち、現在の段階を指定すると「今の段階の詳細」「前後の段階の見出し」だけを返すMCPサーバーを作って。全文は要求されたときだけ返して。
出力形式: 分割の書式（区切り方の記法）と実装コード、レスポンス例を出して。
021議事録から決定事項だけを配る
前提: 会議の議事録が溜まっているが、決定事項だけを後から探すのが大変。
指示: 議事録ファイル群から「決定事項」「保留事項」「担当者と期限」だけを抽出して返すMCPサーバーを作って。抽出は見出しやキーワードに頼りすぎず、該当が曖昧なときは元の文をそのまま引用して返して。
出力形式: 抽出結果の表（日付・決定事項・担当・期限・出典ファイル）で返す実装にして。
022用語集を全社に配信する
前提: 社内でしか通じない略語が多く、新入社員が毎回聞いて回っている。
指示: 用語・読み・意味・使う場面・関連語を持つ用語集を配信するMCPサーバーを作って。表記ゆれ（大文字小文字・カタカナ・英字）を吸収して引けるようにして。
出力形式: 用語集の元データ書式（CSVまたはYAML）の例と、実装コードを出して。
023過去のトラブル対応を検索できるようにする
前提: 過去のインシデント対応記録が散らばっていて、似た事象が起きても活かせていない。
指示: 障害記録から「症状」「原因」「対処」「再発防止」を構造化して返すMCPサーバーを作って。症状の言い回しが違っても引けるように、同義語の対応表を持てるようにして。
出力形式: 記録の推奨書式・実装コード・検索結果の返し方（上位3件＋要約）を出して。
024書類のひな型を配信する
前提: 見積書・提案書・報告書のひな型がフォルダに散らばっていて、最新版がどれか分からない。
指示: ひな型の種類を指定すると、最新版の本文と「どこを埋めるか」の一覧を返すMCPサーバーを作って。埋める箇所は〈〉で囲む記法に統一して。
出力形式: ひな型の管理方法（フォルダ構成と版の付け方）と実装コードを出して。
025承認フローの判断基準を配る
前提: 金額や種類によって承認者が変わるルールがあり、担当者が毎回上長に確認している。
指示: 条件（金額・種類・部署）を渡すと、必要な承認者と根拠となる規定条項を返すMCPサーバーを作って。条件が規定の範囲外なら、勝手に判断せず「規定外・要確認」と返して。
出力形式: 条件と承認者の対応表の書式例と、実装コードを出して。
026教育コンテンツを段階順に配る
前提: 研修教材があるが、全部まとめて渡すと受講者が最初の1つで止まってしまう。
指示: 受講者の進捗（何番まで終えたか）を渡すと、次の1段階分の教材だけを返すMCPサーバーを作って。進捗はトークンごとにサーバー側で保持し、指定が無ければ最初から返して。
出力形式: 進捗の保持方法・実装コード・受講者から見た使い方の説明文を出して。
027よくある質問を配信する
前提: 顧客からの同じ質問に、担当者ごとに違う答え方をしてしまっている。
指示: 質問と模範回答の対を配信するMCPサーバーを作って。回答には「言ってはいけない表現」の注記も持たせ、本文と一緒に返して。該当する質問が無ければ、勝手に作らず「未登録」と返して。
出力形式: 元データの書式・実装コード・未登録時のレスポンス例を出して。
028文書の禁止表現チェックを配る
前提: 資料や広告で使ってはいけない表現があるが、担当者ごとに把握度が違う。
指示: 渡された文章に禁止表現・要注意表現が含まれていないか検査して返すMCPサーバーを作って。指摘には該当箇所・理由・言い換え候補を必ず添え、判断が微妙なものは「要確認」として分けて。
出力形式: 禁止表現リストの書式と実装コード、検査結果の表の形を出して。
029部署ごとに見える範囲を変える
前提: 同じ配信サーバーで、部署によって見せていい文書と見せられない文書がある。
指示: トークンに部署情報を紐づけ、その部署に許可された文書だけを返すMCPサーバーを作って。許可されていない文書は一覧にも出さず、存在自体を伏せて。
出力形式: 権限設定ファイルの例・実装コード・権限外アクセス時のレスポンス例を出して。
030変更があった文書だけを知らせる
前提: 規定や手順が更新されても、現場が気づかず古いやり方を続けてしまう。
指示: 前回の確認時刻を渡すと、それ以降に更新された文書の一覧と変更点の要約を返すMCPサーバーを作って。要約は3行以内にし、原文の該当箇所へのリンクを添えて。
出力形式: 実装コードと、変更点の要約が長くなりすぎたときの切り詰め方を書いて。
031顧客ごとの取り決めを配る
前提: 顧客ごとに納期・請求条件・連絡ルールが違い、担当が代わるたびに事故が起きる。
指示: 顧客名を渡すと、その顧客固有の取り決めと過去のトラブル履歴を返すMCPサーバーを作って。顧客名の表記ゆれ（正式名称・略称・英字）を吸収して引けるようにして。
出力形式: 元データの書式・実装コード・表記ゆれ対応表の作り方を出して。
032社内の連絡先と役割を配る
前提: 誰が何の担当か分からず、社内で聞いて回る時間が無駄になっている。
指示: 業務内容を渡すと、担当部署・担当者の役割・連絡すべき手段を返すMCPサーバーを作って。個人の連絡先そのものは返さず、部署の窓口までに留めて。
出力形式: 元データの書式・実装コードと、個人情報を持たせない設計になっている理由を3行で書いて。
033業界の法令・規約要点を配る
前提: 広告表現や商品説明で守るべき法令・規約があり、担当者ごとに確認レベルが違う。
指示: 業種と表現内容を渡すと、確認すべき条項の要点と、判断が分かれる場合の相談先を返すMCPサーバーを作って。法的判断は断定せず、必ず「最終確認は専門家へ」の注記を付けて。
出力形式: 元データの書式・実装コード・注記の定型文を出して。
034過去の提案書から勝ちパターンを配る
前提: 受注した提案書は残っているが、なぜ勝てたのかが個人の頭の中にしかない。
指示: 提案書群から「構成の順番」「使われた根拠の種類」「価格の見せ方」を抽出して返すMCPサーバーを作って。顧客名・金額などの固有情報は伏せ字にして返して。
出力形式: 抽出結果の表と、伏せ字にする項目の一覧を出して。
035現場からの改善要望を集める口を作る
前提: 配ったスキルや手順への不満が、こちらまで届かないまま放置されている。
指示: 使っている最中に「この手順が合わない」と伝えられる受付口を持つMCPサーバーを作って。受け付けた内容は対象スキル名・日時・本文の形で追記保存し、個人特定情報は保存しないで。
出力形式: 実装コード・保存形式・溜まった要望を読み返す簡単な手順を出して。

データにつなぐ

036スプレッドシートを読み取り専用でつなぐ
前提: 売上や在庫の管理をスプレッドシートでしており、AIに聞くたびに手でコピーしている。
指示: 指定したシートの指定範囲を読み取り専用で返すMCPサーバーを作って。書き込み機能は一切持たせず、範囲外の取得要求は拒否して。取得結果は列名つきの表形式にして。
出力形式: 実装コード・認証情報の安全な渡し方・読み取り範囲の設定例を出して。
037社内データベースに安全に問い合わせる
前提: 社内データベースの数字をAIに集計させたいが、更新や削除は絶対にさせたくない。
指示: 参照のみを許可するMCPサーバーを作って。実行できる文の種類を参照系だけに限定し、対象テーブルも許可リストで縛って。1回の取得件数にも上限を設けて。
出力形式: 実装コード・許可リストの設定例・拒否時のエラー文例を出して。
038CSVの山を検索できるようにする
前提: 過去の実績CSVが大量にあり、必要な行を探すのに毎回表計算ソフトで開いている。
指示: 指定フォルダのCSVを横断して条件に合う行だけを返すMCPサーバーを作って。ファイルごとに列名が違う場合に備え、列名の対応表を設定で持てるようにして。
出力形式: 実装コード・対応表の書式・返す件数が多すぎるときの絞り込み方を出して。
039問い合わせ履歴を読み込む
前提: 顧客からの問い合わせ履歴が別システムにあり、対応のたびに探しに行っている。
指示: 顧客識別子を渡すと直近の問い合わせ履歴を時系列で返すMCPサーバーを作って。個人情報にあたる項目は既定で伏せ、明示的に要求されたときだけ返す設計にして。
出力形式: 実装コード・伏せる項目の一覧・履歴が無いときのレスポンス例を出して。
040予定表を読み取って空き時間を返す
前提: 打ち合わせの日程調整で、空き時間を毎回手で探して伝えている。
指示: 指定期間の空き時間を、指定した長さで切り出して返すMCPサーバーを作って。予定の中身は返さず、空いている時間帯だけを返して。営業時間外と昼休みは除外して。
出力形式: 実装コード・除外時間の設定例・レスポンス例（実際の日時入り）を出して。
041課題管理ツールの状況を読む
前提: 課題管理ツールを見ないと進捗が分からず、毎朝の確認に時間がかかっている。
指示: 担当者・状態・期限で絞り込んだ課題一覧を返すMCPサーバーを作って。期限切れと今日期限のものは先頭にまとめ、残り件数も添えて。
出力形式: 実装コード・絞り込み条件の指定方法・レスポンス例を出して。
042アクセス解析の要点だけを返す
前提: サイトの数字を見るために毎回管理画面を開いていて、見る項目もその場の気分で変わる。
指示: 期間を渡すと、訪問数・流入元の上位5件・よく見られたページ上位5件だけを返すMCPサーバーを作って。前期間との増減も併記して。
出力形式: 実装コード・レスポンス例・「どの数字を見ないと決めたか」の理由を3行で書いて。
043在庫と発注点をつなぐ
前提: 在庫データはあるが、発注が必要かどうかの判断が担当者の勘に頼っている。
指示: 商品ごとの在庫数と、あらかじめ決めた発注点を突き合わせて「発注が必要な商品」を返すMCPサーバーを作って。発注点は商品ごとに設定でき、未設定の商品は別枠で一覧に出して。
出力形式: 実装コード・発注点の設定書式・レスポンス例を出して。
044経費データを科目別にまとめる
前提: 経費の明細はあるが、科目ごとの集計を毎月手作業でやっている。
指示: 期間を渡すと科目別の合計と、前月比で大きく増えた科目の上位3件を返すMCPサーバーを作って。科目の分類ルールは設定ファイルで直せるようにして。
出力形式: 実装コード・分類ルールの書式・レスポンス例を出して。
045受注データから納期リスクを返す
前提: 受注案件の納期が守れないことがあるが、危ないものを事前に把握できていない。
指示: 受注データと工程の進捗を突き合わせ、納期に間に合わない可能性がある案件を返すMCPサーバーを作って。判定根拠（どの工程がどれだけ遅れているか）も一緒に返して。
出力形式: 実装コード・判定ロジックの説明・レスポンス例を出して。
046社内Wikiを横断して引く
前提: 社内Wikiの情報が多すぎて、キーワード検索では目的のページにたどり着けない。
指示: 質問文を渡すと、関連しそうなページの見出しと該当箇所の抜粋を返すMCPサーバーを作って。全文は返さず、ページへのリンクと抜粋3件までに絞って。
出力形式: 実装コード・抜粋の長さの目安・該当なしのときのレスポンス例を出して。
047メールの下書きだけを作る
前提: 定型的なメールの作成に時間がかかるが、AIに送信までさせるのは怖い。
指示: 宛先・用件・トーンを渡すと下書きを作って保存するだけのMCPサーバーを作って。送信機能は実装せず、下書きの保存先と件名の付け方を明確にして。
出力形式: 実装コードと、「送信機能を持たせない」という設計判断の理由を3行で書いて。
048ファイル置き場から最新版だけを返す
前提: 共有フォルダに同じ資料の版が複数あり、どれが最新か毎回迷う。
指示: 資料名を渡すと、更新日時が最も新しいファイルの場所と要約を返すMCPサーバーを作って。似た名前のファイルが複数あるときは、候補を一覧で出して人に選ばせて。
出力形式: 実装コード・ファイル名の揺れを吸収する方法・レスポンス例を出して。
049外部APIの結果を整形して返す
前提: 外部サービスのAPIをそのまま呼ぶと、返ってくるデータが冗長でAIが読み切れない。
指示: 外部APIを呼び、必要な項目だけを抜き出して整形して返すMCPサーバーを作って。抜き出す項目は設定で変えられるようにし、既定では10項目以内に収めて。
出力形式: 実装コード・整形前後のデータ量の比較・設定の書式を出して。
050複数サービスの数字を1つにまとめる
前提: 売上・広告費・問い合わせ数が別々のサービスにあり、まとめて見るのに手間がかかる。
指示: 複数の取得元から数字を集め、1つの表にまとめて返すMCPサーバーを作って。どれか1つが取得に失敗しても他は返し、失敗した取得元を明記して。
出力形式: 実装コード・取得元の設定書式・一部失敗時のレスポンス例を出して。
051検索結果の鮮度を明示する
前提: 取得したデータがいつ時点のものか分からず、古い数字で判断してしまうことがある。
指示: すべてのレスポンスに取得時刻とデータの基準日時を必ず含めるMCPサーバーを作って。基準日時が指定日数より古い場合は、本文の先頭に警告文を自動で足して。
出力形式: 実装コード・警告文の文面・しきい値の決め方を出して。
052取得できる範囲を先に宣言させる
前提: AIが取得できないデータについて、それらしい答えを作ってしまうことがある。
指示: サーバーが扱える対象・期間・粒度を一覧で返す口を持つMCPサーバーを作って。範囲外の要求には推測で答えず、扱える範囲を提示して差し戻して。
出力形式: 一覧のレスポンス例・範囲外要求時のレスポンス例・実装コードを出して。

業務を自動で回す

053定型レポートを毎朝作らせる
前提: 毎朝、前日の数字を集めて報告用にまとめる作業に30分かかっている。
指示: 前日分のデータを集めて定型の報告文を組み立てて返すMCPサーバーを作って。文面のひな型は外部ファイルで持ち、数字が前日比で大きく動いた項目には自動で注記を付けて。
出力形式: 実装コード・ひな型ファイルの例・出力される報告文の実例を出して。
054会議前の下調べをまとめる
前提: 打ち合わせ前に相手先の情報や過去のやり取りを調べる時間が取れていない。
指示: 相手先の名前を渡すと、過去のやり取りの要約・前回の宿題・未解決の論点を1枚にまとめて返すMCPサーバーを作って。情報源が無い項目は空欄にせず「記録なし」と明示して。
出力形式: 実装コード・まとめの構成（見出しの順番）・レスポンス例を出して。
055請求書の突合を自動化する
前提: 請求書と発注データの突合を目視でやっており、月末に時間を取られている。
指示: 請求データと発注データを突き合わせ、金額・数量・単価が一致しない行だけを返すMCPサーバーを作って。差異は「金額違い」「数量違い」「対応する発注なし」に分類して。
出力形式: 実装コード・突合ルールの設定書式・差異一覧の表の形を出して。
056問い合わせを振り分ける
前提: 問い合わせの内容によって担当が変わるが、振り分けを人が毎回判断している。
指示: 問い合わせ本文を渡すと、担当部署の候補と判断理由、緊急度を返すMCPサーバーを作って。判断に迷う場合は候補を複数返し、勝手に1つに決めないで。
出力形式: 実装コード・振り分けルールの書式・判断が割れた場合のレスポンス例を出して。
057議事録から次アクションを切り出す
前提: 会議は活発だが、決まったことが実行に移らない。
指示: 議事録を渡すと「誰が・何を・いつまでに」の形でアクション項目だけを抽出して返すMCPサーバーを作って。担当や期限が書かれていない項目は「未定」と明示し、勝手に補わないで。
出力形式: 実装コード・抽出結果の表・未定項目の扱い方の説明を出して。
058見積の妥当性をチェックする
前提: 見積を作るとき、過去実績や社内の基準単価との整合を確認しきれていない。
指示: 見積の明細を渡すと、社内基準単価との差が大きい行と、過去の類似案件の単価を返すMCPサーバーを作って。差が大きい理由の推測はせず、事実だけを示して。
出力形式: 実装コード・基準単価データの書式・チェック結果の表を出して。
059資料の体裁を機械的に整える
前提: 資料の表記ゆれ（半角全角・数字の書き方・敬称）を毎回手で直している。
指示: 文書を渡すと表記ルールに沿って整形し、変更箇所の一覧を返すMCPサーバーを作って。意味が変わる可能性がある変更は自動適用せず、候補として提示するだけにして。
出力形式: 実装コード・表記ルールの書式・変更一覧の表の形を出して。
060採用応募の一次整理をする
前提: 応募書類が多く、担当者によって見る観点がバラついている。
指示: 応募書類を渡すと、募集要件との合致項目・不足項目・確認したい点を返すMCPサーバーを作って。合否の判断はせず、事実の対応関係だけを示して。人種・性別・年齢などに関わる推測は一切行わないで。
出力形式: 実装コード・要件データの書式・出力例を出して。合否判断をさせない設計理由も3行で書いて。
061契約書の確認ポイントを洗い出す
前提: 契約書のレビューで見るべき条項が担当者の経験に依存している。
指示: 契約書を渡すと、社内で定めた確認項目それぞれについて「該当条項の有無」と「原文の引用」を返すMCPサーバーを作って。法的な可否の判断はせず、必ず「最終確認は法務へ」と添えて。
出力形式: 実装コード・確認項目リストの書式・出力例を出して。
062日報から詰まりを見つける
前提: 日報は集まっているが、読み流しているだけで改善につながっていない。
指示: 直近の日報群を読み、同じ課題が3日以上続いて記載されているものを抽出して返すMCPサーバーを作って。個人の評価には使わないため、出力は課題内容ごとの集計にして氏名は含めないで。
出力形式: 実装コード・集計結果の表・氏名を含めない設計理由を3行で書いて。
063定期タスクの抜けを見つける
前提: 月次・週次の定型作業に抜けが出ることがあるが、気づくのが遅い。
指示: 定期タスクの一覧と実施記録を突き合わせ、期日を過ぎて未実施のものを返すMCPサーバーを作って。実施記録の書式は柔軟に受け付け、判定できないものは「判定不能」として分けて。
出力形式: 実装コード・タスク定義の書式・出力例を出して。
064顧客への定期連絡を組み立てる
前提: 顧客への定期連絡が担当者任せで、忙しい月は抜けてしまう。
指示: 最終接触日から一定期間が過ぎた顧客を抽出し、それぞれに合った連絡文の下書きを返すMCPサーバーを作って。送信は行わず、下書きの提示までに留めて。
出力形式: 実装コード・期間のしきい値設定・下書きの実例を出して。
065作業ログから所要時間の目安を返す
前提: 作業時間の見積が担当者の感覚で、実績と乖離することが多い。
指示: 過去の作業ログから、作業種別ごとの所要時間の中央値と幅（最短・最長）を返すMCPサーバーを作って。件数が5件未満の種別は「データ不足」と明示して。
出力形式: 実装コード・ログの書式・出力例を出して。平均ではなく中央値を使う理由も1行添えて。
066翻訳と用語統一を同時にやる
前提: 海外向け資料を作るとき、担当者ごとに訳語が変わってしまう。
指示: 文章を渡すと、社内の用語対訳表に従って翻訳し、対訳表に無い専門語は翻訳せず一覧で報告するMCPサーバーを作って。
出力形式: 実装コード・対訳表の書式・未登録語の報告形式を出して。
067アンケート結果を分類する
前提: アンケートの自由記述が大量にあり、読むだけで終わってしまう。
指示: 自由記述を渡すと、あらかじめ決めた分類に振り分けて件数と代表的な原文を返すMCPサーバーを作って。どの分類にも当てはまらないものは「その他」に入れ、全件を必ずどこかに割り当てて。
出力形式: 実装コード・分類定義の書式・出力例を出して。
068作業手順を実行順に並べ替える
前提: 手順書に書いてある順番と、実際にやるべき順番がずれていることがある。
指示: 手順の一覧と依存関係を渡すと、実行可能な順序に並べ替えて返すMCPサーバーを作って。循環している依存関係は解こうとせず、該当箇所を明示して差し戻して。
出力形式: 実装コード・依存関係の書式・循環検出時のレスポンス例を出して。
069月次の締め作業をチェックリスト化する
前提: 月次の締め作業の手順が長く、その月に不要な項目も混ざっている。
指示: 対象月と条件（決算月か・イベントがあったか等）を渡すと、その月に必要な項目だけのチェックリストを返すMCPサーバーを作って。除外した項目とその理由も併記して。
出力形式: 実装コード・手順定義の書式・出力例を出して。

チームで安全に運用する

070個人ごとの接続URLを発行する
前提: 同じURLを全員に配ると、退会した人の分だけ止めることができない。
指示: 管理者が個人ごとの接続トークンを発行・失効できるMCPサーバーを作って。トークンは推測できない長さにし、保存はハッシュ化して。失効したトークンでの接続は即座に拒否して。
出力形式: 実装コード・発行と失効の手順・失効後のレスポンス例を出して。
071利用ログを追記専用で残す
前提: 誰がいつ何を使ったかの記録が必要だが、改ざんできる形では意味がない。
指示: 利用ログを追記のみのファイルに書くMCPサーバーを作って。1行1件のJSON形式にし、書き込み失敗時はリクエスト自体を失敗させて記録漏れを起こさないで。
出力形式: 実装コード・ログ1行の書式・ローテーションの考え方を出して。
0721人あたりの呼び出し回数を制限する
前提: 配信サーバーが従量課金の基盤に乗る予定で、使われ方によっては費用が読めない。
指示: トークンごとに時間あたりの呼び出し回数上限を設けるMCPサーバーを作って。上限に達したら分かりやすいメッセージで拒否し、いつ復帰するかも返して。上限値はトークンごとに変えられるようにして。
出力形式: 実装コード・上限設定の書式・拒否時のレスポンス例を出して。
073管理画面から配信を止める
前提: 配信内容に誤りが見つかったとき、修正が終わるまで一時的に止めたい。
指示: 配信全体または個別スキルを一時停止できる管理用の口を持つMCPサーバーを作って。停止中は理由と再開見込みを返し、管理用の口は別のトークンでしか叩けないようにして。
出力形式: 実装コード・管理トークンの分け方・停止中のレスポンス例を出して。
074誰が何を見られるかを一覧で出す
前提: 権限の設定が増えてきて、誰が何にアクセスできるのか全体像が見えない。
指示: 現在の権限設定を、利用者×スキルの一覧表で返す管理用の口を持つMCPサーバーを作って。設定ファイルと実際の挙動が食い違っていないかの検査も同時に行って。
出力形式: 実装コード・一覧表の形・食い違い検出時の報告形式を出して。
075本番と検証を分ける
前提: スキルを直している最中の内容が、そのまま全員に届いてしまうのが怖い。
指示: 本番用と検証用の2系統を持つMCPサーバーを作って。検証用は限られたトークンからしか接続できず、検証で問題がなければ本番へ反映する手順を用意して。
出力形式: 実装コード・系統の切り替え方法・本番反映の手順を出して。
076外部に出してはいけない内容を検知する
前提: 社外秘の内容が、配信対象のフォルダに紛れ込む可能性がある。
指示: 配信前に本文を検査し、社外秘マーカーや指定したキーワードを含むファイルは配信対象から自動で外すMCPサーバーを作って。外したファイルは管理者にだけ一覧で報告して。
出力形式: 実装コード・マーカーの決め方・報告形式を出して。
077接続元を制限する
前提: 社内からのみ使う配信サーバーなのに、URLさえ知っていれば外から叩ける状態になっている。
指示: 許可した接続元からのリクエストだけを受けるMCPサーバーを作って。許可リストは設定で変更でき、拒否したリクエストは接続元と時刻だけをログに残して。
出力形式: 実装コード・許可リストの書式・拒否時のログ1行の例を出して。
078秘密情報を環境変数だけで扱う
前提: 過去にAPIキーをリポジトリに含めてしまった経験があり、同じ事故を避けたい。
指示: 秘密情報を一切コード内に持たず環境変数からのみ読むMCPサーバーを作って。必要な環境変数が欠けている場合は起動時に明確なメッセージで停止し、値そのものはログに出さないで。
出力形式: 実装コード・必要な環境変数の一覧・起動失敗時のメッセージ例を出して。
079配信内容の差分を承認制にする
前提: 複数人でスキルを編集していて、確認なしに配信内容が変わるのを避けたい。
指示: 配信内容の変更を検知したら、承認されるまで前の内容を配り続けるMCPサーバーを作って。承認待ちの差分は管理用の口から確認でき、承認は別トークンでのみ行えるようにして。
出力形式: 実装コード・差分表示の形・承認手順を出して。
080エラーを人が読める形で返す
前提: 接続に失敗したとき、受け取る側にはエラーの理由が伝わらず問い合わせが来る。
指示: 失敗の種類ごとに、原因と次にやるべきことを日本語で返すMCPサーバーを作って。内部の詳細情報は返さず、対処に必要な情報だけに絞って。
出力形式: 実装コード・想定するエラーの種類一覧・それぞれのメッセージ文面を出して。
081設定の変更履歴を残す

# 🎁 自作MCPサーバー 発注プロンプト100選

Claude Code などに貼るだけで、自分専用のMCPサーバー（AIに手順やデータを届けるサーバー）の設計と雛形づくりが進む発注文を100本まとめました。ファイルを配るのをやめて、URL1本で配れる状態を目指すためのものです。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 使いたい1本をコピーして、Claude Code にそのまま貼ってください。〈 〉の部分だけ自分の状況に置き換えれば動きます。

## スキルを配る

### 1. 手元のスキル1本を配信サーバーにする

いま使っているSKILL.mdを、他人に渡せる形に切り替える最初の1本。

```text
前提: 手元の .claude/skills/ にあるSKILL.mdを1本、他の人にも使ってもらいたい。ファイルは渡したくない。
指示: そのSKILL.mdの本文をそのまま返すリモートHTTPのMCPサーバーを作って。読み込む対象はファイルパスで指定できるようにし、サーバー起動時ではなく呼び出しのたびにファイルを読み直す実装にして。
出力形式: 起動手順・接続用URL・claude mcp add のコマンド例を最後にまとめて出して。コードは1ファイルに収め、依存パッケージは最小限にして。
```

### 2. 複数スキルをまとめて配信する

フォルダごと配信し、増やしたら自動で反映される形にする。

```text
前提: skills/ フォルダの下にスキルが複数あり、今後も増やしていく予定。増えるたびにサーバーを直したくない。
指示: 指定フォルダ配下のSKILL.mdを起動時ではなく毎回スキャンして、一覧と本文を返すMCPサーバーを作って。スキル名はフォルダ名から取り、frontmatterのdescriptionを一覧の説明に使って。
出力形式: フォルダ構成の想定図・実装コード・動作確認の手順（スキルを1つ足して反映されるか試す方法）を順に出して。
```

### 3. GitHubリポジトリを配信元にする

```text
前提: スキルの正本をGitHubの公開リポジトリで管理していて、pushしたら配信内容も切り替わってほしい。
指示: 指定リポジトリのraw URLからSKILL.mdを取得して返すMCPサーバーを作って。取得結果は短時間だけキャッシュし、キャッシュ時間は環境変数で変えられるようにして。取得失敗時は前回の内容を返し、その旨をログに残して。
出力形式: 実装コードと、キャッシュ時間の目安（何分が妥当か）の判断材料を3行で添えて。
```
