①ブランチ・コミット規約

001新しい機能ブランチを切る前に、変更内容から適切なブランチ名（feature/fix/ch…
前提: 複数のAIエージェントに並行して機能実装を任せる開発チーム向け。
指示: 新しい機能ブランチを切る前に、変更内容から適切なブランチ名（feature/fix/chore等のプレフィックス＋内容を表す短い英語）を提案して。既存ブランチと名前が衝突しないかも確認して。
出力形式: ブランチ名の候補を3つ、理由つきで箇条書きにして。衝突がある場合はその旨を先頭に警告として書いて。
002直近の変更差分を確認し、Conventional Commits形式（feat/fix/…
前提: エージェントが自律的にコミットする頻度が増え、コミット履歴が読みにくくなっているプロジェクト。
指示: 直近の変更差分を確認し、Conventional Commits形式（feat/fix/refactor等）でコミットメッセージを作成して。1コミットに複数の意図が混ざっていたら分割を提案して。
出力形式: コミットメッセージ本文と、分割が必要な場合はその理由を2〜3行で添えて。
003今回の変更を、後続の変更が依存できる最小単位に分割する案を考えて。
前提: 依存関係のあるPRを連続して出したいが、レビュー待ちで後続作業がブロックされがちなチーム。
指示: 今回の変更を、後続の変更が依存できる最小単位に分割する案を考えて。それぞれの単位が独立してレビューできるかも確認して。
出力形式: 分割案を番号付きリストで、各項目に「変更範囲」「依存元」「レビュー観点」を1行ずつ添えて。
004今から着手する作業が、他の進行中のブランチと衝突しそうなファイルを触っていないか確認して…
前提: 複数人・複数エージェントが同時に同じリポジトリで作業する状況。
指示: 今から着手する作業が、他の進行中のブランチと衝突しそうなファイルを触っていないか確認して。触っている場合は着手前に確認すべき相手を教えて。
出力形式: 「衝突リスク: 高/中/低」を先頭に書き、根拠となるファイルパスを箇条書きで示して。
005直接プッシュしそうな変更を検知したら、代わりに新しいブランチを作ってそこにコミットし直す…
前提: mainブランチへの直接プッシュを禁止し、PR経由に統一したいチーム。
指示: 直接プッシュしそうな変更を検知したら、代わりに新しいブランチを作ってそこにコミットし直す手順を提示して。
出力形式: 実行するコマンド列を番号付きで示し、最後にPR作成用のタイトル案を1つ添えて。
006統合対象のブランチ一覧をもとに、マージ順序（依存関係が壊れない順番）を提案して。
前提: リリース前に、複数のfeatureブランチをまとめて統合する必要があるプロジェクト。
指示: 統合対象のブランチ一覧をもとに、マージ順序（依存関係が壊れない順番）を提案して。
出力形式: マージ順のリストと、各ステップで想定されるコンフリクトの有無を一言で添えて。
007今回のコミットメッセージの末尾に、使用したモデル名と生成範囲（全体/一部）を注記する形式…
前提: コミットメッセージに「AIが生成した」ことを明示したいチームのポリシー。
指示: 今回のコミットメッセージの末尾に、使用したモデル名と生成範囲（全体/一部）を注記する形式で追記して。
出力形式: 通常のコミットメッセージ本文＋末尾に `[AI-assisted: <モデル名>, 範囲: <全体/一部>]` の1行を追加して。
008全ブランチの最終更新日とマージ状況を確認し、削除候補・要確認・生存中の3分類に振り分けて…
前提: 長期間放置されたブランチが増え、どれが生きているか分からなくなっているリポジトリ。
指示: 全ブランチの最終更新日とマージ状況を確認し、削除候補・要確認・生存中の3分類に振り分けて。
出力形式: 3つの見出し（削除候補／要確認／生存中）ごとにブランチ名を箇条書きにして。
009作業開始前に、mainブランチが最新であることを確認し、古ければ最新化してから作業ブラン…
前提: 複数のエージェントが同時にmainブランチをベースに作業を始めるタイミング。
指示: 作業開始前に、mainブランチが最新であることを確認し、古ければ最新化してから作業ブランチを切る手順を実行して。
出力形式: 実行したコマンドと、その結果（最新だったか更新が必要だったか）を2行で報告して。
010今回の変更差分から、PRタイトル（変更内容が一目で分かる形）と説明文（背景・変更点・確認…
前提: PRのタイトルと説明文が空欄・簡素すぎて後から追いにくいプロジェクト。
指示: 今回の変更差分から、PRタイトル（変更内容が一目で分かる形）と説明文（背景・変更点・確認方法）を作成して。
出力形式: タイトル1行＋説明文を「背景」「変更点」「確認方法」の3見出しで構成して。
011関連する複数リポジトリのコミットに、共通の識別子（作業チケット番号等）をコミットメッセー…
前提: 複数のリポジトリにまたがる変更を1つの意図として管理したいプロジェクト。
指示: 関連する複数リポジトリのコミットに、共通の識別子（作業チケット番号等）をコミットメッセージに含める形で統一して。
出力形式: 各リポジトリごとのコミットメッセージ案を、リポジトリ名を見出しにして列挙して。
012セマンティックバージョニング（major.minor.patch）に沿ったタグ名を、今回…
前提: Gitタグでのリリース管理を始めたいが運用ルールが未整備なチーム。
指示: セマンティックバージョニング（major.minor.patch）に沿ったタグ名を、今回の変更内容（破壊的変更/機能追加/バグ修正）から提案して。
出力形式: 提案タグ名と、その根拠となる変更分類を1行で添えて。

②PRレビュー観点

013このPRの差分を確認し、意図しないファイル変更・デバッグ用コードの残存・機密情報の混入が…
前提: AIエージェントが開いたPRの一次チェックを人間の手間なく済ませたいチーム。
指示: このPRの差分を確認し、意図しないファイル変更・デバッグ用コードの残存・機密情報の混入が無いかをチェックして。
出力形式: 「問題なし」または「要確認」の判定を先頭に書き、要確認の場合は該当ファイル・行番号を箇条書きで示して。
014未レビューのPR一覧から、変更の影響範囲（大/中/小）とレビューの緊急度を判定して優先順…
前提: 複数のPRが同時に積み上がり、優先度が分かりにくくなっているレビューキュー。
指示: 未レビューのPR一覧から、変更の影響範囲（大/中/小）とレビューの緊急度を判定して優先順位を付けて。
出力形式: 表形式（PR名／影響範囲／緊急度／理由）でまとめて。
015依存関係にあるPR群を確認し、どの順番でレビュー・マージすべきかを、依存が壊れないように…
前提: スタックPR（依存関係のある複数PR）を扱う機会が増えたチーム。
指示: 依存関係にあるPR群を確認し、どの順番でレビュー・マージすべきかを、依存が壊れないように整理して。
出力形式: マージ順のリストと、各PRが依存する直前のPRを矢印でつないで表示して。
016このPRの差分から、レビュアーが最初に確認すべき3つのポイントを抽出して。
前提: PRの説明文だけでは変更意図が読み取れないことが多いチーム。
指示: このPRの差分から、レビュアーが最初に確認すべき3つのポイントを抽出して。
出力形式: 「注目ポイント」として3項目、それぞれ「なぜ重要か」を1文で添えて。
017このPRの本体コードの変更に対して、対応するテストが追加・修正されているか確認して。
前提: テストコードが変更に追随しているか毎回確認するのが手間なプロジェクト。
指示: このPRの本体コードの変更に対して、対応するテストが追加・修正されているか確認して。不足していれば具体的にどのケースが足りないか指摘して。
出力形式: 「テストカバレッジ: 十分/不十分」を先頭に、不十分な場合は不足ケースを箇条書きで示して。
018このPRの差分に、既存の呼び出し側に影響する可能性のある変更が含まれていないか確認して。
前提: 破壊的変更（Breaking Change）が意図せず紛れ込むことがあるAPIプロジェクト。
指示: このPRの差分に、既存の呼び出し側に影響する可能性のある変更が含まれていないか確認して。
出力形式: 「破壊的変更の可能性: あり/なし」を先頭に、ありの場合は影響を受けそうな箇所を挙げて。
019このPRのコードスタイル上の問題（命名規則・フォーマット・重複コード）を機械的にチェック…
前提: コードスタイルの指摘に毎回時間を取られているレビュー体制。
指示: このPRのコードスタイル上の問題（命名規則・フォーマット・重複コード）を機械的にチェックし、ロジック面の指摘とは分けて報告して。
出力形式: 「スタイル指摘」と「ロジック指摘」の2見出しに分けて箇条書きにして。
020このPRが「ドキュメント修正のみ」「軽微な文言修正のみ」等、自動承認して良い基準に該当す…
前提: 大量のPRを効率よく捌くため、自動承認してよい変更とそうでない変更を切り分けたいチーム。
指示: このPRが「ドキュメント修正のみ」「軽微な文言修正のみ」等、自動承認して良い基準に該当するか判定して。
出力形式: 「自動承認可否」を先頭に判定理由を1〜2行で添えて。
021このPRにセキュリティへ影響する変更（認証処理・権限チェック・外部API呼び出し）が含ま…
前提: セキュリティに関わる変更（認証・権限・外部通信）を見落とさずレビューしたいチーム。
指示: このPRにセキュリティへ影響する変更（認証処理・権限チェック・外部API呼び出し）が含まれていないか確認して。
出力形式: 該当箇所があれば「セキュリティ関連の変更あり」として一覧化し、無ければ「該当なし」とだけ書いて。
022このPRの変更内容が、他の進行中のPRと機能的に重複していないか確認して。
前提: 複数エージェントが並行して同じ機能に手を入れており、重複実装が起きやすい状況。
指示: このPRの変更内容が、他の進行中のPRと機能的に重複していないか確認して。
出力形式: 重複の疑いがあれば対象PR名と重複箇所を示し、無ければ「重複なし」と書いて。
023過去のレビューコメント一覧と現在の差分を突き合わせ、対応済み・未対応を仕分けして。
前提: レビューコメントへの対応漏れが頻発しているプロジェクト。
指示: 過去のレビューコメント一覧と現在の差分を突き合わせ、対応済み・未対応を仕分けして。
出力形式: 「対応済み」「未対応」の2見出しに分け、未対応はコメント内容を引用して示して。
024このPRに、既存処理の実行速度を悪化させる可能性がある変更が含まれていないか確認して。
前提: パフォーマンスに影響しうる変更（ループ処理・DBクエリ追加等）を見落としたくないチーム。
指示: このPRに、既存処理の実行速度を悪化させる可能性がある変更が含まれていないか確認して。
出力形式: 懸念箇所があれば理由とともに列挙し、無ければ「パフォーマンス上の懸念なし」と書いて。

③コンフリクト解決

025発生しているコンフリクトの内容を確認し、両者の変更意図を壊さずに統合する修正案を提示して…
前提: 複数のAIエージェントが同じファイルを並行編集し、マージコンフリクトが頻発するプロジェクト。
指示: 発生しているコンフリクトの内容を確認し、両者の変更意図を壊さずに統合する修正案を提示して。
出力形式: 統合後のコード全文と、判断の根拠を2〜3行で添えて。
026自動解決できなかったコンフリクト箇所を一覧化し、それぞれなぜ自動判断できなかったかを推測…
前提: 自動マージを試みて失敗した箇所を、人間が最終確認する前段階の整理をしたいチーム。
指示: 自動解決できなかったコンフリクト箇所を一覧化し、それぞれなぜ自動判断できなかったかを推測して。
出力形式: 表形式（ファイル／行範囲／自動解決できなかった理由）でまとめて。
027コンフリクトの原因が依存パッケージの更新にあるかを確認し、そうであればバージョン整合の取…
前提: 依存パッケージの更新が原因で複数箇所にコンフリクトが波及したプロジェクト。
指示: コンフリクトの原因が依存パッケージの更新にあるかを確認し、そうであればバージョン整合の取り方を提案して。
出力形式: 原因の特定結果を先頭に書き、対応手順を番号付きリストで示して。
028マージ前に、コンフリクトが起きそうなファイルを事前に洗い出し、影響が大きい順に並べて。
前提: 長期間分岐していたブランチをmainに統合する際、大量のコンフリクトが予想される状況。
指示: マージ前に、コンフリクトが起きそうなファイルを事前に洗い出し、影響が大きい順に並べて。
出力形式: 「高リスク」「中リスク」「低リスク」の3段階に分けてファイルパスを列挙して。
029差分に `<<<<<<<` 等のコンフリクトマーカーが残っていないか確認して。
前提: CIが落ちる原因がコンフリクトの残骸（マーカー消し忘れ等）であることが多いプロジェクト。
指示: 差分に `<<<<<<<` 等のコンフリクトマーカーが残っていないか確認して。
出力形式: 「マーカー残存: あり/なし」を先頭に、ありの場合は該当ファイルと行番号を示して。
030両方のリファクタリング意図を汲み取り、どちらの設計思想を採用すべきか、または両立できる第…
前提: 同じ関数を複数エージェントが別方向にリファクタリングしてコンフリクトした状況。
指示: 両方のリファクタリング意図を汲み取り、どちらの設計思想を採用すべきか、または両立できる第三の実装があるか検討して。
出力形式: 「採用案」を1つ提示し、不採用にした案とその理由も併記して。
031今回のコンフリクトをどう解決したか、判断の理由とともに記録を残して。
前提: コンフリクト解決の判断を後から追えるようにしたいチーム。
指示: 今回のコンフリクトをどう解決したか、判断の理由とともに記録を残して。
出力形式: 「解決方針」「採用した変更」「見送った変更とその理由」の3項目で1つのメモにまとめて。
032今回のコンフリクトが機械的に解決可能か、それとも設計判断が必要かを見極めて。
前提: テキストベースの自動マージでは対応できない、設計判断が必要なコンフリクトが多いプロジェクト。
指示: 今回のコンフリクトが機械的に解決可能か、それとも設計判断が必要かを見極めて。
出力形式: 「機械的解決可能」または「人間の設計判断が必要」を先頭に明記し、後者の場合は判断すべき論点を箇条書きにして。
033コンフリクトしているファイル群の依存関係を整理し、どのファイルから解決すべきかの着手順を…
前提: 複数ファイルにまたがる大規模な変更同士がコンフリクトした状況。
指示: コンフリクトしているファイル群の依存関係を整理し、どのファイルから解決すべきかの着手順を提案して。
出力形式: 着手順のリストと、各ファイルの他ファイルへの影響度を一言で添えて。
034コンフリクトを解決したら、関連するテストを特定して実行し、結果を報告して。
前提: コンフリクト解決後にテストが通るかを都度確認する手間を減らしたいチーム。
指示: コンフリクトを解決したら、関連するテストを特定して実行し、結果を報告して。
出力形式: 「実行したテスト」「結果（成功/失敗）」「失敗時の原因推測」の3項目で報告して。
035今回の状況（ブランチの共有状況・履歴の見やすさへの要求）から、リベースかマージのどちらが…
前提: リベースとマージのどちらでコンフリクトを解決すべきか毎回迷うチーム。
指示: 今回の状況（ブランチの共有状況・履歴の見やすさへの要求）から、リベースかマージのどちらが適切かを判断して。
出力形式: 「推奨: リベース/マージ」を先頭に、判断理由を2〜3行で添えて。
036直近のコンフリクト履歴を振り返り、同じファイル・同じ関数で繰り返しコンフリクトが起きてい…
前提: コンフリクト頻発の根本原因（設計の疎結合度の低さ等）を把握したいチーム。
指示: 直近のコンフリクト履歴を振り返り、同じファイル・同じ関数で繰り返しコンフリクトが起きていないか傾向を分析して。
出力形式: 「頻発箇所トップ3」を挙げ、それぞれ根本原因の推測を1行で添えて。

④監査証跡・メタデータ管理

037今回のコミットに含まれる変更のうち、AIが生成した割合と箇所を整理して。
前提: AIが書いたコードと人間が書いたコードを後から区別できるようにしたいチーム。
指示: 今回のコミットに含まれる変更のうち、AIが生成した割合と箇所を整理して。
出力形式: 「AI生成箇所」「人間による箇所」を分け、それぞれのファイル・行範囲を示して。
038今回のコード生成に使った指示内容を、要約した形でコミットメッセージまたは別ファイルに記録…
前提: 使用したプロンプトを後から振り返れるようにしたいプロジェクト。
指示: 今回のコード生成に使った指示内容を、要約した形でコミットメッセージまたは別ファイルに記録して。
出力形式: 「使用した指示の要約」を3行以内で書き、生成日時とモデル名を併記して。
039指定した範囲のコードについて、生成に使ったモデル・日時・元になった指示の記録が残っている…
前提: 監査対応のため、特定のコード変更がいつ・どのモデルで生成されたか追跡する必要があるプロジェクト。
指示: 指定した範囲のコードについて、生成に使ったモデル・日時・元になった指示の記録が残っているか確認して。
出力形式: 「記録あり」「記録なし」を先頭に明記し、記録がある場合はその内容を引用して。
040AI生成コードのうち、認証・決済・外部通信に関わる「高リスク領域」を触っている箇所を特定…
前提: エージェントが自律的に大量のコードを書くため、レビュー優先度をリスクベースで決めたいチーム。
指示: AI生成コードのうち、認証・決済・外部通信に関わる「高リスク領域」を触っている箇所を特定して。
出力形式: 「高リスク領域の変更」として該当ファイルを一覧化し、理由を1行ずつ添えて。
041今回の変更で参照したファイル・ドキュメントの一覧を、生成時のコンテキストとして記録して。
前提: コンテキストウィンドウの設定（読み込んだファイル範囲等）を記録に残したいプロジェクト。
指示: 今回の変更で参照したファイル・ドキュメントの一覧を、生成時のコンテキストとして記録して。
出力形式: 「参照したファイル」を箇条書きで列挙し、末尾に参照した合計ファイル数を書いて。
042直近のAI生成コミットを集計し、後から修正が必要になった割合（手直し率）を確認して。
前提: AI生成コードの品質を定期的に振り返りたいチーム。
指示: 直近のAI生成コミットを集計し、後から修正が必要になった割合（手直し率）を確認して。
出力形式: 「対象コミット数」「うち手直しが発生した件数」「手直し率」の3項目で報告して。
043リポジトリ内のコミット履歴から、使用ツール・モデル別の生成コード量を集計して。
前提: どのモデル・どのツールでコードが生成されたかをプロジェクト全体で可視化したいチーム。
指示: リポジトリ内のコミット履歴から、使用ツール・モデル別の生成コード量を集計して。
出力形式: ツール・モデルごとの件数を表形式でまとめ、最も多い組み合わせを先頭に明記して。
044今回のコミットに、モデル名・プロンプト概要・生成範囲の記録が漏れなく含まれているか確認し…
前提: 監査証跡の記録漏れを防ぎたいプロジェクト。
指示: 今回のコミットに、モデル名・プロンプト概要・生成範囲の記録が漏れなく含まれているか確認して。
出力形式: 「記録完備」または「記録不足」を先頭に書き、不足がある場合は補うべき項目を箇条書きで示して。
045指定した不具合発生箇所のコードについて、生成時の記録（モデル・プロンプト・日時）を遡って…
前提: 過去にさかのぼって、ある不具合の原因コードがAI生成かどうかを調べたいチーム。
指示: 指定した不具合発生箇所のコードについて、生成時の記録（モデル・プロンプト・日時）を遡って確認して。
出力形式: 「発見した記録」の内容を時系列で示し、記録が無い場合はその旨を明記して。
046今回使用した指示文のうち、意図通りの結果が得られたものとそうでなかったものを振り返って。
前提: プロンプトの品質改善のため、良かった指示・悪かった指示を蓄積したいチーム。
指示: 今回使用した指示文のうち、意図通りの結果が得られたものとそうでなかったものを振り返って。
出力形式: 「うまくいった指示」「改善が必要な指示」の2見出しに分け、理由を1〜2行で添えて。
047今回の生成コードが、既存の外部コードを参考にした可能性がある箇所を洗い出して。
前提: 生成コードのライセンス・著作権リスクを記録として残しておきたいプロジェクト。
指示: 今回の生成コードが、既存の外部コードを参考にした可能性がある箇所を洗い出して。
出力形式: 該当箇所があれば「要確認」として一覧化し、無ければ「該当なし」と書いて。
048今回のエージェントの作業内容（実行したコマンド・生成したファイル・判断した分岐点）を要約…
前提: エージェントの自律作業ログを、後から人間が読める形で要約したいチーム。
指示: 今回のエージェントの作業内容（実行したコマンド・生成したファイル・判断した分岐点）を要約して。
出力形式: 「実行内容の要約」を時系列の箇条書きで、5項目以内にまとめて。

指示: 今回のデプロイに対するロールバック手順を、事前に確認できる形で整理して。
出力形式: ロールバック手順を番号付きリストで、想定所要時間も添えて。
054各環境の設定ファイルを比較し、意図しない差分が無いか確認して。

指示: 各環境の設定ファイルを比較し、意図しない差分が無いか確認して。

055現在のCIパイプラインのうち、時間がかかっているステップを特定し、並列化や不要な処理の削…

056現在の設定を確認し、チーム共有の環境シークレットに移すべき項目を洗い出して。

指示: 現在の設定を確認し、チーム共有の環境シークレットに移すべき項目を洗い出して。

057現在のPRに紐づくすべてのチェック（ビルド・テスト・デプロイ）の状態を確認して。

指示: 現在のPRに紐づくすべてのチェック（ビルド・テスト・デプロイ）の状態を確認して。
出力形式: チェック名ごとに「成功/失敗/実行中」を一覧表示して。
058現在の依存関係一覧から、既知の脆弱性が報告されているパッケージが無いか確認して。

指示: 現在の依存関係一覧から、既知の脆弱性が報告されているパッケージが無いか確認して。

前提: デプロイの成功率を定期的にモニタリングしたいチーム。

# 🎁 AIエージェント大量PR時代の運用指示文60選

AIエージェントが大量にPRを開く時代の運用を、ブランチ規約・レビュー・コンフリクト解決・監査証跡・CI連携の5カテゴリで指示文にまとめました。GitHub・Origin・Claude Codeなど、使っているツールを問わず貼るだけで使えます。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: そのままAIエージェントへの指示として貼り付けてください。プロジェクト名やファイルパスなど、具体的な情報に置き換えるとより精度が上がります。

## ①ブランチ・コミット規約

### 1.

```text
前提: 複数のAIエージェントに並行して機能実装を任せる開発チーム向け。
指示: 新しい機能ブランチを切る前に、変更内容から適切なブランチ名（feature/fix/chore等のプレフィックス＋内容を表す短い英語）を提案して。既存ブランチと名前が衝突しないかも確認して。
出力形式: ブランチ名の候補を3つ、理由つきで箇条書きにして。衝突がある場合はその旨を先頭に警告として書いて。
```

### 2.

```text
前提: エージェントが自律的にコミットする頻度が増え、コミット履歴が読みにくくなっているプロジェクト。
指示: 直近の変更差分を確認し、Conventional Commits形式（feat/fix/refactor等）でコミットメッセージを作成して。1コミットに複数の意図が混ざっていたら分割を提案して。
出力形式: コミットメッセージ本文と、分割が必要な場合はその理由を2〜3行で添えて。
```

### 3.

```text
前提: 依存関係のあるPRを連続して出したいが、レビュー待ちで後続作業がブロックされがちなチーム。
指示: 今回の変更を、後続の変更が依存できる最小単位に分割する案を考えて。それぞれの単位が独立してレビューできるかも確認して。
出力形式: 分割案を番号付きリストで、各項目に「変更範囲」「依存元」「レビュー観点」を1行ずつ添えて。
```

### 4.

```text
前提: 複数人・複数エージェントが同時に同じリポジトリで作業する状況。
指示: 今から着手する作業が、他の進行中のブランチと衝突しそうなファイルを触っていないか確認して。触っている場合は着手前に確認すべき相手を教えて。
出力形式: 「衝突リスク: 高/中/低」を先頭に書き、根拠となるファイルパスを箇条書きで示して。
```

### 5.

```text
前提: mainブランチへの直接プッシュを禁止し、PR経由に統一したいチーム。
指示: 直接プッシュしそうな変更を検知したら、代わりに新しいブランチを作ってそこにコミットし直す手順を提示して。
出力形式: 実行するコマンド列を番号付きで示し、最後にPR作成用のタイトル案を1つ添えて。
```

### 6.

```text
前提: リリース前に、複数のfeatureブランチをまとめて統合する必要があるプロジェクト。
指示: 統合対象のブランチ一覧をもとに、マージ順序（依存関係が壊れない順番）を提案して。
出力形式: マージ順のリストと、各ステップで想定されるコンフリクトの有無を一言で添えて。
```

### 7.

```text
前提: コミットメッセージに「AIが生成した」ことを明示したいチームのポリシー。
指示: 今回のコミットメッセージの末尾に、使用したモデル名と生成範囲（全体/一部）を注記する形式で追記して。
出力形式: 通常のコミットメッセージ本文＋末尾に `[AI-assisted: <モデル名>, 範囲: <全体/一部>]` の1行を追加して。
```

### 8.

```text
前提: 長期間放置されたブランチが増え、どれが生きているか分からなくなっているリポジトリ。
指示: 全ブランチの最終更新日とマージ状況を確認し、削除候補・要確認・生存中の3分類に振り分けて。
出力形式: 3つの見出し（削除候補／要確認／生存中）ごとにブランチ名を箇条書きにして。
```

### 9.

```text
前提: 複数のエージェントが同時にmainブランチをベースに作業を始めるタイミング。
指示: 作業開始前に、mainブランチが最新であることを確認し、古ければ最新化してから作業ブランチを切る手順を実行して。
出力形式: 実行したコマンドと、その結果（最新だったか更新が必要だったか）を2行で報告して。
```

### 10.

```text
前提: PRのタイトルと説明文が空欄・簡素すぎて後から追いにくいプロジェクト。
指示: 今回の変更差分から、PRタイトル（変更内容が一目で分かる形）と説明文（背景・変更点・確認方法）を作成して。
出力形式: タイトル1行＋説明文を「背景」「変更点」「確認方法」の3見出しで構成して。
```

### 11.

```text
前提: 複数のリポジトリにまたがる変更を1つの意図として管理したいプロジェクト。
指示: 関連する複数リポジトリのコミットに、共通の識別子（作業チケット番号等）をコミットメッセージに含める形で統一して。
出力形式: 各リポジトリごとのコミットメッセージ案を、リポジトリ名を見出しにして列挙して。
```

### 12.

```text
前提: Gitタグでのリリース管理を始めたいが運用ルールが未整備なチーム。
指示: セマンティックバージョニング（major.minor.patch）に沿ったタグ名を、今回の変更内容（破壊的変更/機能追加/バグ修正）から提案して。
出力形式: 提案タグ名と、その根拠となる変更分類を1行で添えて。
```

## ②PRレビュー観点

### 13.

```text
前提: AIエージェントが開いたPRの一次チェックを人間の手間なく済ませたいチーム。
指示: このPRの差分を確認し、意図しないファイル変更・デバッグ用コードの残存・機密情報の混入が無いかをチェックして。
出力形式: 「問題なし」または「要確認」の判定を先頭に書き、要確認の場合は該当ファイル・行番号を箇条書きで示して。
```

### 14.

```text
前提: 複数のPRが同時に積み上がり、優先度が分かりにくくなっているレビューキュー。
指示: 未レビューのPR一覧から、変更の影響範囲（大/中/小）とレビューの緊急度を判定して優先順位を付けて。
出力形式: 表形式（PR名／影響範囲／緊急度／理由）でまとめて。
```

### 15.

```text
前提: スタックPR（依存関係のある複数PR）を扱う機会が増えたチーム。
指示: 依存関係にあるPR群を確認し、どの順番でレビュー・マージすべきかを、依存が壊れないように整理して。
出力形式: マージ順のリストと、各PRが依存する直前のPRを矢印でつないで表示して。
```

### 16.

```text
前提: PRの説明文だけでは変更意図が読み取れないことが多いチーム。
指示: このPRの差分から、レビュアーが最初に確認すべき3つのポイントを抽出して。
出力形式: 「注目ポイント」として3項目、それぞれ「なぜ重要か」を1文で添えて。
```

### 17.

```text
前提: テストコードが変更に追随しているか毎回確認するのが手間なプロジェクト。
指示: このPRの本体コードの変更に対して、対応するテストが追加・修正されているか確認して。不足していれば具体的にどのケースが足りないか指摘して。
出力形式: 「テストカバレッジ: 十分/不十分」を先頭に、不十分な場合は不足ケースを箇条書きで示して。
```

### 18.

```text
前提: 破壊的変更（Breaking Change）が意図せず紛れ込むことがあるAPIプロジェクト。
指示: このPRの差分に、既存の呼び出し側に影響する可能性のある変更が含まれていないか確認して。
出力形式: 「破壊的変更の可能性: あり/なし」を先頭に、ありの場合は影響を受けそうな箇所を挙げて。
```

### 19.

```text
前提: コードスタイルの指摘に毎回時間を取られているレビュー体制。
指示: このPRのコードスタイル上の問題（命名規則・フォーマット・重複コード）を機械的にチェックし、ロジック面の指摘とは分けて報告して。
出力形式: 「スタイル指摘」と「ロジック指摘」の2見出しに分けて箇条書きにして。
```

### 20.

```text
前提: 大量のPRを効率よく捌くため、自動承認してよい変更とそうでない変更を切り分けたいチーム。
指示: このPRが「ドキュメント修正のみ」「軽微な文言修正のみ」等、自動承認して良い基準に該当するか判定して。
出力形式: 「自動承認可否」を先頭に判定理由を1〜2行で添えて。
```

### 21.

```text
前提: セキュリティに関わる変更（認証・権限・外部通信）を見落とさずレビューしたいチーム。
指示: このPRにセキュリティへ影響する変更（認証処理・権限チェック・外部API呼び出し）が含まれていないか確認して。
出力形式: 該当箇所があれば「セキュリティ関連の変更あり」として一覧化し、無ければ「該当なし」とだけ書いて。
```

### 22.

```text
前提: 複数エージェントが並行して同じ機能に手を入れており、重複実装が起きやすい状況。
指示: このPRの変更内容が、他の進行中のPRと機能的に重複していないか確認して。
出力形式: 重複の疑いがあれば対象PR名と重複箇所を示し、無ければ「重複なし」と書いて。
```

### 23.

```text
前提: レビューコメントへの対応漏れが頻発しているプロジェクト。
指示: 過去のレビューコメント一覧と現在の差分を突き合わせ、対応済み・未対応を仕分けして。
出力形式: 「対応済み」「未対応」の2見出しに分け、未対応はコメント内容を引用して示して。
```

### 24.

```text
前提: パフォーマンスに影響しうる変更（ループ処理・DBクエリ追加等）を見落としたくないチーム。
指示: このPRに、既存処理の実行速度を悪化させる可能性がある変更が含まれていないか確認して。
出力形式: 懸念箇所があれば理由とともに列挙し、無ければ「パフォーマンス上の懸念なし」と書いて。
```

## ③コンフリクト解決

### 25.

```text
前提: 複数のAIエージェントが同じファイルを並行編集し、マージコンフリクトが頻発するプロジェクト。
指示: 発生しているコンフリクトの内容を確認し、両者の変更意図を壊さずに統合する修正案を提示して。
出力形式: 統合後のコード全文と、判断の根拠を2〜3行で添えて。
```

### 26.

```text
前提: 自動マージを試みて失敗した箇所を、人間が最終確認する前段階の整理をしたいチーム。
指示: 自動解決できなかったコンフリクト箇所を一覧化し、それぞれなぜ自動判断できなかったかを推測して。
出力形式: 表形式（ファイル／行範囲／自動解決できなかった理由）でまとめて。
```

### 27.

```text
前提: 依存パッケージの更新が原因で複数箇所にコンフリクトが波及したプロジェクト。
指示: コンフリクトの原因が依存パッケージの更新にあるかを確認し、そうであればバージョン整合の取り方を提案して。
出力形式: 原因の特定結果を先頭に書き、対応手順を番号付きリストで示して。
```

### 28.

```text
前提: 長期間分岐していたブランチをmainに統合する際、大量のコンフリクトが予想される状況。
指示: マージ前に、コンフリクトが起きそうなファイルを事前に洗い出し、影響が大きい順に並べて。
出力形式: 「高リスク」「中リスク」「低リスク」の3段階に分けてファイルパスを列挙して。
```

### 29.

```text
前提: CIが落ちる原因がコンフリクトの残骸（マーカー消し忘れ等）であることが多いプロジェクト。
指示: 差分に `<<<<<<<` 等のコンフリクトマーカーが残っていないか確認して。
出力形式: 「マーカー残存: あり/なし」を先頭に、ありの場合は該当ファイルと行番号を示して。
```

### 30.

```text
前提: 同じ関数を複数エージェントが別方向にリファクタリングしてコンフリクトした状況。
指示: 両方のリファクタリング意図を汲み取り、どちらの設計思想を採用すべきか、または両立できる第三の実装があるか検討して。
出力形式: 「採用案」を1つ提示し、不採用にした案とその理由も併記して。
```

### 31.

```text
前提: コンフリクト解決の判断を後から追えるようにしたいチーム。
指示: 今回のコンフリクトをどう解決したか、判断の理由とともに記録を残して。
出力形式: 「解決方針」「採用した変更」「見送った変更とその理由」の3項目で1つのメモにまとめて。
```

### 32.

```text
前提: テキストベースの自動マージでは対応できない、設計判断が必要なコンフリクトが多いプロジェクト。
指示: 今回のコンフリクトが機械的に解決可能か、それとも設計判断が必要かを見極めて。
出力形式: 「機械的解決可能」または「人間の設計判断が必要」を先頭に明記し、後者の場合は判断すべき論点を箇条書きにして。
```

### 33.

```text
前提: 複数ファイルにまたがる大規模な変更同士がコンフリクトした状況。
指示: コンフリクトしているファイル群の依存関係を整理し、どのファイルから解決すべきかの着手順を提案して。
出力形式: 着手順のリストと、各ファイルの他ファイルへの影響度を一言で添えて。
```

### 34.

```text
前提: コンフリクト解決後にテストが通るかを都度確認する手間を減らしたいチーム。
指示: コンフリクトを解決したら、関連するテストを特定して実行し、結果を報告して。
出力形式: 「実行したテスト」「結果（成功/失敗）」「失敗時の原因推測」の3項目で報告して。
```

### 35.

```text
前提: リベースとマージのどちらでコンフリクトを解決すべきか毎回迷うチーム。
指示: 今回の状況（ブランチの共有状況・履歴の見やすさへの要求）から、リベースかマージのどちらが適切かを判断して。
出力形式: 「推奨: リベース/マージ」を先頭に、判断理由を2〜3行で添えて。
```

### 36.

```text
前提: コンフリクト頻発の根本原因（設計の疎結合度の低さ等）を把握したいチーム。
指示: 直近のコンフリクト履歴を振り返り、同じファイル・同じ関数で繰り返しコンフリクトが起きていないか傾向を分析して。
出力形式: 「頻発箇所トップ3」を挙げ、それぞれ根本原因の推測を1行で添えて。
```

## ④監査証跡・メタデータ管理

### 37.

```text
前提: AIが書いたコードと人間が書いたコードを後から区別できるようにしたいチーム。
指示: 今回のコミットに含まれる変更のうち、AIが生成した割合と箇所を整理して。
出力形式: 「AI生成箇所」「人間による箇所」を分け、それぞれのファイル・行範囲を示して。
```

### 38.

```text
前提: 使用したプロンプトを後から振り返れるようにしたいプロジェクト。
指示: 今回のコード生成に使った指示内容を、要約した形でコミットメッセージまたは別ファイルに記録して。
出力形式: 「使用した指示の要約」を3行以内で書き、生成日時とモデル名を併記して。
```

### 39.

```text
前提: 監査対応のため、特定のコード変更がいつ・どのモデルで生成されたか追跡する必要があるプロジェクト。
指示: 指定した範囲のコードについて、生成に使ったモデル・日時・元になった指示の記録が残っているか確認して。
出力形式: 「記録あり」「記録なし」を先頭に明記し、記録がある場合はその内容を引用して。
```

### 40.

```text
前提: エージェントが自律的に大量のコードを書くため、レビュー優先度をリスクベースで決めたいチーム。
指示: AI生成コードのうち、認証・決済・外部通信に関わる「高リスク領域」を触っている箇所を特定して。
出力形式: 「高リスク領域の変更」として該当ファイルを一覧化し、理由を1行ずつ添えて。
```

### 41.

```text
前提: コンテキストウィンドウの設定（読み込んだファイル範囲等）を記録に残したいプロジェクト。
指示: 今回の変更で参照したファイル・ドキュメントの一覧を、生成時のコンテキストとして記録して。
出力形式: 「参照したファイル」を箇条書きで列挙し、末尾に参照した合計ファイル数を書いて。
```

### 42.

```text
前提: AI生成コードの品質を定期的に振り返りたいチーム。
指示: 直近のAI生成コミットを集計し、後から修正が必要になった割合（手直し率）を確認して。
出力形式: 「対象コミット数」「うち手直しが発生した件数」「手直し率」の3項目で報告して。
```

### 43.

```text
前提: どのモデル・どのツールでコードが生成されたかをプロジェクト全体で可視化したいチーム。
指示: リポジトリ内のコミット履歴から、使用ツール・モデル別の生成コード量を集計して。
出力形式: ツール・モデルごとの件数を表形式でまとめ、最も多い組み合わせを先頭に明記して。
```

### 44.

```text
前提: 監査証跡の記録漏れを防ぎたいプロジェクト。
指示: 今回のコミットに、モデル名・プロンプト概要・生成範囲の記録が漏れなく含まれているか確認して。
出力形式: 「記録完備」または「記録不足」を先頭に書き、不足がある場合は補うべき項目を箇条書きで示して。
```

### 45.

```text
前提: 過去にさかのぼって、ある不具合の原因コードがAI生成かどうかを調べたいチーム。
指示: 指定した不具合発生箇所のコードについて、生成時の記録（モデル・プロンプト・日時）を遡って確認して。
出力形式: 「発見した記録」の内容を時系列で示し、記録が無い場合はその旨を明記して。
```

### 46.

```text
前提: プロンプトの品質改善のため、良かった指示・悪かった指示を蓄積したいチーム。
指示: 今回使用した指示文のうち、意図通りの結果が得られたものとそうでなかったものを振り返って。
出力形式: 「うまくいった指示」「改善が必要な指示」の2見出しに分け、理由を1〜2行で添えて。
```

### 47.

```text
前提: 生成コードのライセンス・著作権リスクを記録として残しておきたいプロジェクト。
指示: 今回の生成コードが、既存の外部コードを参考にした可能性がある箇所を洗い出して。
出力形式: 該当箇所があれば「要確認」として一覧化し、無ければ「該当なし」と書いて。
```

### 48.

```text
前提: エージェントの自律作業ログを、後から人間が読める形で要約したいチーム。
指示: 今回のエージェントの作業内容（実行したコマンド・生成したファイル・判断した分岐点）を要約して。
出力形式: 「実行内容の要約」を時系列の箇条書きで、5項目以内にまとめて。
```

## ⑤CI・デプロイ連携

### 49.

```text
前提: PRごとにプレビュー環境を用意し、レビュー時に実際の画面を確認したいチーム。
指示: 今回のPRに対応するプレビューデプロイのURLを確認し、変更箇所が実際に反映されているか確かめて。
出力形式: 「プレビューURL」と「確認結果（反映済み/未反映）」を2行で報告して。
```

### 50.

```text
前提: 既存のCIワークフローを大きく変更せずに新しいチェックを追加したいプロジェクト。
指示: 現在のCI設定ファイルを確認し、既存のジョブを壊さない形で新しいチェック（Lint等）を追加する案を提示して。
出力形式: 追加する設定の差分（追加前後）と、既存ジョブへの影響有無を書いて。
```

### 51.

```text
前提: CIが失敗した際に原因特定に時間がかかっているチーム。
指示: 直近で失敗したCIログを確認し、失敗の根本原因を特定して。
出力形式: 「失敗の原因」を1〜2行で要約し、対応すべきファイル・行を示して。
```

### 52.

```text
前提: マージ前に必ず特定のチェック（テスト・型検査等）を通す運用にしたいプロジェクト。
指示: マージ条件として必須にすべきチェック項目を、現在のプロジェクト構成から提案して。
出力形式: 必須チェック項目を優先度順の箇条書きで、それぞれ理由を1行添えて。
```

### 53.

```text
前提: デプロイ後に問題が起きた際、すぐに切り戻せる体制を整えたいチーム。
指示: 今回のデプロイに対するロールバック手順を、事前に確認できる形で整理して。
出力形式: ロールバック手順を番号付きリストで、想定所要時間も添えて。
```

### 54.

```text
前提: 複数の環境（開発・検証・本番）でデプロイ設定が食い違いがちなプロジェクト。
指示: 各環境の設定ファイルを比較し、意図しない差分が無いか確認して。
出力形式: 環境間の差分を表形式（項目／開発／検証／本番）でまとめて。
```

### 55.

```text
前提: CI実行時間が長くなり開発速度が落ちているプロジェクト。
指示: 現在のCIパイプラインのうち、時間がかかっているステップを特定し、並列化や不要な処理の削減案を提案して。
出力形式: 「時間がかかっているステップ」を挙げ、それぞれの改善案を1行ずつ添えて。
```

### 56.

```text
前提: 環境変数やシークレットの管理が個人の手元に散らばっているプロジェクト。
指示: 現在の設定を確認し、チーム共有の環境シークレットに移すべき項目を洗い出して。
出力形式: 「個人シークレットのまま残すもの」「チーム共有に移すもの」の2つに分けて列挙して。
```

### 57.

```text
前提: CI/CDのステータスをPR画面から一目で把握したいチーム。
指示: 現在のPRに紐づくすべてのチェック（ビルド・テスト・デプロイ）の状態を確認して。
出力形式: チェック名ごとに「成功/失敗/実行中」を一覧表示して。
```

### 58.

```text
前提: 依存パッケージの脆弱性チェックをCIに組み込みたいプロジェクト。
指示: 現在の依存関係一覧から、既知の脆弱性が報告されているパッケージが無いか確認して。
出力形式: 該当パッケージがあれば「パッケージ名／深刻度／推奨対応」の表でまとめ、無ければ「該当なし」と書いて。
```

### 59.

```text
前提: 複数のCIプロバイダ（例: 既存のGitHub Actionsと新しいCI）を併用する移行期間にあるプロジェクト。
指示: 同じチェック内容が両方のCIで二重実行されていないか確認して。
出力形式: 「二重実行あり」の場合は対象ジョブを示し、片方の無効化を提案して。無ければ「重複なし」と書いて。
```

### 60.

```text
前提: デプロイの成功率を定期的にモニタリングしたいチーム。
指示: 直近のデプロイ履歴から、成功率と失敗時の主な原因を集計して。
出力形式: 「成功率」「主な失敗原因トップ3」の2項目でまとめて。
```

**ポイント**: 出力はそのまま採用せず、必ず人間が最終確認してから反映してください。以上、60個です。
