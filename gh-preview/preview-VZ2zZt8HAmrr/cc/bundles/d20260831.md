# 🎁 セッション節約コマンド逆引き100選

「こんな時どうする」のシチュエーション別に、Claude Codeのセッションコストを抑えるコマンド・言い回しを100個まとめました。状況→打つコマンド→何が起きるか、の3点セットでそのまま使えます。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 該当する状況になったら、そのままコマンド欄を打ち込むか、言い回し欄を参考に依頼してください。

1. 状況: 今日はじめてClaude Codeを開いた

4. 状況: 今日は単純作業しかない予定

5. 状況: 今日は複雑な設計判断が必要

   効果: 直近セッションの傾向をHTMLレポートで確認できる

   コマンド: /mcp で一覧を確認する
   効果: 使っていないサーバーをその場で無効化できる

   効果: 200行を超えていたら軽量化の目安が立つ

# 🎁 セッションコスト診断チェックシート

「なぜこのセッションは高くついたのか」を、Claude Code公式ドキュメントが挙げる原因リストに沿って自己診断できるチェックシートです。上から順にチェックするだけで、原因の見当がつきます。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: セッションのコストが高いと感じたら、■ステップ1から順に□を確認してください。YESが出た時点で、その行の→の対処を実行すれば大半のケースで解決します。

```text
【セッションコスト診断チェックシート】

■ ステップ1：セッションの長さを確認する
□ 同じ会話を半日以上つなぎっぱなしにしていないか
→ YES: 区切りごとに/clearするか、少なくとも/compactで軽量化する運用に変える

□ 会話の後半で、前半の話題とはもう関係のない作業をしていないか
→ YES: /clearしてから新しい依頼を書き直す

■ ステップ2：モデル・effortの選び方を確認する
□ 単純作業なのにOpusなど上位モデルのままになっていないか
→ YES: 次のタスク開始前に/modelでSonnetかHaikuへ切り替える
指示例: 「このタスクからはSonnetで進めて」と依頼するか、会話冒頭で/modelを実行してください。

□ 会話の途中で/modelや/effortを変更していないか
→ YES: 変更のタイミングを「会話を始める前」に統一する。途中変更はキャッシュを破棄しフル再プリフィルになる

■ ステップ3：キャッシュの状態を確認する
□ 1時間（APIキーは5分）以上放置してから再開していないか
→ YES: キャッシュミスが起きている可能性が高い。離席前は/compactしておく運用に変える

□ ENABLE_PROMPT_CACHING_1H=1を設定せずAPIキーで長時間作業していないか
→ YES: 環境変数を設定してキャッシュ保持時間を1時間に延ばす

■ ステップ4：コンテキストの中身を確認する
□ /contextを実行したことがないまま作業を続けていないか
→ YES: 一度/contextを実行し、CLAUDE.md・MCP定義がどれだけ枠を占めているか確認する

□ CLAUDE.mdが200行を超えていないか
→ YES: 使用頻度の低い手順から順にスキルへ移し、オンデマンド読み込みに変える
指示例: 「CLAUDE.mdのうち、PRレビュー手順の部分をスキルに分離して」と依頼してください。

□ 使っていないMCPサーバーが繋がったままになっていないか
→ YES: /mcpで一覧を確認し、使っていないサーバーを無効化する

■ ステップ5：コマンド出力の量を確認する
□ テスト・ビルド・ログ確認などの出力をそのままコンテキストに流し込んでいないか
→ YES: PreToolUseフックで失敗行だけに絞り込む設定を追加する（hooksフィルタリングスクリプト50選を参照）

□ 大きなファイルや長いログを都度全文読み込ませていないか
→ YES: 該当箇所だけを指定して読ませるか、事前にgrepで絞り込んでから渡す

■ ステップ6：サブエージェント・並列処理を確認する
□ ログ解析やドキュメント取得など、ノイズの多い作業を本体の会話で直接やっていないか
→ YES: サブエージェントに切り出し、model: haikuを指定して単価も抑える
指示例: 「このログ解析はサブエージェントに任せて、要点だけ報告して」と依頼してください。

□ Agent teams（並列チーム）をplanモードで大人数編成のまま動かしていないか
→ YES: 通常セッションの約7倍のトークンを使うため、チーム人数を必要最小限に絞る

□ 役目を終えたチームメイトが動き続けていないか
→ YES: 明示的に終了させる。稼働中は待機していてもトークンを消費し続ける

■ ステップ7：背景で動いているものを確認する
□ 使っていないスケジュールタスクが登録されたままになっていないか
→ YES: 不要なタスクを無効化・削除する。稼働のたびにフルコンテキストが送られる

□ 他セッションからのクロスセッションメッセージを受け取る設定のままになっていないか
→ YES: 離席中は不要ならcrossSessionInboundをholdに設定する

■ ステップ8：診断結果のまとめ
□ ここまでで2つ以上「YES」があったか
→ YES: 該当する対処を上から順に1つずつ適用し、次回セッションで/usageを見て変化を確認する

□ すべて「NO」だったか
→ YES: 既に効率的な運用ができている。/insightsで定期的に振り返り、癖の変化がないか確認する
```

**ポイント**: 一度に全部直そうとせず、まずステップ1（セッションの長さ）とステップ2（モデル選択）の2つだけ直すと、体感できる変化が一番早く出ます。
