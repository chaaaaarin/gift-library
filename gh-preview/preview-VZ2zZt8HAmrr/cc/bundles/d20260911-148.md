# 🎁 CLAUDE.md／SKILL.md 健診シート

自分の CLAUDE.md や SKILL.md を、公開 SKILL.md 138,133件の調査でいちばん多かった欠陥3タイプ（説明文が弱い／本文が肥大／整理不足）で1項目ずつ点検できます。「作ったのに呼ばれない」「毎回ブレる」の原因をその場で特定し、見つかった箇所ごとに、そのまま貼れる直し方の指示例まで用意しています。10分の点検で、以降の出力のブレとやり直しがはっきり減ります。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 点検したいファイルを1つ開く（CLAUDE.md でも、`.claude/skills/<名前>/SKILL.md` でも可）→ このシートを上から読み、□の項目を1つずつ確認 → 「当てはまる」なら → の行動を実行。指示例は、そのファイルを開いた Claude Code のセッションにそのまま貼れます。

```text
【CLAUDE.md／SKILL.md 健診シート】

点検対象: 〔ファイルのパス〕 ／ このファイルの役割を1文で: 〔　〕

■ ステップ1：説明文（冒頭）が弱くないか　※SKILL.md は description、CLAUDE.md は先頭の要約段落
□ 1文目で「何をするファイルか」が言い切れていない（"補助" "いろいろ" など曖昧語で始まる）
  → YES: 1文目を「〜するための〔対象〕。〜のとき使う」の形に書き直す
  指示例: 「このファイルの冒頭説明を、1文目＝何をするか／2文目＝どんな依頼・キーワードのとき使うか、の2文に直して。曖昧語は使わないで」
□ 「いつ使うか」が書いていない（キーワード・状況の例がない）
  → YES: 発火してほしい依頼の言い回しを3つ足す
  指示例: 「このスキルを使ってほしい依頼文の例を、実際のユーザーの言い方で3つ挙げて、説明文に『こういう依頼のとき使う』として追記して」
□ 似た役割の他ファイルと説明が見分けられない
  → YES: 違いを依頼文レベルで1行書く
  指示例: 「〔このファイル〕と〔似たファイル〕は、どんな依頼のときにどちらが選ばれるべきか、対比で1行ずつ書いて」
□ 「このスキルを使わない場面」が書いていない
  → YES: 除外条件を1つ足す
  指示例: 「このスキルを使うべきでない場面を1つ、説明文の最後に『〜のときは使わない』として足して」

■ ステップ2：本文が肥大していないか
□ 手順に関係ない前置き・背景説明・ポエムが数行以上ある
  → YES: 手順の実行に必要ない段落を削る
  指示例: 「この本文から、手順を実行するのに不要な前置き・背景・重複を削って。残すのは『やること』だけ。削った行数も教えて」
□ 同じ指示が言い方を変えて2回以上出てくる
  → YES: 1箇所に統合する
  指示例: 「同じ内容を繰り返している箇所を洗い出して、1箇所にまとめて。どこを統合したか差分で見せて」
□ 「適切に」「いい感じに」「必要に応じて」など、判定できない言葉が指示に入っている
  → YES: 機械的に判定できる条件に置き換える
  指示例: 「この中の『適切に』『いい感じに』等を、守れたか否かをその場で判定できる具体的な条件に書き換えて」
□ 1ファイルに複数の作業が詰め込まれている
  → YES: 作業ごとに分ける
  指示例: 「このファイルは何種類の作業を扱っている？ 2つ以上なら、作業ごとに別ファイルへ分ける案を出して」

■ ステップ3：整理されているか（参照・例・ルールの置き場所）
□ 「OK例」「NG例」がない、または片方しかない
  → YES: OK例とNG例を1つずつ、短く足す
  指示例: 「このルールについて、そのまま真似できるOK例と、やりがちなNG例を1つずつ、3行以内で足して」
□ 迷ったときの優先順位（どのルールを優先するか）が書いていない
  → YES: 優先順位を1行足す
  指示例: 「ルールどうしがぶつかったときに、どれを優先するかを1行で書き足して」
□ 参照すべきファイル・ドキュメントの場所が本文にバラバラに散っている
  → YES: 冒頭か末尾に「参照先」節としてまとめる
  指示例: 「本文中で参照しているファイル・URLを全部拾って、末尾に『参照先』の一覧としてまとめて。本文からは一覧を指すだけにして」
□ 見出しがなく、上から読まないと構造が分からない
  → YES: 手順・章に見出しを付ける
  指示例: 「この本文に、手順のまとまりごとの見出しを付けて。見出しだけ拾えば全体の流れが分かる状態にして」

■ 仕上げ：直した後に確認する
□ 直したファイルを読み直し、1文目だけで「何をする・いつ使う」が分かるか
□ 本文を、関係ない人が読んでも手順どおり実行できるか
□ 「いい感じに」「適切に」で検索して0件か
  → YES: 完了。今回の直し方を、次に別ファイルを作るときのテンプレとして残す
```

**ポイント**: いちばん効くのはステップ1（説明文）。SKILL.md が「必要なときに呼ばれない」原因は、9割ここにあります。CLAUDE.md の「毎回ブレる」はステップ3のOK例・NG例・優先順位で止まります。全ファイルを一度に直そうとせず、いちばん使うファイル1つから。

# 🎁 Claude Codeに頼む前の30秒テンプレ 厳選10

Claude Code に投げる前に、場面に合ったテンプレの〔　〕を埋めるだけ。考えるより先に埋めるので30秒。それだけでAIが推測する余地が減り、「惜しいけど違う」実装がぐっと減ります。実装・リファクタ・バグ修正・調査・レビュー・CLAUDE.md/SKILL.md書き・サブエージェント依頼まで、コーディングの主要場面を10個そろえました。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 使う場面のテンプレを1つ選ぶ → 〔　〕を埋める → Claude Code の依頼の冒頭に貼る → 最初の出力は“叩き台”として受け取り、差分だけ直す。

```text
【Claude Codeに頼む前の30秒テンプレ 厳選10】

─────────────────────────────
01. 小さい実装（関数・エンドポイント1つ）
期待できるメリット：仕様の往復が減り、動くものが一発で近づく。「先に不明点を聞いて」で手戻りが消える。
使う場面：関数1つ・APIエンドポイント1本くらいの新規実装を頼むとき。
前提：対象ファイル or ディレクトリを指定。入力と出力の例を書く。
テンプレ：
　目的：〔ユーザーIDを受け取り、未読通知の件数を返す〕関数／エンドポイントが欲しい。
　受け入れ条件：入力例〔　〕→出力例〔　〕。異常系（存在しないID・0件）でも落ちない。既存テストがgreenのまま。
　制約：〔言語・フレームワーク〕。新規ライブラリ追加なし。既存の〔命名規約・ディレクトリ構成〕に合わせる。
　やらないこと：関係ないファイルの整形。設定ファイルの変更。過剰な抽象化。
　確認方法：追加/変更したテストと、手元での実行手順を1行で。
　進め方：不明点を先に質問して。埋まるまでコードを書かないで。→ 叩き台 → 私が差分指示。
つまずきどころ：勝手にライブラリを足したら「標準機能だけで書き直して。追加が必要なら理由を先に説明して」。

─────────────────────────────
02. 既存コードのリファクタ
期待できるメリット：「挙動を変えずに整える」が守られる。レビューで差分が読める大きさに収まる。
使う場面：関数が長い・重複がある・見通しが悪い箇所を整理したいとき。
前提：対象範囲（ファイル／関数名）を1つに絞って指定。
テンプレ：
　目的：〔認証まわりのトークン検証〕を1関数に集約し、呼び出し側は変えない。
　受け入れ条件：外から見た挙動は不変。既存テスト全部green＋境界ケースのテストを2本追加。
　制約：変更は〔対象ファイル〕だけ。公開インターフェース（関数シグネチャ）は変えない。差分は200行以内。
　やらないこと：ついでの機能追加。命名の一括変更。フォーマッタの全体がけ。
　確認方法：変更前後でテスト結果を並べて。差分の要約を3行で。
　進め方：まず「どう分割するか」の方針だけ先に見せて。合意してから着手。
つまずきどころ：差分が膨らんだら「今回はステップ1（〔　〕）だけにして。残りは別コミット」。

─────────────────────────────
03. バグ修正
期待できるメリット：「なぜか動かない」を、症状の共有だけで原因まで切り分けられる。
使う場面：エラーが出る・期待と違う動きをする箇所を直したいとき。
前提：エラーメッセージ全文、再現手順、期待する動きと実際の動きを貼る。
テンプレ：
　目的：〔この症状〕を解消し、〔期待する動き〕にする。
　受け入れ条件：原因の説明＋最小の修正。他の挙動が変わっていない。回帰テストを1本追加。
　制約：修正は必要な範囲だけ。大規模な書き換え・ライブラリ追加・設定変更はしない。
　やらないこと：関係ない箇所の“ついで整形”。原因不明のまま当て推量で複数箇所いじる。
　確認方法：「原因／修正差分／確認方法」の3見出しで。
　進め方：まず原因の仮説を2つ挙げて。切り分け方法を先に相談。
つまずきどころ：直りきらないときは「変更を1つずつに分けて、それぞれ試せる形で出して」。

─────────────────────────────
04. 新機能（画面・機能のまとまり）
期待できるメリット：「数千の暗黙要件」を先に潰せる。着手前に認識ズレが見つかる。
使う場面：ログイン・検索・通知など、複数ファイルにまたがる機能を作るとき。
前提：関連しそうなファイル／既存の似た機能を指す。
テンプレ：
　目的：〔既存ユーザーがメール＋パスワードでサインインできる〕。
　受け入れ条件：誤入力でエラー表示／成功で〔遷移先〕へ／既存のセッション処理に乗る。E2Eの正常系1本＋異常系1本。
　制約：新規ライブラリ追加なし。既存の〔UIコンポーネント／APIクライアント〕を使う。〔設計方針の資料〕に従う。
　やらないこと：SNSログイン・パスワード再発行・2要素認証は今回対象外（別チケット）。
　確認方法：変更ファイル一覧＋動作確認手順＋対象外にした項目の明記。
　進め方：先に「作るファイルと役割」の一覧を出して。合意してから実装。
つまずきどころ：範囲が広がったら「対象外リストに〔　〕を追加。今回は〔　〕だけ」。

05. テストを足す
期待できるメリット：「何をテストすべきか」から丸投げできる。カバレッジ稼ぎの空テストを防げる。
使う場面：既存コードにテストが無い／薄いとき。リファクタの前準備にも。
前提：対象の関数／モジュールを指定。使っているテストフレームワークを書く。
テンプレ：
　目的：〔対象関数〕の振る舞いを、変更してもすぐ気づける形で固定する。
　受け入れ条件：正常系・境界値・異常系を各1つ以上。テスト名から何を確認しているか分かる。既存の書き方に合わせる。
　制約：実装コードは変えない（テスト追加のみ）。モックは最小限。外部通信はしない。
　やらないこと：意味の薄いゲッター/セッターのテスト。1つのテストで何でも確認する。
　確認方法：追加したテスト一覧＋「わざとバグを入れたら落ちるか」を1ケースで確認。
　進め方：先に「テストする観点のリスト」だけ出して。合意してからコード化。
つまずきどころ：観点が浅いときは「この関数が壊れる典型パターンを、実際のバグ想定で3つ挙げて」。

─────────────────────────────
06. コードベースを調べる（実装前の下調べ）
期待できるメリット：あてずっぽうで grep する時間が消える。改修の影響範囲が先に見える。
使う場面：知らないコードに手を入れる前に、構造と依存を把握したいとき。
前提：知りたいことを1つに絞る。エントリポイント（画面・URL・関数）を1つ指す。
テンプレ：
　目的：〔◯◯の処理〕が、どのファイルのどの関数で、どういう順に走るかを知りたい。
　受け入れ条件：呼び出しの流れ（ファイル:関数）を順に。関係する設定・環境変数も。推測は「推測」と明記。
　制約：コードは変更しない（調査のみ）。根拠にしたファイルと行を必ず示す。
　やらないこと：一般論の解説。読んでいないファイルを「たぶんこう」で語る。
　出力形式：「入口 → 処理の流れ → 出口」＋「改修するならどこを触るか」。
つまずきどころ：話が広がったら「今日知りたいのは〔　〕だけ。関係ない部分は省いて」。

07. 変更のセルフレビューを頼む
期待できるメリット：PRを出す前に、観点の抜けを自分で潰せる。レビュアーの往復が減る。
使う場面：実装が一段落して、コミット／PR前にチェックしたいとき。

　やらないこと：スタイルの好みだけの指摘を上位に置く。褒めるだけで終わる。
```
