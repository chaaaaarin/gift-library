# 🎁 手戻りを減らすCodex依頼文テンプレ10選

「いい感じにやっといて」で毎回ブレていたAIエージェントへの依頼が、タスク別のテンプレを貼るだけで毎回ほぼ同じ品質で返ってくるようになります。GPT-6 Astra（アストラ）は曖昧な指示でも routine な穴は自分で埋めますが、結果が変わる判断はこちらの書き方しだいです。切り出し・文脈・境界・レビュー条件を最初に渡しておくためのテンプレを10個そろえました。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 自分のタスクに近いものを選び、`< >` の中を自分の状況に置き換えてから、Codex（コーデックス）やClaude Code（クロードコード）の最初の1通目に貼ります。テンプレ8は `AGENTS.md`（エージェンツ・エムディー）に貼っても効きます。

```text
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
手戻りを減らすCodex依頼文テンプレ10選
━━━━━━━━━━━━━━━━━━━━━━━━━━━━

──────────────────────────────
01. バグ調査・原因特定
──────────────────────────────
期待できるメリット: 「直しといて」で見当違いの箇所をいじられる事故が減り、原因の切り分けから
  一緒に進められる。調査ログが残るので、直らなかったときの次の一手も早くなる。
使う場面: 症状は分かっているが原因が特定できていない不具合を、エージェントと一緒に追いたいとき。
前提: 再現手順か、失敗しているテスト／エラーログのどちらかを手元に用意できている。
指示（ここから貼る）:
  次のバグの原因を特定してください。まずは修正せず、原因の仮説と根拠だけを先に出してください。
  ・症状: <何がどうなる。期待する挙動との差>
  ・再現手順: <1) ... 2) ... 3) ...>
  ・エラー / ログ: <スタックトレースや該当ログを貼る。無ければ「なし」>
  ・関係していそうな範囲: <ファイル / ディレクトリ / 機能名。分からなければ「不明」>
  調べる順番は「再現を確認 → 関係コードを読む → 原因の仮説を1〜3個 → 各仮説の確かめ方」。
  仮説が1つに絞れたら、修正案を差分の形で提案してから、私の確認を待って適用してください。
出力形式・制約: 最初の返信は「原因の仮説（根拠つき）」と「確かめる手順」だけ。コード変更はしない。
  本番データ・本番環境には触れない。
つまずきどころ: いきなりパッチが返ってきたら「まず原因の仮説だけ」と一度突き返す。再現手順が
  曖昧だと調査が発散するので、最小の再現ケースを先に渡す。

──────────────────────────────
02. 新機能の実装
──────────────────────────────
期待できるメリット: 完成イメージのズレによる作り直しが減る。受け入れ条件を先に共有するので、
  「動くけど求めていたものと違う」を最初のレビューで潰せる。
使う場面: 仕様がだいたい決まった小〜中規模の機能を、1セッションで実装してほしいとき。
前提: 実現したいこと（ユーザーから見た挙動）と、触ってよい範囲が言語化できている。
指示（ここから貼る）:
  次の機能を実装してください。
  ・ゴール（完了条件）: <ユーザーから見て何ができるようになれば完成か。1文で>
  ・スコープに含む: <対象の画面 / API / 関数>
  ・スコープに含めない: <今回はやらないこと。例: 既存の○○の挙動は変えない>
  ・参考にする既存実装: <似た機能のファイルパス。無ければ「なし」>
  ・制約: <使ってよい / 使ってはいけないライブラリ、命名規則、テストの要否>
  実装前に、変更するファイルの一覧と方針を3〜5行で先に出してください。合意できたら実装し、
  差分の要約とテスト結果を添えて提出してください。
出力形式・制約: 着手前に「変更ファイル一覧＋方針」。完了時は「差分の要約」「テスト結果」「動作確認の手順」。
  依存パッケージの追加は事前に理由とともに提案し、承認を待つ。
つまずきどころ: スコープに含めない範囲を書き忘れると、周辺コードまで「親切に」直される。
  既存の挙動を変えてほしくないなら明記する。

──────────────────────────────
03. 大きめのリファクタリング
──────────────────────────────
期待できるメリット: 「途中で挙動が変わっていた」を防げる。1回で全部やらせず段階に割るので、
  レビューが現実的な大きさに収まり、問題が起きた地点を特定しやすい。
使う場面: 構造の作り直し・共通化・命名の統一など、動作は変えずに内部だけ整理したいとき。
前提: 現状の挙動を守るためのテスト、または動作確認の手順がある。
指示（ここから貼る）:
  次のリファクタリングをしてください。外から見た挙動は一切変えないでください。
  ・対象: <ファイル / モジュール / 機能>
  ・目的: <何を良くしたいか。例: 重複した処理を1か所にまとめる>
  ・守ること: 既存テストが全て通ること。公開API・関数シグネチャを変えないこと。
  進め方: (1) 現状の構造と問題点を要約 (2) 変更を意味のある単位に分割した計画 (3) 1単位ずつ
  実施し、そのつどテストを流して結果を報告。私が「次へ」と言うまで次の単位に進まないこと。
出力形式・制約: まず「現状要約＋分割計画」。以降は1単位ごとに「変更内容＋テスト結果」。
  1単位あたりの差分は目安200行以内に収める。
つまずきどころ: 「ついでに」機能追加やバグ修正を混ぜられると差分が読めなくなる。混ぜない指示を明記。
  分割せず一気にやられたら、計画に戻して区切り直す。

──────────────────────────────
04. ライブラリ / フレームワークの移行
──────────────────────────────
期待できるメリット: 移行漏れと「動くが非推奨の書き方」の混入を減らせる。先に移行方針を決めるので、
  途中でやり方が変わって二重作業になるのを防げる。
使う場面: バージョンアップや別ライブラリへの乗り換えを、影響範囲を見ながら進めたいとき。
前提: 移行元と移行先、対象バージョンがはっきりしている。公式の移行ガイドがあれば手元にある。
指示（ここから貼る）:
  <移行元> から <移行先>（バージョン <x.y>）へ移行してください。
  最初に、変更が必要な箇所を一覧化してください（ファイルパスと理由）。
  ・参照する公式ガイド: <URL。無ければ「なし」>
  ・優先順位: まず動く状態を保ちながら段階的に。ビルドが通らない状態を長く残さない。
  ・非推奨API: 移行先で非推奨の書き方は使わず、推奨される書き方に合わせる。
  一覧に合意できたら、1グループずつ移行し、そのつどビルドとテストの結果を報告してください。
出力形式・制約: 最初に「変更必要箇所の一覧」。以降はグループ単位で「変更内容＋ビルド／テスト結果」。
  一度に全ファイルを書き換えない。
つまずきどころ: 移行先バージョンを指定しないと、最新前提で古い環境では動かないコードになる。
  「まず一覧だけ」を守らせないと、影響の全体像が見えないまま進む。

──────────────────────────────
05. 既存のプルリクエストのレビュー依頼
──────────────────────────────
期待できるメリット: 自分のレビューの抜けを補える。指摘が「重大度つき」で返るので、直すべき順番が
  分かり、些細な指摘に時間を取られない。
使う場面: 他人（または過去の自分）のPRを読む前に、機械的な観点を先に洗い出しておきたいとき。
前提: 対象のブランチ／差分がローカルにある。レビューの観点（何を重視するか）が言える。
指示（ここから貼る）:
  次の差分をレビューしてください。コードは変更しないでください。
  ・対象: <ブランチ名 / PR番号 / 差分の範囲>
  ・重視する観点: <例: 例外処理の漏れ、境界値、既存挙動への影響、命名>
  ・このリポジトリの約束事: <あれば。例: ログの書式、エラーの返し方>
  指摘は「重大度（高 / 中 / 低）」「場所（ファイル:行）」「なぜ問題か」「直し方の提案」の4点セットで、
  重大度が高い順に並べてください。良い点も2〜3個挙げてください。
出力形式・制約: 指摘の表（重大度／場所／理由／提案）。コードの書き換えはしない。推測で仕様を
  決めつけず、確認が必要な点は「要確認」として分ける。
つまずきどころ: 観点を渡さないと粒度がバラバラの指摘が大量に返る。重視する2〜3点に絞って伝える。

──────────────────────────────
06. テストの追加
──────────────────────────────
期待できるメリット: 「カバレッジは上がったが意味の薄いテスト」を避けられる。どの分岐・境界を守りたいか
  先に伝えるので、後から効くテストになる。
使う場面: 仕様は固まっているのにテストが薄い箇所へ、狙いを定めてテストを足したいとき。
前提: テストフレームワークと、既存テストの置き場所・書き方の慣習がある。
指示（ここから貼る）:
  次の対象にテストを追加してください。
  ・対象: <関数 / クラス / エンドポイント>
  ・仕様（期待する挙動）: <正常系と異常系を箇条書きで>
  ・特に守りたいケース: <境界値、例外、過去に壊れたことがある条件>
  ・書き方: 既存の <テストファイル名> の書式に合わせる。1テスト1アサーションを基本に。
  実装コードは変更しないでください。テストを足した結果、既存のバグが見つかったら、直さずに
  「失敗するテスト＋原因の見立て」として報告してください。
出力形式・制約: 追加したテストの一覧（何を確認するテストか1行ずつ）＋実行結果。プロダクトコードは触らない。
つまずきどころ: 「特に守りたいケース」を書かないと、通りやすいハッピーパスだけが増える。
  過去に壊れた条件を思い出して渡す。

──────────────────────────────
07. パフォーマンス改善
──────────────────────────────
期待できるメリット: 体感や勘ではなく計測に基づいて直せる。「速くなったが別の所が遅くなった」を
  ビフォーアフターの数字で検知できる。
使う場面: 遅い箇所の心当たりはあるが、原因と効果を数字で確かめながら直したいとき。
前提: 遅さを再現できる操作・入力と、計測する方法（時間の測り方）がある。
指示（ここから貼る）:
  次の処理のパフォーマンスを改善してください。まず計測してから直してください。
  ・遅い操作: <どの操作 / どの入力サイズで遅いか>
  ・現状の数値: <分かれば。例: 1万件で約8秒>
  ・目標: <例: 2秒以内。無ければ「まず現状を計測して提案」>
  進め方: (1) 現状を計測し、時間を食っている箇所を特定 (2) 改善案を効果の見込みとともに提示
  (3) 合意した案だけ実施 (4) 改善後を同じ条件で計測し、ビフォーアフターを report。
  可読性を大きく損なう最適化は、そうと明記して選べるようにしてください。
出力形式・制約: 「計測結果（前）」→「改善案と見込み」→「改善後の計測」。挙動を変えないこと（結果が
  変わる最適化はしない）。
つまずきどころ: 目標値も計測方法も渡さないと、推測で書き換えられて逆に遅くなることがある。
  まず計測、を徹底する。

──────────────────────────────
08. 不明点が出たときの振る舞いを決める ★動画で読み上げるテンプレ
──────────────────────────────
期待できるメリット: エージェントが「勝手に突き進む」と「いちいち止まる」の中間で動くようになる。
  待ち時間が減り、かつ後戻りできない判断は必ず人に回ってくる。長時間タスクほど効く。
使う場面: 依頼のたびに書くのが面倒なら、AGENTS.md（またはCLAUDE.md）に一度書いておく。
前提: 何が「後戻りできない判断」かを自分の言葉で決められる。
指示（ここから貼る。AGENTS.md にそのまま貼れる）:
  ## 不明点が出たときの進め方
  - 結果が変わらない細かい前提（命名、置き場所、書式など）は、このリポジトリの慣習に合わせて
    自分で埋めて進めてください。埋めた前提は作業ログに1行残してください。
  - 判断で結果が変わる場合は、質問を投げたうえで、その回答を待たなくても進められる部分は
    先に進めてください（非同期で質問する）。
  - 次のものは「後戻りできない判断」です。私の明示的なOKが出るまで実行しないでください:
    <例: 本番データベースへの書き込み / 課金が発生する操作 / 外部への通知・投稿 /
    依存パッケージの追加・削除 / 100行を超える一括変更>
  - 30分待っても回答が無いときは、安全側（変更を最小にする側）の仮定で進め、危険な操作の
    手前で止まって待ってください。
出力形式・制約: 作業の区切りごとに「自分で埋めた前提」「投げた質問」「止まって待っている項目」を
  短くまとめて報告する。
つまずきどころ: 「後戻りできない判断」のリストが空だと、結局なんでも自分で決めて進んでしまう。
  自分の現場で怖い操作を3〜5個は具体的に挙げる。

──────────────────────────────
09. 長時間タスクを分割して進めてもらう
──────────────────────────────
期待できるメリット: 数時間かかる作業でも、途中の成果が確認できる状態で積み上がる。1か所こけても
  そこまでの成果が無駄にならない。
使う場面: 一括では大きすぎるタスク（全体移行、広範囲の対応、大量ファイルの一括処理）を任せるとき。
前提: タスクを意味のある小単位に分ける切り口が言える（機能別、ディレクトリ別、種類別など）。
指示（ここから貼る）:
  次のタスクを一気にやらず、小単位に分けて進めてください。
  ・全体のゴール: <最終的にどうなれば完了か>
  ・分ける切り口: <例: ディレクトリ単位 / 対応の種類単位>
  ・1単位の完了条件: <例: その範囲でビルドが通り、テストが緑>
  最初に「分割した単位の一覧」と「進める順番」を出してください。以降は1単位ずつ、完了条件を
  満たしたら「done: <単位名>、次は <次の単位>」と報告して、私の「次へ」で進んでください。
  作業メモ（判明した注意点、詰まった箇所）は単位ごとに残してください。
出力形式・制約: 「分割一覧＋順番」→ 単位ごとに「done報告＋作業メモ」。1単位が想定より大きいと
  分かったら、さらに分けてよい。
つまずきどころ: 完了条件を決めないと「だいたいできた」で次に進み、後半で破綻する。1単位ごとに
  緑になる条件を必ず置く。

──────────────────────────────
10. 技術選定・下調べ（結論を急がせない）
──────────────────────────────
期待できるメリット: それらしい結論が先に出て検討が終わってしまうのを防げる。選択肢と長所短所が
  並ぶので、自分たちの条件で選べる。
使う場面: ライブラリ選定、設計方針の比較など、すぐコードを書く前に判断材料をそろえたいとき。
前提: 何を優先するか（速度、保守性、学習コスト、実績など）の優先順位がある程度言える。
指示（ここから貼る）:
  次のテーマについて、結論を出す前に選択肢を比較する材料をそろえてください。
  ・テーマ: <何を選ぶか。例: ○○を実現するライブラリ>
  ・前提条件: <言語 / 実行環境 / チームの習熟度 / 既存構成>
  ・重視する軸: <例: 保守のしやすさ ＞ 実行速度 ＞ 学習コスト>
  出してほしいもの: 候補を2〜4個、各候補について「向いている場合／向かない場合」「導入の手間」
  「実績・更新の活発さ」「今回の前提条件との相性」を表で。最後に、私が判断するための
  「決め手になる質問」を2〜3個。あなたの推しは最後に1つだけ、理由つきで。
出力形式・制約: 比較表 ＋ 決め手の質問 ＋ 推し1つ。コードは書かない。出典が確認できない主張は
  「未確認」と明記する。
つまずきどころ: 重視する軸を渡さないと、一般論の「よく使われている」で結論が出る。自分たちの
  優先順位を先に渡す。
```

**ポイント**: どのテンプレも共通して「まず方針・一覧・計測だけを先に出させて、合意してから実行させる」形にしています。Astra は放っておいても進みますが、进み出す前に一度止めて向きを合わせるほど、最後の手戻りが小さくなります。


### 3. OpenAIアカデミー攻略ルート表（Astra時代版）（テンプレート）

# 🎁 OpenAIアカデミー攻略ルート表（Astra時代版）

何十時間ぶんもあるOpenAIアカデミー（academy.openai.com）の教材から、「いま自分が見るべき90分ぶん」だけを最短で選べる早見表です。非エンジニアとエンジニアで入口を分け、見る順番・持ち帰るもの・今は飛ばしていい教材まで1枚にしています。GPT-6 Astra（アストラ）が出たあとに、どこから手をつけるかで迷わなくなります。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: ステップ1で自分がどちら側かを決め、そのルートのステップだけを上から順にチェックしてください。所要時間はすべて公式表記または実測の目安です。

```text
【OpenAIアカデミー攻略ルート表（Astra時代版）】

前提: academy.openai.com は閲覧だけならサインイン不要。進捗の保存と修了証にはChatGPTアカウント
（無料枠で可）が要る。受講料・サブスク・クレカは不要。

■ ステップ1：自分がどちら側かを決める
□ コードは書かない。エージェントに仕事を「任せる側」で使いたい
  → YES: ルートA（非エンジニア）へ
□ 自分でコードを書く。Codex や Claude Code を開発に使っている／使いたい
  → YES: ルートB（エンジニア）へ
（両方あてはまる人は、ルートA → ルートB の順で回ると土台が揃う）

──────────────────────────────
ルートA：非エンジニア（任せる側）
──────────────────────────────
■ ステップA-1：土台の2コースを流す（合わせて約2〜2時間半）
□ 「AI Foundations」を受けたか（所要60〜75分）
  → YES: 明確な指示・文脈の足し方・出力レビュー・責任ある利用の基本が入る
□ 「Applied AI Foundations」を受けたか（所要75〜90分）
  → YES: 繰り返し作業を「手順に分けて、レビューを挟む」形にできるようになる
指示例: 学んだ手順分解を、自分の定例業務1つ（例: 週次レポート作成）にあてはめて、
  「工程・AIに任せる部分・人が確認する部分」を箇条書きにしてください。

■ ステップA-2：本命の「Agents and Workflows」を受ける（所要75〜90分・修了証あり）
□ 受講して修了証を取得したか
  → YES: 文脈を渡す／出力を定義する／境界を決める／下書きをレビューする／効いたやり方を
    再利用する、というエージェントへの仕事の任せ方が一通り身につく
補足: 修了証はGradual（グラデュアル）発行の「学習の修了証明」であって、OpenAIの公式資格ではない。
  履歴書の資格欄に書くものではなく、社内共有や学習の区切りに使う位置づけ。

■ ステップA-3：現場で1回試す
□ 実際の業務1つを、ステップA-1で作った工程表どおりにエージェントへ依頼したか
  → YES: 「任せられる形になっていたか」を振り返り、抜けた工程を工程表に追記する
指示例: 今回の依頼で曖昧だった点を3つ挙げて、次回の依頼文にそのまま足せる一文にしてください。

──────────────────────────────
ルートB：エンジニア（自分で書く側）
──────────────────────────────
■ ステップB-1：Codexの基礎教材を流す（academy.openai.com → Communities → Builders）
□ 「Codex 101: Introduction and Onboarding」を読んだか（教材ページ・随時更新）
  → YES: Codex（コーデックス）の全体像とセットアップが分かる
□ 「Codex 102: Practical Workflows」を読んだか
  → YES: CLI・IDE連携・MCP（エムシーピー）・コードレビューまわりの実務の流れが分かる
補足: これらの教材はGPT-5.6世代の記述が残っている。読み替えの原則は「教わる“型”は変わらない、
  モデル名だけ新しいものに置き換える」。

■ ステップB-2：Codex Bootcampの録画を、必要なレベルだけ見る（各1時間）
□ 101「Agentic coding」を見たか
  → YES: タスクの切り出し・文脈の渡し方・進行中の軌道修正・適用前のコードレビュー、の4つの型
□ 201「Team workflows」を見たか（チームで使うなら）
  → YES: 共有コンテキスト・リポジトリ指針・承認・サンドボックス・再利用スキル・自動化・worktree
□ 301「Advanced automation」を見たか（本番自動化まで行くなら）
  → YES: 権限・サブエージェント・plan mode・memory・Codex SDK・Codex exec・CI／セキュリティのパターン
指示例: 101で出てくる「4つの型」を、自分が今週やる予定のタスク1つに当てはめて、
  依頼文の下書きにしてください。

■ ステップB-3：実プロジェクトで4つの型を回す
□ 実タスク1件を「切り出し → 文脈 → 境界 → 適用前レビュー」の順で依頼したか
  → YES: 手戻りが出た型（切り出しが甘かった等）を特定し、次回はそこを厚くする
□ 「不明点が出たときの振る舞い」を AGENTS.md に1回書いたか
  → YES: 依頼のたびに書かずに済む（別キット「Codex依頼文テンプレ10選」のテンプレ8）

──────────────────────────────
共通：いま学ばなくていいもの（時間を使わない）
──────────────────────────────
□ AgentKit の「Agent Builder」（ノーコードのビジュアル構築）
  → 2026年11月30日でEvalsとともに提供終了が公式告知済み。ここに時間を投資しない。
    コードで組むなら Agents SDK、自然言語で使うなら ChatGPT の Workspace Agents が公式の代替。
□ 「とりあえず全コース制覇」
  → アカデミーは何十時間ぶんもある。上のルートで自分に要る90分〜数時間だけ取り、
    残りは必要になってから逆引きで見る。

──────────────────────────────
30秒サマリ
──────────────────────────────
・非エンジニア: AI Foundations → Applied → Agents and Workflows（修了証）→ 現場で1回試す
・エンジニア: Codex 101/102 → Codex Bootcamp 101（必要なら201/301）→ 実プロジェクトで4つの型
・全員: Agent Builder は学ばない（11/30終了）。修了証は資格ではない。教材のモデル名は読み替える。
```

**ポイント**: このルート表は「まず自分に要る分だけ取る」ための地図です。アカデミーは網羅的すぎて、順番を決めずに入ると迷子になります。上から2〜3ステップ進めたら、あとは詰まったときに逆引きで戻ってくる使い方が続きます。
