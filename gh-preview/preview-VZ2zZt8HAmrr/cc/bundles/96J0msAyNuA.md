# 🎁 Human-Agent Team 設計テンプレート

人間とAIエージェントが同じチームで働くための「名簿・北極星・信頼の広げ方」を決めるテンプレート。ループを個人の作業から、チームの仕組みへ育てるときに使う。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: チームのドキュメント（Slack canvas・Notion 等、エージェントが読める場所）に置く。「書かれていなければ存在しない」——エージェントは検索できるテキストからしか状況を理解できない。

```text
# Human-Agent Team 設計シート

## 1. 北極星（North Star）
- 事業・ミッションに根ざした長期ゴール（1文）:
- これを共有すると、優秀なエージェントは自分から次の作業を提案しはじめる

## 2. 名簿（Roster）— 誰が何を持つか
| メンバー | 人/AI | 担当タスク | 使えるツール |
|---|---|---|---|
| 例: レビュー担当 | AI | PRの初回レビュー | GitHub, テスト実行 |
|  |  |  |  |
- 人間もエージェントも同じスレッドで働き、誰でも途中から続けられるようにする

## 3. 公開性（Work in public）
- [ ] 意思決定・議事・ドキュメントを検索可能な場所に残す
- [ ] 共有はアイテム単位でなくワークスペース単位の境界で管理
- [ ] エージェントを主な読み手と想定してドキュメントを書く

## 4. 検証の仕組み（Verification）
- [ ] Doer-Verifier（起案役と検証役を分ける）
- [ ] 完了条件・チェックリスト・ルーブリックを用意
- [ ] 重要な判断はまとめて人間レビューに回す

## 5. 信頼を段階的に広げる（Trust over time）
- 最初: すべての出力を人間がレビューしフィードバック
- 次: 実績が出たタスク種別から自律範囲を広げる
- 定例: 週次で「教訓と失敗」を記録させ、同じ失敗を繰り返さない
```

**ポイント**: これは新しい話ではなく「明確な役割・良いドキュメント・共通の品質基準・失敗からの学習」という普遍のチーム論。エージェントが加わることで、それらが“あった方がいい”から“必須”に変わる。


### 3. Loop設計テンプレート（テンプレート）
# ループを「なんとなく回す」のではなく、トリガー・停止条件・検証・記録まで埋めてから回すための穴埋めテンプレート。

# 🎁 Loop設計テンプレート

ループを「なんとなく回す」のではなく、トリガー・停止条件・検証・記録まで埋めてから回すための穴埋めテンプレート。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: そのままコピーして、対象タスク・停止条件を埋める。まずは1つの繰り返し作業をループ化することから始める。

```text
# Loop 設計テンプレート

## 0. まず決める（シンプルから始める）
- このタスクは本当にループが必要か？（1回のプロンプトで済むなら不要）
- 使うループの種類: [ ] ターン [ ] ゴール(/goal) [ ] タイム(/loop・/schedule) [ ] プロアクティブ

## 1. 目的（Goal）
- 何を達成したら「完了」か:
- 完了を機械が判定できる形にする:（例: テストが通る / Lighthouse 90以上 / lintゼロ）

## 2. トリガー（いつ始まるか）
- [ ] 人がプロンプトを送る（ターンベース）
- [ ] その場で /goal 実行（ゴールベース）
- [ ] 時間間隔 /loop（ローカル）・/schedule（クラウド常駐）
- [ ] イベント（PR・webhook・メール受信・監視アラート）＝プロアクティブ

## 3. ループ本体（Act → Verify）
1. 実行役: 作業する
2. 検証役: 完了条件を満たしたか判定する（実行役と分ける）
3. 未達なら差分を直して再実行、達成ならユーザーに返す

## 4. 停止条件（Stop condition）※必ず数値・明確な条件で
- [ ] 完了条件を満たした
- [ ] 最大試行回数（例: 5回）に到達
- [ ] コスト上限に到達

## 5. 記録（Memory / Log）
- 実行日時・対象・変更点・判断理由を LOG に追記
- 次回はこの LOG を読んでから始める（同じ失敗を繰り返さない）

## 6. ガードレール
- 「絶対にやってはいけないこと」は指示ではなくフック＋権限で止める
- 隔離環境（worktree / クラウドボックス）で回す
- 人間の最終確認を挟む工程を明記する
```

**ポイント**: 停止条件を必ず数値で決めておくと、無限ループとトークンの暴走を防げる。「思考はアウトソースできても、理解はアウトソースできない」——出力は必ずレビューする。

# 🎁 Loop 全体構成図（Mermaid）

トリガー → 実行役 → 検証役 → （未達なら戻る／達成なら完了）→ 記録、という「良いループ」の骨格を1枚に描いた Mermaid 図。内側ループ（1タスク）と外側ループ（次のトリガーを待つ）の関係も表現。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: GitHub / Notion / Obsidian など Mermaid 対応の場所にそのまま貼ると図として描画される。

```text
flowchart TB
    subgraph OUTER[外側のループ: 次のトリガーを待ち続ける]
      T([トリガー<br/>人のプロンプト / 時間 / イベント]) --> D[実行役エージェント<br/>Doer]
      subgraph INNER[内側のループ: 1タスクを完了させる]
        D --> V{検証役<br/>Verifier<br/>完了条件を満たした?}
        V -->|未達| F[差分を修正] --> D
      end
      V -->|達成| L[(共有メモリ / LOG<br/>判断・変更を記録)]
      L --> R[人間がレビュー<br/>要所を確認]
      R --> T
    end
    G[[ガードレール: Hook + 権限<br/>絶対にやってはいけないことを止める]] -.- INNER
    ML[["まずシンプルに始める<br/>停止条件は必ず明確に"]] -.- OUTER
```

**ポイント**: 心臓部は「V →（未達）→ D」の戻り矢印。完了条件を満たすまで回るこの部分が、ループを“ただの1回実行”と分ける。検証役を実行役と分けると、自己採点バイアスが減って品質が安定する。


### 5. Rule テンプレート（テンプレート）
# 特定のファイル・パスにだけ効かせたい制約を書くファイル。`paths` を指定すると、そのパスに触るときだけ読み込まれるので、無駄なコンテキストを使わない。

# 🎁 Rule テンプレート

特定のファイル・パスにだけ効かせたい制約を書くファイル。`paths` を指定すると、そのパスに触るときだけ読み込まれるので、無駄なコンテキストを使わない。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: `.claude/rules/<rule-name>.md` として保存。`paths` を書けば path-scoped（推奨）、書かなければ CLAUDE.md と同じく常時ロードになる。

```text
---
paths:
  - "src/api/**"
  - "**/*.handler.ts"
---

# API ハンドラの制約

- すべての API ハンドラは、処理の前に Zod で入力を検証すること
- DB マイグレーションは追記のみ（既存マイグレーションを書き換えない）
- 外部APIの呼び出しには必ずタイムアウトとリトライ上限を設定する
- 秘密情報（APIキー・トークン）をログやレスポンスに出さない
```

**ポイント**: パス限定ルールは「そのファイルを触るときだけ」読み込まれる。ドキュメントだけ編集するセッションでは API ルールが読み込まれず、コンテキストが軽くなる。「絶対に止めたい」ことはルール（指示）ではなく Hook（決定論的ガードレール）で止めるのが確実。

# 🎁 SKILL.md テンプレート

手順（ワークフロー）を再利用可能な形で書くファイル。呼び出し時にだけ読み込まれるので、コンテキストコストが低い。検証手順をここに書くと、Claude自身の自己検証が効くようになる。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: `.claude/skills/<skill-name>/SKILL.md` として保存。名前と説明で自動マッチ、またはスラッシュコマンドで起動する。

```text
---
name: verify-frontend-change
description: フロントの変更を検証する手順。UIを変えたら毎回この手順で自己検証する。
---

# フロントエンド変更の検証手順

この手順は、UIに変更を加えたあと「見た目・動作・エラー」を自分で確認するためのもの。
どれか1つでも失敗したら、直して最初からやり直す。中途半端なまま返さないこと。

## 手順
1. 開発サーバを起動し、対象ページを開く
2. 変更箇所を操作し、before/after のスクリーンショットを撮る
3. ブラウザのコンソールを確認する（エラー・警告ゼロが条件）
4. Chrome DevTools MCP で Core Web Vitals を計測する
5. 関連するテストを実行し、すべてパスすることを確認する

## 完了条件（定量的に）
- [ ] コンソールエラー 0件
- [ ] 対象テストがすべてパス
- [ ] レイアウト崩れなし（スクショで確認）

## 失敗したら
- 原因を特定して修正 → 手順1からやり直す
- 3回試して直らなければ、状況と試したことを添えて人間に戻す
```

**ポイント**: 検証は「定量的な基準」ほどClaudeが自己判定しやすい（エラー0件・スコア90以上など）。手順を SKILL.md に固定すると、毎回同じ品質でチェックが回る。
