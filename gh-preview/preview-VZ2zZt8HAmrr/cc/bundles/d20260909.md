# 🎁 長い自動化がコケた時の復旧手順

Claude Code に任せた長い作業（大きめのリファクタ、複数ファイルの実装、リサーチ、資料作成、データ整理など）が途中で失敗・脱線したときに、最初からやり直さずに「壊れた所だけ」を直して再開するための手順書です。論文でいう「実行時状態管理（状態記録・失敗箇所の特定・復旧）」を、Claude Code の実際の操作（コミット・`/rewind`・`--resume`・サブエージェント）に落としたものです。

**受け取り方**: このファイルをそのままコピー、またはダウンロードしてご利用ください。

**使い方**: 失敗に気づいた時点で上から順に埋めます。各ステップの「指示例」はそのまま Claude に貼れます。次からは、作業を始める前にステップ0を仕込んでおくと、この手順がずっと楽になります。

```text
【長い自動化がコケた時の復旧手順（Claude Code版）】

■ ステップ0：次回のために先に仕込む（今から始める人向け）
□ 作業を「調べる→設計→実装→検証」など3〜5個の工程に分け、着手前にプランモードで計画を出させたか
□ 工程がひとつ終わるたびに git commit する、と最初に約束させたか（メッセージに工程名を入れる）
□ 各工程の終わりに「完了した工程名／変更点3行／次の工程名」だけ報告させるようにしたか
□ 検証（レビュー）は別セッションか、レビュー専用サブエージェントに回すと決めたか
→ YES: これで失敗しても「どのコミットまで正しかったか」がすぐ分かる
指示例: これから複数工程の作業をお願いします。着手前に工程分けの計画だけ出してください。各工程が終わるたびに、工程名を含むメッセージでコミットし、「完了した工程名／変更点3行／次の工程名」を報告してから次に進んでください。

■ ステップ1：まず止める・広げない
□ 失敗・脱線に気づいた
□ そのまま「続けて」「直して」と重ねて頼んでいない（間違ったコードの上に積み増さない）
□ 未コミットの変更があるなら git status / git diff で範囲を確認したか
→ YES: 一度セッションを止めて、下の切り分けに移る
指示例: いったん作業を止めてください。今の続きは書かないで、直近で変更したファイルと、どの工程で何をしようとして失敗したかだけ教えてください。

■ ステップ2：どこまでが正しかったかを確定する（戻る地点を決める）
□ 直近で「ここは動く・正しい」と確認できた工程／コミットはどれか
□ その時点の状態は git log で特定できるか（できないなら、そのハッシュを聞く）
□ セッション内で戻れるなら、崩れる前のターンまで /rewind で戻せるか確認したか
→ YES: そのコミット（またはターン）が「戻る地点」。ここより後だけ作り直す
指示例: これまでのコミットのうち、テストが通る・意図どおり動くと確認できている最後のものはどれですか。そのハッシュと、そこまでで完了している工程を教えてください。

■ ステップ3：失敗の原因を1つに絞る
□ 「前提の情報・仕様が足りなかった」タイプか
□ 「工程の順番・分け方が悪く、依存を無視した」タイプか
□ 「途中の指示や決定事項を取り違えた・忘れた」タイプか（コンテキストが長くなりすぎ含む）
→ YES（情報不足）: 足りなかった仕様を渡し、戻る地点から再開
→ YES（順番が悪い）: 工程の分け方を直し、プランを立て直してから再開
→ YES（取り違え）: 戻る地点の状態から新しいセッションを開き、確定事項を最初に貼って再開（/compact ではなく作り直す）
指示例: 今回うまくいかなかった原因は、(a)仕様・前提の不足 (b)工程の分け方・依存の無視 (c)途中の指示の取り違え のどれに近いですか。根拠になった箇所も一言添えてください。

■ ステップ4：戻して、作り直す範囲を決める（全部やり直さない）
□ 戻る地点まで戻したか（git: そのコミットへ checkout / reset、セッション: /rewind、または新セッションで再開）
□ 戻る地点から先の工程を書き出したか
□ そのうち、今回の失敗の影響を受けたのはどれか。受けていない工程の成果はそのまま流用と決めたか
→ YES: 影響を受けた工程だけを作り直し対象にする
指示例: 戻る地点は コミット◯◯ です。そこまでの実装は「確定」として触らず、工程◯以降だけをやり直してください。まず工程◯の計画だけ先に出してください。

■ ステップ5：チェックは別の役にやらせる
□ 作り直した成果を、作ったのと同じセッションでそのまま自己レビューさせていないか
□ 別セッション、またはレビュー専用サブエージェント（読み取り系ツールだけ許可）に、差分だけ渡してレビューさせたか
→ YES: 「自分の判断」を「正しい証拠」と取り違える事故を防げる
指示例: （別セッション or レビュー用サブエージェントで）これは別途作られた差分です。作成の経緯は知らない前提で、バグ・仕様との食い違い・前の工程との矛盾・テスト不足だけを指摘してください。

■ ステップ6：再発防止を1行だけ残す
□ 今回の失敗を、ステップ0のどの項目に足せば防げたかを1行でメモしたか
□ それを CLAUDE.md か、その作業用の指示テンプレに追記したか
→ YES: 次の長い作業のとき、その1行が最初から効く
指示例: 今回の失敗を次回防ぐための注意を、作業開始時の指示に足す形で1文にしてください。CLAUDE.md に足すべきものなら、その文面も出してください。

■ 判定
□ 戻る地点（コミットまたはターン）が決まり、作り直す範囲が「一部の工程」に絞れた
→ YES: そのまま部分的な作り直しへ進む
→ NO（どこまで正しいか分からない・コミットが1つも無い）: 状態が残っていない。今回は作り直しになるが、次回は必ずステップ0のコミット約束を仕込む
```

**ポイント**: 「最初からやり直す」を選ぶ前に、必ずステップ2（どこまで正しかったか）を試すこと。工程ごとのコミットが1つでもあれば、そこが「戻る地点」になり、次回から復旧が一気に楽になります。

# 🎁 3要素への分け直しワークシート（Claude Code）

いま1つのセッションに全部やらせている「長い作業」を、論文の3要素（① 工程分解 ／ ② レビュー分離 ／ ③ 状態記録）に沿って組み直すためのワークシートです。そのままコピーして使える**レビュー専用サブエージェント定義**と、工程分割を指示する**貼るだけのプロンプト**、**CLAUDE.md に足す運用規約の雛形**が入っています。

**使い方**: まず「A. 分け直しワークシート」を上から埋めて、いまの作業のどこが手薄かを出します。次に手薄だった要素に対応する B / C / D をコピーして使います。全部やる必要はありません。

## A. 分け直しワークシート

```text
【1体運用を3要素に分け直すワークシート】

■ ステップ0：対象を1つ選ぶ
□ Claude Code に任せている「長い作業」を1つ書いた（例：機能追加、大規模リファクタ、移行、調査＋実装）
□ その作業は、いつも1つのセッションで最初から最後までやらせている
→ YES: この作業を、下の①②③で点検する

■ ステップ①：工程は分かれているか（タスク組織化）
□ その作業を3〜6個の工程に口で言える（例：影響調査→設計→実装→テスト→ドキュメント）
□ 「どの工程が先で、どれが並行できるか」を書き出したことがある
□ 着手前に、Claude にプランだけ出させている（実装を止めて計画のみ）
→ NO が1つでもある: 「① 工程分解」が手薄。→ C の分割プロンプトを使う
指示例: この依頼を実装せず、まず工程に分けた計画だけ出してください。各工程に「依存する工程」「並行できる工程」を明記してください。

■ ステップ②：レビューは分かれているか（エージェント連携）
□ Claude が書いたコードを、書いたのと別のセッション／サブエージェントに見せている
□ 「テストが通った＝正しい」で完了扱いにしていない
□ レビュー役には、作成の経緯ではなく成果物（差分）だけを渡している
→ NO が1つでもある: 「② レビュー分離」が手薄。→ B のサブエージェント定義を置く
指示例: （レビュー用の別コンテキストで）これは別途作られた差分です。経緯は知らない前提で、バグ・仕様との食い違い・テスト不足だけを指摘してください。

■ ステップ③：状態は残っているか（実行時状態管理）
□ 工程の節目ごとに git commit している（メッセージに工程名が入っている）
□ 途中で崩れたとき、「どのコミットまで正しかったか」がすぐ分かる
□ 崩れたら /rewind や --resume で戻し、その工程だけやり直している
→ NO が1つでもある: 「③ 状態記録」が手薄。→ D の運用規約を CLAUDE.md に足す
指示例: これから工程ごとに進めます。工程が1つ終わるたびに、工程名を含むメッセージでコミットしてから次に進んでください。

■ 判定
□ ①②③のうち、手薄だった要素はどれか（1つでも2つでも）
→ 手薄な要素の対策（B / C / D）だけを、次の作業から1つ試す
→ ①②③すべて満たしている: すでにシステムの知能の入口。次は工程の並行度を上げる
```

## B. レビュー専用サブエージェント定義（`.claude/agents/reviewer.md`）

プロジェクトの `.claude/agents/reviewer.md` に置くと、Claude が実装のレビューをこのエージェントに委譲できるようになります。読み取り系ツールだけ許可しているので、レビュー役が勝手にコードを書き換えることはありません。

```text
---
name: reviewer
description: 実装済みの差分やファイルをレビューする。バグ・仕様との食い違い・テストの抜けだけを指摘し、修正はしない。実装を書いたセッションとは別に、成果物だけを渡して使う。
tools: Read, Grep, Glob, Bash
model: sonnet
---

あなたはコードレビュー専任です。実装の経緯や設計意図は共有されていない前提で、渡された差分・ファイルだけを見てレビューします。

やること:
- バグ（境界条件・null/空・例外未処理・競合）を具体的な行とともに指摘する
- 仕様・既存コードとの食い違いを指摘する
- テストの抜け（追加された分岐に対応するテストが無い等）を指摘する
- 指摘は「重大 / 中 / 軽微」で分類し、重大から並べる

やらないこと:
- コードを書き換える・ファイルを編集する（読み取りのみ）
- 経緯を推測して「たぶんこういう意図だろう」で見逃す
- スタイルの好みだけの指摘（機能に影響しないものは省く）

指摘が無ければ「重大・中の指摘なし」と明言する。「たぶん大丈夫」は書かない。
```

**使い方**: 実装が一区切りしたら、実装セッションで `git diff` を取り、別セッションまたは「reviewer で差分をレビューして」と頼んでこのエージェントに渡します。指摘を受けてから実装セッションに戻って直します。

## C. 工程分割を指示するプロンプト（貼るだけ）

長い作業を頼むとき、実装より先に貼ります。

```text
これから複数工程の作業をお願いします。まだ実装はしないでください。

1. この依頼を3〜6個の工程に分け、各工程に「目的」「触るファイル」「依存する工程」「並行できる工程」を書いてください。
2. 並行できる工程は、別々に進める前提でグループ分けしてください。
3. 各工程の「完了の判定基準」（何が満たされたら次に進んでよいか）を1行で書いてください。
4. 計画に合意したら、工程1から進めます。工程が1つ終わるたびに、工程名を含むメッセージでコミットし、「完了した工程名／変更点3行／次の工程名」を報告してから次に進んでください。
5. 実装の一区切りごとに、レビューは別途 reviewer に回します。あなたは自己レビューで完了扱いにしないでください。
```

## D. CLAUDE.md に足す運用規約の雛形

プロジェクトの `CLAUDE.md` に足すと、長い作業のたびに毎回指示しなくてよくなります。

```text
## 長い作業の進め方（3工程以上に分かれる依頼のとき）

- 実装前に、工程・依存・並行可否・完了判定を書いた計画を出す（プランのみ）
- 工程が1つ終わるたびに、工程名を含むメッセージでコミットする
- 各工程の終わりに「完了した工程名／変更点3行／次の工程名」を報告する
- 実装の一区切りごとに、レビューは reviewer サブエージェント（または別セッション）に差分だけ渡す。自己レビューで完了扱いにしない
- 途中で崩れたら、続きを書かずに一度止め、崩れる前のコミットに戻ってからその工程だけやり直す
```

**ポイント**: いきなり全部を導入しなくてかまいません。ワークシートAで手薄だった要素の1つ（多くは②のレビュー分離）から始めると、いちばん早く効果が出ます。
