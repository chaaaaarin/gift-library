# 🎁 AIコーディングツール 冗長化セットアップ手順

「AIの頭脳を1社に預けない」を、口で言うだけで終わらせないための手順書。30分で、メインとは別のツール／モデルをいつでも動かせる並行環境を作り、指示（ルール）を両対応にして、片方が止まっても作業が続く状態にします。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 上から順に実行します。ステップ1〜3が「並行環境づくり」（1回だけ）、ステップ4が「ルールの両対応化」（プロジェクトごと）、ステップ5が「毎週の点検」（習慣）。コマンドは自分の環境に合わせて読み替えてください。

```text
【AIコーディングツール 冗長化セットアップ手順】

──────────────────────────────
■ ステップ0：なぜやるか（30秒で読む）
──────────────────────────────
・便利なツールほど、中身のAI（モデル）を他社に頼っている。
・会社どうしの契約で、ある日いきなり特定モデルが使えなくなることがある
  （2026年11月、CursorからOpenAIモデルの直接アクセスが止まる——のが実例）。
・対策は「乗り換え」ではなく「もう1系統を、いつでも動かせる状態にしておく」。
・目標：メインが3日止まっても、別ツール＋別モデルで作業を続けられる。

──────────────────────────────
■ ステップ1：2つ目のツールを入れる（10分・1回だけ）
──────────────────────────────
□ いま何をメインにしている？
  → Claude Code がメインなら、2つ目は Cursor（GUI）か Codex CLI
  → Cursor がメインなら、2つ目は Claude Code（CLI）
□ 2つ目を最小構成で入れる。フル移行はしない。ログインが通り、
  1回コードを書かせられれば合格。

  # 例：Claude Code をサブに入れる（Node.js 18+ が必要）
  npm install -g @anthropic-ai/claude-code
  cd <あなたのプロジェクト>
  claude
  # → 「このリポジトリの構成を3行で説明して」で疎通確認

  # 例：Cursor をサブに入れる
  # cursor.com からダウンロード → 対象プロジェクトフォルダを開く
  # → Cmd/Ctrl+L でチャットを開き、同じ質問で疎通確認

□ 2つ目のツールで「モデルを1つ、メインとは別の会社のものにする」
  （メインが Claude なら、サブでは Gemini か GPT系 を既定にしておく）。

──────────────────────────────
■ ステップ2：モデルの逃げ道を1つ用意する（10分・1回だけ）
──────────────────────────────
□ いま使えるモデルを棚卸しする。最低「2社」動く状態にする。
  例）メイン＝Claude（Anthropic）、サブ＝Gemini（Google）または GPT（OpenAI）
□ サブのモデルは「プラン内の枠」か「自分のAPIキー」のどちらかで動くようにする。
  APIキーを使う場合は、キーを .env などに置き、リポジトリにコミットしない。

  # .gitignore に追記（キー流出防止）
  echo ".env" >> .gitignore
  echo ".env.local" >> .gitignore

□ 「このモデルでビルド〜テストまで一周できるか」を1回試す。
  できない機能（補完だけ、エージェントだけ 等）があればメモしておく。

──────────────────────────────
■ ステップ3：手元にバックアップを取る（5分・1回だけ）
──────────────────────────────
□ 大事なやり取り・設定・プロンプトを、ツールの外（自分のリポジトリ）に置く。

  mkdir -p .ai/rules .ai/prompts .ai/notes
  # よく使う指示文を1ファイル1個で .ai/prompts/ に保存
  # 重要なチャットの結論を .ai/notes/ に日付つきで残す

□ これで、どのツールが使えなくなっても「指示の型」は手元に残る。

──────────────────────────────
■ ステップ4：ルールを両対応にする（プロジェクトごと・15分）
──────────────────────────────
□ メインのルールファイルを「素の Markdown」で書く（ツール固有記法を避ける）。
  Claude Code    → CLAUDE.md（リポジトリ直下）
  Cursor         → .cursor/rules/（.mdc ファイル）
  Codex / 汎用   → AGENTS.md

□ 中身を下の「共通ルール雛形」で書き、両方に配る（または片方を symlink）。

  # 片方を正、もう片方をリンクにする例（内容を1箇所で管理）
  ln -s ../CLAUDE.md .cursor/rules/00-shared.mdc   # 環境により拡張子は調整

── 共通ルール雛形（CLAUDE.md / AGENTS.md にそのまま貼れる）──
# プロジェクト共通ルール

## 前提
- このリポジトリは <一言で用途>。主要言語は <言語>。
- パッケージ管理は <npm/pnpm/uv 等>。テストは <コマンド>。

## 守ること
- 変更は最小差分で。関係ないリファクタや抽象化を混ぜない。
- 外部入力（ユーザー入力・API応答）の境界だけでエラーハンドリングする。
- 秘密情報（APIキー・トークン）をコードやログに出さない。
- コミット前に <テストコマンド> が通ることを確認する。

## 作業の型
- 大きめの変更は「やること・対象ファイル・確認方法」を先に3行で出す。
- 完了条件：<ここまでやれば終わり、の基準を具体的に>。

## モデル差し替え時の注意（重要）
- このルールは特定モデルの癖に最適化しない。どのモデルでも通る書き方にする。
- 「前の会話を覚えている前提」で書かない。必要な文脈は毎回ファイルから読ませる。
──────────────────────────────────────────────

□ ツール固有の指示（Cursorの .mdc の frontmatter 等）は別ファイルに分け、
  共通ルール本体には混ぜない。

──────────────────────────────
■ ステップ5：毎週5分の点検（習慣にする）
──────────────────────────────
□ サブのツールを1回起動し、小さいタスクを1つ通す（放置すると壊れる）。
□ サブのモデルで「ビルド→テスト」が一周できるか確認する。
□ 今週の重要なやり取り・決定を .ai/notes/ に追記したか。
□ メインのルールに変更があったら、サブ側にも反映したか（symlink なら不要）。
□ APIキーの残高・期限が近くないか（BYOKを保険にしている場合）。

──────────────────────────────
■ よくあるつまずき
──────────────────────────────
・「サブを入れたのに一度も使わず、いざという時に動かなかった」
  → ステップ5を守る。使わない保険は保険にならない。
・「ルールをツール固有記法で書いていて、別ツールで読めない」
  → 共通ルールは素のMarkdownで。固有設定は別ファイルに隔離する。
・「APIキーをコミットしてしまった」
  → 直ちにキーを無効化して作り直す。.gitignore を先に設定しておく。
・「サブのモデルだと補完・自動化が使えない」
  → それは仕様。サブは「最低限、書いて・直して・テストできる」を基準に。
     全機能の再現を目指さない。
```

**ポイント**: 目的は「完全な二重化」ではなく「片方が止まっても手が止まらないこと」。サブ環境は軽くて構いません。いちばん大事なのはステップ5——使わない保険は、いざという時に動きません。
