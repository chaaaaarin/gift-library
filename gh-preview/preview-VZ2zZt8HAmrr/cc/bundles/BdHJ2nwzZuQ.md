# 🎁 使い分け判断シート＋沼脱出プロンプト30

「Skills・MCP・Plugin・CLI のどれで作るか」を5問で決める判断シートと、作る前・作っている最中・配った後のそれぞれで詰まったときに貼るプロンプト30本をまとめました。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 判断シートはそのまま読んで使ってください。プロンプトは、詰まっている状況に合うものをコピーして Claude Code に貼ってください。

## 使い分け判断シート

### 1. Skills / MCP / Plugin / CLI 使い分け判断シート

5問で「どれで作るか」が決まる判定シート。早見表と、よくある選び間違いつき。

```text
【Skills / MCP / Plugin / CLI 使い分け判断シート】

AIに何かをやらせたいとき、作る手段は4つあります。
選び間違えると「作ったのに使われない」「配れない」「重い」のどれかで詰まります。
上から順に5問だけ答えてください。1問目でYESなら、そこで決まりです。

■ ステップ1：そもそも作る必要があるか

□ 同じ指示を、これまでに3回以上コピペしているか
→ YES: 作る価値がある。ステップ2へ進む
→ NO: まだ作らない。会話の中で直接お願いするほうが速い

□ その作業の手順が、毎回同じ形に決まっているか
→ YES: ステップ2へ進む
→ NO: 手順が固まってから作る。今作ると作り直しになる

指示例: 直近1か月で同じ依頼を何回したか数えて。3回未満なら作らない判断でいいか一緒に考えて。

■ ステップ2：外の世界につなぐ必要があるか

□ 社外のサービス・データベース・APIから、その場のデータを取ってくる必要があるか
→ YES: MCPサーバーで作る。ステップ4へ進む
→ NO: 次の項目へ

□ 手元のファイルを読む・コマンドを打つだけで済むか
→ YES: Skills（SKILL.md）で足りる。ステップ3へ進む

□ すでにコマンドライン用のツールが存在するか（そのサービスの公式CLIなど）
→ YES: MCPを足さず、CLIを使う手順をSkillsに書くほうが軽い
→ 補足: MCPは接続するだけで説明文を読み込む。CLIで済むならCLIのほうがトークンを食わない

指示例: この作業に必要なデータの取得元を全部挙げて。手元のファイルだけで済むもの、外部サービスが要るものに分けて。

■ ステップ3：自分だけで使うか、人に配るか

□ 自分（または同じリポジトリを触る人）だけが使うか
→ YES: Skills のまま。プロジェクトの .claude/skills/ に置いて終わり

□ 別のパソコンの人に渡したいか
→ YES: 渡し方を決める必要がある。ステップ4へ進む

□ 渡した後、中身を更新する予定があるか
→ YES: ファイルで配ってはいけない。MCPでの配信を検討する。ステップ4へ進む
→ NO: zipやリポジトリで配ってもよい（更新しないなら版ズレも起きない）

指示例: このスキルを渡したい相手の人数と、今後の更新頻度を整理して。ファイル配布とサーバー配信のどちらが向くか判断材料を出して。

■ ステップ4：配る単位を決める

□ 配りたいのは「手順」だけか
→ YES: MCPサーバーでスキル本文を返す構成にする

□ 手順に加えて「つなぎ先の設定」も一緒に渡したいか
→ YES: Plugin（1つのパッケージにまとめる形）が向く
→ 注意: Claude Code は Agent Plugins の形式に未対応（2026年8月時点）。当面はMCPで配る

□ 相手ごとに配る内容を変えたいか
→ YES: MCPサーバーで、接続トークンごとに出し分ける

□ 誰が何を使ったかを記録したいか
→ YES: MCPサーバー一択。ファイル配布では記録が取れない

指示例: 配りたい中身を「手順」「つなぎ先の設定」「実行するコード」に分類して。どれが含まれるかで配布方式を判断して。

■ ステップ5：作る前に、やめる条件を決める

□ この仕組みを止めるときの手順を決めてあるか
→ YES: 着手してよい
→ NO: 先に決める。止め方が無い配布は、必ず後で困る

□ 秘密情報や社外秘が含まれるか
→ YES: 公開リポジトリ経由の配信は使わない。自前サーバーにする

□ うまくいかなかったときに、元に戻せるか
→ YES: 着手してよい
→ NO: 戻し方を先に用意する

指示例: この仕組みを1年後に止めるとしたら、何をどの順で止める必要があるか手順にして。


■ 早見表

　自分だけ・手元だけ　　　　　　→ Skills
　自分だけ・外部サービスあり　　→ MCP（自分用）
　人に配る・更新しない　　　　　→ Skills をリポジトリで共有
　人に配る・更新する　　　　　　→ MCP で配信
　人に配る・道具もセットで　　　→ Plugin（Claudeは未対応・当面はMCP）
　公式CLIが既にある　　　　　　→ CLI を使う手順を Skills に書く


■ よくある選び間違い

　配るのにファイルにした　　　　→ 更新のたびに全員へ連絡する羽目になる
　自分用なのにMCPにした　　　　→ 作るのも直すのも重い。Skillsで十分だった
　CLIがあるのにMCPを足した　　 → 接続しただけでトークンを消費する
　止め方を決めずに配った　　　　→ 対象外の人の手元に残り続ける
　説明文を曖昧にした　　　　　　→ 作ったのに一度も呼び出されない

```

## 作る前に詰まったとき

### 2. 何を作るべきか決まらない

アイデアはあるが、最初の1個が決まらないときに使う。

```text
前提: AIに任せたい作業がいくつかあるが、どれから手をつけるべきか決められない。
指示: 直近1か月で私が繰り返した作業を洗い出す質問を10個して。回答をもとに「繰り返し回数×1回あたりの時間×手順の固定度」で並べ替えて、最初に作るべき1つを推奨して。
出力形式: 質問→（回答後）並べ替えた表→推奨1つと、それを選んだ理由を3行で。
```

### 3. SkillsとMCPのどちらか決まらない

方式選びで止まっているときに使う。

```text
前提: 作りたいものは決まったが、SkillsとMCPのどちらで作るべきか判断できない。
指示: 私がやりたいことを聞いたうえで、「外部接続の有無」「配る相手の範囲」「更新の頻度」「利用記録の要否」の4点を確認して、方式を1つ推奨して。選ばなかった方式の弱点も必ず添えて。
出力形式: 4つの確認質問→（回答後）推奨方式・理由・選ばなかった方式の弱点。
```

### 4. 作る範囲が広がりすぎる

あれもこれも入れたくなって着手できないときに使う。

```text
前提: 作りたい機能を挙げていたら数が増えすぎて、いつまでも着手できない。
指示: 挙げた機能を「これが無いと成立しないもの」「あると便利なもの」「あとで足せるもの」の3つに仕分けして。1つ目だけで動く最小構成を提案し、残りは着手しない理由を1行ずつ添えて。
出力形式: 3分類の表と、最小構成の仕様（箇条書き5行以内）。
```

### 5. 誰に配るか決まっていない

「とりあえず作る」の前に、渡す相手を確定させる。

```text
前提: 作ろうとしているが、誰にどう渡すかを考えていなかった。
指示: 想定する受け取り手について、人数・所属（社内か社外か）・技術レベル・更新頻度の4点を質問して。回答をもとに、配布方式と必要な認証の有無を判断して。
出力形式: 4つの質問→（回答後）配布方式の推奨と、認証が必要かどうかの判断、その理由。
```

### 6. 既に似たものがあるか分からない

作る前に、車輪の再発明を避ける。

```text
前提: 作ろうとしている機能が、既存のツールやサービスで実現できる可能性がある。
指示: やりたいことを整理したうえで、既存の手段（公式CLI・既存のMCPサーバー・標準機能）で代替できないか調べて。代替できる場合は、それを使う手順を示して。
出力形式: 代替候補の一覧（名前・できること・できないこと）と、自作すべきかどうかの結論。
```

### 7. 止め方を決めていない

始める前に、終わらせ方を決めておく。

```text
前提: 仕組みを作ろうとしているが、将来止めるときのことを考えていない。
指示: この仕組みを1年後に止めると仮定して、止めるために必要な作業を洗い出して。データの扱い・利用者への告知・権限の削除・記録の保管期間まで含めて。
出力形式: 止める手順の一覧（順番つき）と、今のうちに用意しておくべきものを3つ。
```

### 8. 秘密情報の扱いが不安

配る前に、出してはいけないものを確認する。

```text
前提: 配布したい内容に、社外秘や個人情報が混ざっている可能性がある。
指示: 配布予定の内容を確認して、外に出せないものを分類して。分類は「絶対に出せない」「条件付きで出せる」「出しても問題ない」の3段階にし、判断が微妙なものは必ず要確認に分けて。
出力形式: 3分類の一覧と、条件付きのものについて満たすべき条件を1行ずつ。
```

### 9. 費用が読めない

始める前に、かかるお金の当たりをつける。

```text
前提: MCPサーバーを立てたいが、どれくらい費用がかかるか見当がつかない。
指示: 想定する利用人数・呼び出し頻度・データ量を質問したうえで、無料枠で足りるか、超えるならどの項目が効いてくるかを整理して。
出力形式: 質問→（回答後）無料枠で足りるかの判断、超える場合の主な要因、費用を抑える工夫を3つ。
```

## 作っている最中に詰まったとき

### 10. つながらない

接続エラーで止まったときに、最初に打つ1本。

```text
前提: MCPサーバーを登録したが、クライアントから接続できない。
指示: 「サーバーが起動しているか」「URLに直接アクセスして応答が返るか」「認証情報が渡っているか」「設定ファイルの記述」「クライアントの再起動が必要か」の順に、1つずつ確認する手順を出して。私に確認結果を聞きながら、次に見る場所を絞り込んで。
出力形式: 1手順ずつ提示し、私の返答を待ってから次へ進む形式で。まとめて全部出さないで。
```

### 11. つながったのに呼ばれない

接続は成功しているのに使われないときに使う。

```text
前提: MCPサーバーへの接続は成功しているが、AIがそれを使ってくれない。
指示: サーバー側の説明文（server instructionsとツールの説明）を読んで、どんな依頼文なら呼ばれそうかを5例挙げて。呼ばれない原因が説明文にある場合は、書き換え案を出して。
出力形式: 呼ばれそうな依頼文5例、現在の説明文の問題点、書き換え後の説明文。
```

### 12. スキルが意図しない場面で呼ばれる

誤爆するスキルの説明文を直す。

```text
前提: 作ったスキルが、関係ない場面でも呼び出されてしまう。
指示: 現在のdescriptionを読み、呼ばれてほしくない場面の依頼文を5つ生成して。それらと区別できるように、対象を絞り込んだdescriptionの書き換え案を出して。
出力形式: 誤爆しそうな依頼文5例、現在の説明文が広すぎる理由、書き換え案。
```

### 13. 重くなった

つないだ後にトークン消費が増えたときに使う。

```text
前提: MCPサーバーをつないでから、やりとりが重くなった気がする。
指示: 接続しているMCPサーバーの数と、それぞれのツール数・説明文の長さを確認して。ツール検索が有効になっているかも確認し、重さの原因になっている箇所を特定して。
出力形式: 現状の一覧（サーバー・ツール数・説明文の文字数）と、削減できる箇所を3つ。
```

### 14. 更新が反映されない

直したのに古い内容が返ってくるときに使う。

```text
前提: スキルの本文を直したのに、呼び出すと古い内容が返ってくる。
指示: キャッシュ・起動時読み込み・クライアント側の保持の3か所を切り分けて、どこで古い内容が保持されているか特定する手順を出して。特定できたら、その箇所で毎回読み直す実装への変更案を出して。
出力形式: 切り分け手順（実行するコマンド付き）と、原因ごとの修正案。
```

### 15. 認証で弾かれる

トークンを渡しているのに拒否されるときに使う。

```text
前提: 認証トークンを設定したはずだが、接続が拒否される。
指示: ヘッダの名前・値の形式・空白や改行の混入・トークンの有効期限・サーバー側の照合ロジックの5点を順に確認する手順を出して。秘密情報そのものは出力に含めないで。
出力形式: 確認手順を1つずつ提示し、私の返答を待って次へ進む形式で。
```

### 16. エラーの意味が分からない

見慣れないエラーで手が止まったときに使う。

```text
前提: エラーメッセージが出ているが、何を言っているのか分からない。
指示: エラーメッセージ全文を読み、「何をしようとして」「どこで」「なぜ」失敗したかを日本語で説明して。原因の候補を可能性の高い順に3つ挙げ、それぞれの確かめ方も添えて。
出力形式: エラーの意味の説明、原因候補3つ（可能性・確かめ方・対処）の表。
```

### 17. コードが長くなりすぎた

1ファイルが膨らんで手に負えなくなったときに使う。

```text
前提: MCPサーバーの実装が1ファイルに膨らみ、どこを直せばいいか分からなくなった。
指示: 現在のコードを読み、責務ごとに分割する案を出して。分割は「接続の受け口」「認証」「データ取得」「整形」の4つを基本にし、それぞれの行数の目安も添えて。
出力形式: 分割後のファイル構成図、各ファイルの責務、移す順番（1度に全部やらない手順）。
```

### 18. テストの書き方が分からない

動作確認を手作業でやり続けているときに使う。

```text
前提: MCPサーバーの動作確認を毎回手で行っていて、変更のたびに時間がかかる。
指示: このサーバーで最低限確認すべき項目を洗い出して。正常系・認証失敗・データ取得失敗・範囲外の要求の4つを軸に、自動で確認できるテストの書き方を示して。
出力形式: 確認項目の一覧、テストコードの実例、実行コマンド。
```

### 19. 秘密情報がコードに残っている

うっかり書き込んだ鍵を、正しく外に出す。

```text
前提: 開発中にAPIキーをコードに直接書いてしまい、そのままになっている。
指示: コード内の秘密情報らしき文字列を全て洗い出して。それぞれを環境変数に移す手順を示し、過去のコミット履歴に残っていないかの確認方法も添えて。値そのものは出力しないで。
出力形式: 検出箇所の一覧（行番号と種別のみ）、移行手順、履歴の確認方法、鍵の再発行が必要かの判断。
```

### 20. どこまで作ったか分からなくなった

中断から戻ってきたときに使う。

```text
前提: 作りかけで数日空けてしまい、どこまでできているか分からない。
指示: 現在のコードと変更履歴を読んで、実装済みの機能・未実装の機能・動作未確認の箇所を整理して。次にやるべき1つも推奨して。
出力形式: 3分類の一覧と、次にやること1つ（それを選んだ理由つき）。
```

### 21. 作り込みすぎて進まない

完璧を目指して止まっているときに使う。

```text
前提: 細部が気になって、いつまでも公開できずにいる。
指示: 現在の実装のうち、「無くても他人が使い始められる部分」を洗い出して。それらを後回しにして、今日中に1人に渡せる状態にするための最短手順を出して。
出力形式: 後回しにできる項目の一覧と、今日やることの手順（3ステップ以内）。
```

## 配った後に詰まったとき

### 22. 使われていない

配ったのに反応が無いときに使う。

```text
前提: スキルを配ったが、利用ログを見るとほとんど呼ばれていない。
指示: 「そもそも接続されていない」「接続はされているが呼ばれない」「呼ばれたが結果が使われていない」の3つを切り分ける方法を出して。切り分けた結果ごとに、次にやるべきことを提案して。
出力形式: 切り分け手順と、3つのケースそれぞれの対処案。
```

### 23. 受け取り側が設定でつまずく

「動きません」の問い合わせが続くときに使う。

```text
前提: 配布した相手から接続できないという連絡が繰り返し来る。
指示: 私が渡している手順書を読んで、前提知識が必要な箇所・環境によって変わる箇所・確認方法が書かれていない箇所を洗い出して。手順書の改訂案も出して。
出力形式: 問題箇所の一覧（該当行・なぜつまずくか）と、改訂後の手順書。
```

### 24. 更新を伝えたい

中身を直したことを、受け取り側に知らせる。

```text
前提: 配信中のスキルを大きく変更したので、使っている人に伝えたい。
指示: 変更内容を読んで、受け取る側の視点で「何が変わったか」「対応が必要か」を書いた告知文を作って。対応不要な変更は、そう明記して。
出力形式: 告知文（そのまま送れる形）と、対応が必要な人の条件。
```

### 25. 特定の人だけ止めたい

対象外になった人へのアクセスを切る。

```text
前提: 受講が終わった人がいるので、その人だけ配信を止めたい。
指示: 現在の認証方式を確認したうえで、特定の利用者だけを失効させる手順を出して。失効後にその人が接続したときに返すメッセージの文面も提案して。
出力形式: 失効の手順（コマンド付き）、失効後のメッセージ文面、失効漏れを防ぐ確認方法。
```

### 26. 内容が古くなった

配りっぱなしになった中身を点検する。

```text
前提: 配信しているスキルの中に、しばらく更新していないものがある。
指示: 配信中の各スキルの最終更新日と直近の利用回数を突き合わせて、「使われているのに古い」ものを優先度順に並べて。1つずつ、何を確認すべきかも添えて。
出力形式: 優先度順の一覧（スキル名・最終更新・利用回数・確認すべき点）。
```

### 27. 似たスキルが増えて選ばれない

スキルが増えすぎて呼び分けができないときに使う。

```text
前提: 配信しているスキルが増え、AIが正しいものを選べなくなってきた。
指示: 全スキルのdescriptionを読んで、説明が似ていて競合しているものの組み合わせを洗い出して。統合すべきものと、説明文を書き分けるべきものに分けて提案して。
出力形式: 競合の組み合わせ一覧、統合案、書き分け案（具体的な文面つき）。
```

### 28. 何を次に作るか分からない

利用ログを、次の一手につなげる。

