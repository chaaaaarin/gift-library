# 🎁 “同じ土俵”で比べる実測プロンプト10選（Fable 5.1 と GPT-6 Astra）

ベンチマークの勝ち負けではなく、**自分の環境で同じ仕事を両方に投げて、所要時間・トークン量・仕上がりを表で比べる**ための依頼文10本です。使うと、乗り換え・併用・様子見の判断が「なんとなく」ではなく自分の数字になります。Claude Code（Fable 5.1）と Codex（GPT-6 Astra）の両方に、同じものを貼って使ってください。

**受け取り方**: 下の各コードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: `＜　＞` の部分を自分の案件に置き換えて、Claude Code と Codex の両方に同じ文を貼ります。最後に必ず「比較表」を出させるので、2つの表を並べれば差が一目で分かります。1〜3はコード、4〜5は文章・資料、6〜7はパソコン操作、8〜10は長時間・コスト・理解の比較です。

## 1. 同じリファクタを投げて、差分・時間・トークンを表で出させる

```text
期待できるメリット: 「どっちが速く・安く・きれいにコードを直すか」を、体感ではなく表で比較できる。乗り換え判断の一番の材料になる。
使う場面: 手元のプロジェクトに、動きは変えずに整理したいファイルが1つ以上あるとき。
前提・状況: 対象ファイルを貼り付けられる、またはリポジトリ内でパスを指定できる。

指示: あなたはコード改善の担当です。これから渡すファイルに対して、外から見た動きを変えずに、読みやすく整理（リファクタ）してください。既存のテストがあれば壊さないでください。作業のあと、必ず次の表を1つ出してください。
  ・変更したファイルと関数の一覧
  ・かかった時間（体感でよい・分単位）
  ・処理したトークン量（入力／出力、分かる範囲で）
  ・テストが通ったか（Yes / No）。テストが無い場合は、最低限の動作確認手順を3行で
＜ここに対象ファイルの内容、またはリポジトリ内のパスを貼る＞

出力形式・制約: 説明は箇条書き。最後の比較表は「項目 | 値」の2列で。コードの全文再掲は不要、変更点だけ diff 形式で。
つまずきどころ: ファイルが大きすぎると片方が途中で要約に切り替わり条件が揃わなくなる。300行を超えるなら関数単位に絞って渡す。両方に「同じ範囲」を渡すことを徹底する。
```

## 2. 同じバグ修正タスクで、原因特定までの手数を比べる

```text
期待できるメリット: バグ調査を任せたときの「遠回りの少なさ」が分かる。長い調査で差が出やすいポイントを、小さめの再現ケースで先に確かめられる。
使う場面: 再現手順がはっきりしているバグが1つあるとき（クラッシュ、想定外の出力、無限ループなど）。
前提・状況: 再現手順と、期待する正しい挙動を言葉で書ける。関連ファイルを渡せる。

指示: 次のバグを修正してください。まず原因を特定し、最小の修正を当て、最後に再発防止の確認方法を示してください。作業ログとして、次を時系列で残してください。
  ・原因にたどり着くまでに確認したファイル・関数（順番に）
  ・試して外した仮説（あれば）
  ・最終的な修正内容（diff）
  ・かかった時間とトークン量（分かる範囲で）
＜ここにバグの再現手順・期待する挙動・関連ファイルを貼る＞

出力形式・制約: 「確認した箇所」は箇条書きで順番に。修正は diff 形式。憶測で複数箇所を同時に変えない。
つまずきどころ: 再現手順が曖昧だと両方とも探索範囲が広がって比較にならない。「この操作をすると、この出力になるはずが、こうなる」の形まで具体化してから渡す。
```

## 3. 同じ仕様書から実装させて、テストの手厚さを比べる

```text
期待できるメリット: 仕様を渡してゼロから実装させたとき、「どこまで自分でテストを書いて検証するか」の差が見える。品質の作り込みの傾向がつかめる。
使う場面: 小さめの新機能・ユーティリティを1つ、仕様から作らせたいとき。
前提・状況: 入力・出力・エッジケースを箇条書きにできる。言語とフレームワークを指定できる。

指示: 次の仕様を満たす実装を書いてください。実装と同時に、エッジケースを含むテストも書き、実行して結果を報告してください。最後に次を出してください。
  ・作成したファイル一覧
  ・書いたテストの件数と、カバーしたエッジケース
  ・テスト実行結果（成功／失敗の数）
  ・かかった時間とトークン量
＜ここに仕様（入力・出力・エッジケース・使用言語）を貼る＞

出力形式・制約: テストは実際に走る形で。仕様に無い機能を足さない。曖昧な点は「※こう解釈した」と明記してから進める。
つまずきどころ: 仕様が薄いと解釈がぶれて公平に比べられない。エッジケース（空入力・最大値・不正入力）を最低3つ、先に書いておく。
```

## 4. 同じ資料から下書きを作らせて、事実の拾い方を比べる

```text
期待できるメリット: 「調べ物をしながら文章にまとめる」総合力の差が、自分の題材で分かる。出典の追い方・推測の混ぜ方の傾向が見える。
使う場面: 手元の資料（記事・議事録・仕様）から、記事や説明文の下書きを作りたいとき。
前提・状況: 元資料を貼れる。誰向けに・どの長さで・何を伝えたいかを言葉にできる。

指示: これから渡す資料をもとに、＜誰向け＞に＜文字数／構成＞の下書きを書いてください。書いたあと、必ず次を報告してください。
  ・各段落が、資料のどの部分に基づくか（引用箇所を対応づける）
  ・資料に書いておらず、推測で補った部分（「※推測」と明記）
  ・かかった時間とトークン量
＜ここに元資料と、誰向け・長さ・目的を貼る＞

出力形式・制約: 下書き本文のあとに「根拠の対応表」を付ける。誇張表現・断定保証は使わない。数字は資料にあるものだけ。
つまずきどころ: 資料が長いと片方が要約モードに入って対応づけが雑になる。5000字を超えるなら章ごとに分けて、両方に同じ章を渡す。
```

## 5. 同じテンプレに沿わせて、体裁の追従を比べる

```text
期待できるメリット: OpenAI が「Astra はテンプレ追従が得意」と主張している点を、自分のテンプレで検証できる。資料作りをどちらに任せるか決められる。
使う場面: 決まった見出し構成・トーンのテンプレがあり、それに沿った資料を量産したいとき。
前提・状況: 見本のテンプレ（見出し・書式・語調のサンプル）を1つ貼れる。埋める中身の材料がある。

指示: 添付のテンプレA（見本）とまったく同じ見出し構成・書式・語調で、次の中身を埋めた資料Bを作ってください。作業後、次を報告してください。
  ・テンプレAと資料Bで、見出し・順序・書式が一致しているか（ずれた箇所を列挙）
  ・語調（です・ます／体言止め等）を揃えられたか
```

## 6. 同じブラウザ作業を投げて、止まった箇所と時間を比べる

```text
期待できるメリット: パソコン・ブラウザ操作を任せたときの「速さ」と「どこで詰まるか」が、自分の業務で分かる。Astra の速度主張を実地で確かめられる。
使う場面: 複数のページを回って情報を集め、表にまとめる定型作業があるとき（管理画面の棚卸し、価格調査など）。
前提・状況: 対象ページのURL（またはブックマーク）と、取得したい項目、まとめる形式を指定できる。ログインが必要な場合は自分でログイン済み。

指示: 次のブラウザ作業を実行してください。＜対象ページ＞を開き、＜取得する項目＞を集め、＜まとめる形式＞で出力してください。作業のあと、必ず次を報告してください。
  ・実際に開けたページと、取得できた項目
  ・途中で止まった箇所（ログイン要求・認証・要素が見つからない等）と、その対処
  ・かかった時間（実測）
＜ここに対象ページ・取得項目・出力形式を貼る＞

出力形式・制約: 結果は指定形式の表で。取得できなかった項目は空欄にして「取得不可：理由」を添える。勝手に別サイトへ行かない。
つまずきどころ: パスキー認証・2段階認証がある画面はどちらも止まる。そこは比較対象から外し、「認証前まで」で時間を測る。
```

## 7. 同じ画面から手順書を作らせて、正確さを比べる

```text
期待できるメリット: 画面を見て操作手順を書き起こす作業で、UIの読み取り精度の差が分かる。マニュアル作成をどちらに任せるか決められる。
使う場面: 社内ツールや管理画面の操作マニュアルを、画面を見ながら作りたいとき。
前提・状況: 対象の画面を開ける。ゴール（何を達成する手順か）を言葉にできる。

指示: ＜対象画面＞を開き、＜ゴール＞を達成するための操作手順を、初めての人が迷わない粒度で書き出してください。各ステップに「押す場所」「入力する値」「次に表示されるもの」を含めてください。作業後、次を報告してください。
  ・実際に画面で確認したステップ数
  ・推測で書いたステップ（あれば「※未確認」と明記）
  ・かかった時間
＜ここに対象画面と、達成したいゴールを貼る＞

出力形式・制約: 手順は番号付き。1ステップ1操作。専門用語には初出でカッコ書きの説明を付ける。
つまずきどころ: 画面の状態（ログイン後・特定タブ選択済みなど）を前提として書かないと、両方の出発点がずれる。開始状態を1行で固定してから渡す。
```

## 8. 半日級の1タスクを分割せず投げて、完走できるか比べる

```text
期待できるメリット: 「長い1タスクで途中の文脈が消えないか」を検証できる。Astra のノート保持が効くか、自分の作業で確かめられる。
使う場面: 本来なら分割したくなる大きめの作業（大規模リファクタ、複数ファイルにまたがる機能追加、長いデータ移行）を1本で任せたいとき。
前提・状況: 作業全体のゴールと、完了条件（どうなったら終わりか）を明文化できる。

指示: 次の大きめの作業を、分割せずに最後まで進めてください。作業中は、重要な判断・失敗した試み・前提の変更を「作業メモ」として残し続けてください。完了時に次を報告してください。
  ・作業メモ全文（時系列）
  ・途中でコンテキストが切り替わった回数と、そのとき失われた情報の有無
  ・完了条件を満たしたか（項目ごとに Yes / No）
  ・総所要時間とトークン量
＜ここに作業のゴールと完了条件を貼る＞

出力形式・制約: 作業メモは時系列の箇条書き。完了条件は最初に提示したものを1項目ずつ照合する。
つまずきどころ: 完了条件が曖昧だと「終わったこと」にされて比較にならない。チェックできる条件を5個以上、先に列挙する。
```

## 9. 同じ依頼を3回ずつ投げて、料金の実額を出す

```text
期待できるメリット: 「体感で高い／安い」ではなく、自分の典型作業1回あたりの実額が分かる。キャッシュ読み取りの差（$0.25 対 $1.00）が効く使い方かどうか判定できる。
使う場面: 定型的に繰り返す作業（毎朝の要約、定期レポート、決まったチェック）のコストを見積もりたいとき。
前提・状況: その作業でいつも渡している前提文（ルール・過去ログ・コード）を用意できる。料金明細やトークン使用量を確認できる。

指示: 次の作業を、同じ前提文を付けたまま3回連続で実行してください。毎回、次を記録してください。
  ・入力トークン（うちキャッシュから読まれた分）
  ・出力トークン
  ・1回あたりの概算料金（公開単価で計算）
3回分を平均し、「1回あたりの平均コスト」と「キャッシュが効いた割合」を表で出してください。
＜ここに、いつもの前提文と作業内容を貼る＞

出力形式・制約: 3回分＋平均の表。単価は「入力 $10 / 出力 $50 / キャッシュ読み取りは各モデルの公開値」で計算。
つまずきどころ: 1回目はキャッシュが無いので割高になる。2回目以降の平均で比べる。前提文を毎回1文字も変えないこと。
```

## 10. 既存コードベースを説明させて、理解の深さを比べる

```text
期待できるメリット: 引き継いだプロジェクトや久しぶりに触るコードで、「全体像をどれだけ正確に説明できるか」の差が分かる。調査の相棒としての実力が測れる。
使う場面: 中〜大規模のリポジトリを、これから触る前に把握したいとき。
前提・状況: リポジトリ全体を渡せる、またはディレクトリ構成と主要ファイルを指定できる。自分が「正しい」と分かっている事実をいくつか持っている（検算用）。

指示: このリポジトリの全体像を、次の観点で説明してください。①何をするアプリか ②主要なモジュールと役割 ③データの流れ（入口から出口まで）④テスト・ビルドの仕組み ⑤触るときに注意すべき箇所。説明後、次を報告してください。
  ・確信度が低い項目（「※要確認」と明記）
  ・参照したファイル数
  ・かかった時間とトークン量
＜ここにリポジトリ、またはディレクトリ構成と主要ファイルを貼る＞

出力形式・制約: 5観点それぞれ3〜5行。ファイルパスは実在するものだけ。推測は明示する。
つまずきどころ: 自分が答えを知っている質問（「認証はどこで処理してる？」など）を2〜3個まぜて、両方の説明の正確さを検算する。
```
