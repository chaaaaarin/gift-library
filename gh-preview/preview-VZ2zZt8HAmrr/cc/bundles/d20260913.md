## 1. いまのセッションで割引が効いているか、その場で確かめる

**期待できるメリット**: 「Fable 5.1 にしたのに、思ったほど安くなっていない気がする」を、感覚ではなく数字で切り分けられます。キャッシュ読み取りの割合が低い＝直す余地がある、と一目で分かります。
**使う場面**: Fable 5.1 に切り替えた初日、または月末の振り返り時。
**前提**: Claude Code で `/cost` が使えること（数分以上作業したセッションで実行する）。

```text
いまのセッションについて、次を1つの表にまとめて。
(1) 入力トークン・出力トークン・キャッシュ読み取りトークンの内訳
(2) キャッシュ読み取りが「入力トークン全体」の何%を占めているか
(3) その%を Fable 5 の旧価格と Fable 5.1 の新価格（キャッシュ読み取り $0.25/100万トークン）で
    計算したときの、このセッションのコスト差（概算。1ドル=155円で円換算も）
数字は /cost の値を根拠にして、推測が入る箇所は「推測」と明記して。
最後に、キャッシュ読み取りの割合が50%を下回っている場合だけ「改善余地あり」と書いて。
```

**出力形式・制約**: 表＋最後に1行の判定のみ。改善策の提案はここでは不要（別プロンプトで扱う）。
**つまずきどころ**: `/cost` の表記はバージョンで変わります。「キャッシュ読み取り」「cache read」「キャッシュヒット」など近い項目を拾うよう補足してください。

## 2. CLAUDE.md を「先頭固定・末尾可変」に組み替える

**期待できるメリット**: キャッシュは「文頭から変わっていないところ」までしか効きません。CLAUDE.md の中で毎回変わる部分を上に置いていると、その下の全文がキャッシュから外れます。並べ替えるだけで、キャッシュヒット率が上がり、同じ作業が安くなります。
**使う場面**: Fable 5.1 に切り替えた直後、いちど。
**前提**: プロジェクトに `CLAUDE.md` があること。

```text
このプロジェクトの CLAUDE.md を、キャッシュが効きやすい順序に組み替えて。
方針:
- 上から順に「めったに変わらない情報 → ときどき変わる情報 → 毎回変わる情報」に並べる
- めったに変わらない: プロジェクトの目的、技術スタック、命名規則、ディレクトリ構造、禁止事項
- ときどき変わる: 現在の作業ブランチの方針、未解決の課題
- 毎回変わる（あれば末尾へ、なければ削除）: 「今日やること」的なメモ、日付入りの記述
変更後の CLAUDE.md 全文と、「何を上に・何を下に動かしたか」の一覧を出して。
意味は一切変えないで、順序と見出しの整理だけして。
```

**出力形式・制約**: 全文＋移動一覧。内容の追記・削除はしない（毎回変わるメモの削除だけ可、その場合は明記）。
**つまずきどころ**: それでもキャッシュ率が上がらない場合は、CLAUDE.md ではなく、会話の最初に貼っている定型文や `.mcp.json` の順序が毎回ぶれている可能性があります。

## 3. 新規セッションの乱発をやめて、同じセッションを使い回す

**期待できるメリット**: セッションを開き直すたびに、CLAUDE.md も参照ファイルも「初めて読む」扱いになり、キャッシュがゼロから積み直しになります。1つのタスクは1セッションで通す運用にするだけで、キャッシュ読み取りの割合が上がります。
**使う場面**: 「こまめに新しいセッションを開く」癖がある人の運用見直し。
**前提**: 特になし。

```text
私は普段、少しでも話題が変わると Claude Code のセッションを開き直しています。
キャッシュ読み取りを効かせる観点から、次を教えて。
(1) 1セッションを長く使うことのコスト面のメリットを、キャッシュの仕組みから説明して
(2) 逆に「セッションを分けたほうがいい」のはどんなときか（コンテキストが汚れる/無関係な作業 等）
(3) 私の1日の作業を「朝の調査」「実装」「レビュー対応」の3つに分けた場合、
    セッションはいくつに分けるのが妥当か、理由つきで
日本語で、箇条書きで簡潔に。
```

**出力形式・制約**: 3項目の箇条書き。長文の解説は不要。
**つまずきどころ**: 長く使いすぎてコンテキストが膨らむと、今度は入力トークン自体が増えます。1タスク完了ごとに要点だけ残して整理する運用とセットにしてください。

## 4. 大きい参照ファイルを最初にまとめて読ませ、キャッシュに載せる

**期待できるメリット**: 作業の途中で「あのファイルも読んで」と小出しにすると、そのたびにキャッシュの区切りがずれます。最初にまとめて読ませておくと、以降のやり取りが安定して割引の効く状態になります。
**使う場面**: 特定のディレクトリやドキュメント一式を何度も参照する作業（仕様に沿った実装、既存コードの拡張）。
**前提**: 参照したいファイル・ディレクトリが決まっていること。

```text
これから <対象ディレクトリ or ファイル一覧> をベースに作業します。
まず、以下を「作業を始める前に」まとめて読み込んで、要点を1つのメモにして:
- <ファイルA>: 何のためのファイルか、主要な関数/型
- <ファイルB>: 〃
- <ディレクトリC>: 含まれるファイルの一覧と役割
このメモを起点に、以降の指示はこのメモとファイル内容を前提に進めて。
途中で追加のファイルが必要になったら、その都度「なぜ必要か」を一言添えてから読んで。
```

**出力形式・制約**: 最初に「読み込みメモ」を1つ作らせる。以降はそのメモを土台にする。
**つまずきどころ**: 読ませすぎるとキャッシュには載っても入力トークンが増えます。「この作業で確実に触る範囲」に絞ってください。

## 5. effort（考える強さ）を作業別に落とす

**期待できるメリット**: Fable 5.1 は Claude Code で既定の effort が最大（High）です。軽い作業までフルパワーで考えさせると、出力トークンとレイテンシが余計にかかります。作業に応じて下げると、体感速度が戻り、消費も減ります。
**使う場面**: 「Fable 5.1 にしたら少し重くなった気がする」と感じたとき。
**前提**: Claude Code で effort（reasoning effort / 思考の深さ）を切り替えられること。

```text
私の Claude Code の作業を、次の3つに分類して、それぞれ推奨の effort（Low / Medium / High）を教えて。
理由も1行ずつ。
A. 定型作業: フォーマット修正、命名の統一、コメント追加、簡単なバグ修正
B. ふつうの実装: 機能追加、テスト作成、リファクタ（範囲が明確なもの）
C. 難所: 原因不明のバグ調査、設計判断、広範囲に影響する変更
そのうえで、「作業を始めるときに effort を宣言する」ための短い定型文を3パターン作って。
```

**出力形式・制約**: 分類ごとの推奨＋理由1行＋宣言用の定型文3つ。
**つまずきどころ**: 難所（C）で effort を下げると、かえって手戻りが増えて総コストが上がります。下げるのは A・B だけにしてください。

## 6. 9月14日より前に、重い一括作業を棚卸しする

**期待できるメリット**: 9月14日から週の使用量は実質約17%減ります。いまの一時的な+50%枠のうちに、重い作業を消化しておけば、制限変更の影響を受けにくくなります。何を前倒しすべきかを、先にリスト化できます。
**使う場面**: いま（施行前）。
**前提**: プロジェクトに溜まっている「やりたいけど大きい」タスクがあること。

```text
このリポジトリで「いつかやりたいが、範囲が大きい・時間がかかる」作業を洗い出して。
候補: 広範囲のリファクタ、依存ライブラリの一括更新、テストの穴埋め、ドキュメント総ざらい、
      型の厳格化、デッドコード削除、パフォーマンス調査 など。
それぞれ「ざっくりの規模（S/M/L）」「一度に走らせられるか、分割が必要か」を付けて表にして。
最後に、9月14日までに前倒しで着手すべき順に3件だけ選んで、理由を書いて。
```

**出力形式・制約**: 表＋前倒し推奨トップ3。実際の着手はここではしない。
**つまずきどころ**: 「前倒し」を口実に、要らない作業まで増やさないこと。トップ3以外は据え置きでかまいません。

## 7. 週次レポート自動化のプロンプトを「キャッシュ前提」に書き換える

**期待できるメリット**: 毎週まわす自動化ほど、キャッシュが効くかどうかで年間コストが変わります。固定の指示・テンプレを毎回同じ順で先頭に置く形に直すと、2回目以降が安くなります。
**使う場面**: 定期実行しているレポート生成・集計・要約のプロンプトを持っている人。
**前提**: 既存の定期プロンプト（またはスキル）があること。

```text
次の定期実行プロンプトを、キャッシュ読み取りが効きやすい構造に書き換えて。
<ここに既存のプロンプト全文を貼る>
方針:
- 毎回変わらない部分（役割設定・出力フォーマット・判定ルール・用語定義）を「前半」に固めてまとめる
- 毎回変わる部分（対象期間・今回のデータ・今回だけの注意）を「後半」に集める
- 前半と後半の境目に「--- ここから今回分 ---」の区切りを1行入れる
書き換え後の全文と、「前半に動かしたもの／後半に残したもの」の一覧を出して。
処理内容は一切変えないで。
```

**出力形式・制約**: 全文＋前半・後半の振り分け一覧。ロジックは不変。
**つまずきどころ**: スキル（SKILL.md）として持っている場合は、本文の順序だけでなく、読み込む参照ファイルの順序も固定してください。

## 8. サブエージェント・並列実行のコストを事前に見積もる

**期待できるメリット**: 並列でエージェントを走らせると速い一方、それぞれが別々にコンテキストを積むため、キャッシュが分散して割引が効きにくくなります。走らせる前に「本当に並列が得か」を見積もれます。
**使う場面**: サブエージェントや並列タスクを使おうとしているとき。
**前提**: 分割したいタスクの内容が決まっていること。

```text
これから <タスク概要> を、サブエージェントを N 個に分けて並列で進めようとしています。
次を見積もって:
(1) 各エージェントが読む共通のコンテキスト（CLAUDE.md、共通の参照ファイル）はどれくらいか
(2) それを N 個ぶん別々に読むことで、直列で1エージェントが回す場合と比べて
    入力トークンがどれくらい増えるか（概算）
(3) その増加ぶんのコストと、短縮できる時間を天秤にかけて、並列にすべきか直列にすべきか
数字は概算でよいので、判断材料として表にして。
```

**出力形式・制約**: 見積もり表＋「並列 / 直列」の推奨1行。
**つまずきどころ**: 共通コンテキストが小さいタスク（各自が独立したファイルを触るだけ）なら、並列でも割引の損は小さいです。損が出るのは「全員が同じ大きい仕様書を読む」ケースです。

## 9. Astra（Codex）と同条件で1タスクだけ比較する

**期待できるメリット**: Fable 5.1 と GPT-6 Astra は API 標準価格が同じ（入力$10 / 出力$50）です。値段で差がつかない以上、「自分の作業でどちらが手戻りが少ないか」を1回 実測すると、乗り換え・併用の判断ができます。
**使う場面**: API プロジェクトを持っていて、モデル選定を見直したいとき。
**前提**: 同じタスクを両方の環境で回せること（Claude Code と Codex CLI の両方が使える、など）。

```text
これから同じタスクを Fable 5.1（Claude Code）と GPT-6 Astra（Codex）の両方で回します。
比較の観点を、事前にチェックリストにして:
- 完了までにかかった時間 / やり取りの往復回数
- 一発で通ったか、何回 直しを指示したか（手戻りの回数）
- 出力コードのレビューのしやすさ（差分の読みやすさ、説明の分かりやすさ）
- 途中で安全チェックや確認で止まった回数
- 概算コスト（トークン使用量から）
両方を回し終えたら、この観点で並べた比較表と「このタスク系ではどちらが向くか」の結論を出して。
```

**出力形式・制約**: 事前チェックリスト → 実行 → 比較表 → 結論1行。1タスクで判断せず、数回ぶん貯めるのが理想。
**つまずきどころ**: 1回の結果だけで乗り換えを決めないこと。タスクの種類（調査寄り/実装寄り）で向き不向きが変わります。

## 10. 月末に「旧価格 vs 新価格」で差額を振り返る

**期待できるメリット**: 「なんとなく安くなった気がする」を、月次の実額で確定できます。差が小さければ、1〜9 のどこに伸びしろがあるかも見えます。
**使う場面**: 月末、または Fable 5.1 に切り替えて1か月経ったとき。
**前提**: その月のトークン使用量（`/usage` や管理画面の集計）が取れること。

```text
この1か月の Claude Code / API の使用量について、次を計算して:
(1) 入力・出力・キャッシュ読み取りの合計トークン（分かる範囲で）
(2) Fable 5 の旧価格で計算した場合の月額（キャッシュ読み取りの旧単価で）
(3) Fable 5.1 の新価格で計算した場合の月額（キャッシュ読み取り $0.25/100万トークン）
(4) 差額と削減率（%）
(5) 削減率が20%未満だった場合、キャッシュ読み取りの割合を上げる余地がどこにあるか、
    このキットの項目番号（1〜9）で示して
金額は1ドル=155円で円換算も併記して。推測が入る箇所は明記して。
```

**出力形式・制約**: 計算表＋削減率＋（20%未満なら）改善ポイントの項目番号。
**つまずきどころ**: 定額プラン（Pro / Max）の人は、そもそも請求額が変わりません。この振り返りは従量課金・企業プランの人向けです。定額の人は「同じ枠で回せた作業量」で効果を測ってください。

---

**ポイント**: どのプロンプトも、出てきた数字はあくまで概算です。乗り換えや設定変更の最終判断は、`/usage`・`/cost` の実測を数回ぶん貯めてから行ってください。
