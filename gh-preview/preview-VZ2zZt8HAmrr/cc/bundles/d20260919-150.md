# 🎁 Astra 初期設定シート：請求を下げる7項目

GPT-6 Astra を「重い既定設定のまま」使うのをやめ、公式が言う低コスト側へ寄せるための初期設定を1枚にまとめたチェックリスト。上から順に7項目を反映すれば、動画で解説した「1回の直し」が5〜10分で終わり、以降のリクエストで払わなくていい推論トークン・出力トークン・再課金を止められます。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 上から順に「■ ステップ」を1つずつ確認し、`→ YES:` の行の設定を、使っているAPI／Codex／ChatGPT のどれかに反映します。反映が終わったら「□」を潰していってください。全部潰し終われば初期設定は完了です。

```text
【Astra 初期設定シート：請求を下げる7項目】

■ ステップ1：推論の強さ（reasoning effort）を low 基準にする
□ 今の既定 effort は何になっている？（未指定なら medium で動いている）
  → YES（medium 以上だった）: 既定を low に下げる。難しいタスクだけ後述のステップ5で一時的に上げる
  → 補足: Astra は none 非対応（設定すると HTTP 400）。下限は low
  指示例（Responses API）: reasoning={"effort": "low"}
  指示例（Codex config.toml）: model_reasoning_effort = "low"
  指示例（ChatGPT）: モデル／reasoning のメニューで一番低い設定を選ぶ

■ ステップ2：返答の長さ（verbosity）を low にする
□ 出力が毎回、前置き・言い訳・繰り返しで長くなっていないか？
  → YES: verbosity を low にする。思考の深さ（effort）は変わらず、最終回答だけ短くなる
  指示例（Responses API）: text={"verbosity": "low"}
  指示例（Codex config.toml）: model_verbosity = "low"
  つまずきどころ: 説明が必要なタスク（教材・引き継ぎ）まで low にすると情報が足りなくなる。その用途は medium に戻す

■ ステップ3：プロンプトの並び順を直してキャッシュを効かせる
□ システム指示・ツール定義・参照資料など「毎回変わらない部分」は先頭にまとまっているか？
□ ユーザー固有の入力・その日の指示など「毎回変わる部分」は後ろにあるか？
  → NO（可変が前に混ざっている）: 変わらない部分を全部先頭へ、変わる部分を末尾へ並べ替える
  → 効果: 1,024 トークン以上で自動的にキャッシュが効き、再利用ぶんは 0.1倍（9割引・$10→$1）
  つまずきどころ: 可変な値（日付・ユーザー名など）を先頭付近に置くとキャッシュが毎回壊れて全額課金に戻る

■ ステップ4：Fast mode をオフにする
□ Fast mode（高速モード）が有効になっていないか？
  → YES（ON だった）: 標準に戻す。Fast mode は速度2倍だが価格も2倍（ChatGPT では枠の消費も増える）
  → 例外: 「速さそのものが成果になる」作業のときだけ一時的に ON
  指示例（Codex）: features.fast_mode の扱いを確認し、通常は Fast コマンドを使わない

■ ステップ5：max_output_tokens に「切れない」上限を張る
□ 1リクエストで生成されるトークン量に上限を設定しているか？
  → NO: max_output_tokens を設定する。推論トークン＋見える出力＋整形ぶんの合計に上限がかかる
  → 目安: 試し始めは「推論＋出力に最低 25,000 トークン」を確保。慣れたら実測に合わせて調整
  つまずきどころ: 小さくしすぎると status が incomplete で途中終了する。そのとき入力ぶんと推論ぶんは課金済みなので、余裕をもった値にする
  確認方法: レスポンスの usage.output_tokens_details.reasoning_tokens で実際の推論トークン量を毎回見る

■ ステップ6：難所だけ configuration_update で一時的に上げる型を用意する（Astra 限定）
□ 会話の中で「ここだけは深く考えてほしい」1問があるか？
  → YES: その1問の直前に configuration_update を1つ差し込み、その応答だけ high にする。次の更新まで high が続くので、戻したいときはもう一度 low の configuration_update を置く
  指示例: {"type": "configuration_update", "reasoning": {"effort": "high"}}
  つまずきどころ: 自動コンパクション／自動打ち切りと併用不可。configuration_update を2つ隣接して置くのも不可

■ ステップ7：Codex はメモ保持モードにする／急がない処理は Batch へ
□ Codex で長時間セッションを組み、コンパクション（履歴の要約圧縮）が何度も走っていないか？
  → YES: config.toml でメモ保持モードを有効化する。要約に圧縮せず、メモと検索可能な履歴で詳細を保つ
  指示例（config.toml）: [features.context_management] の下に experimental_mode = true
  → 補足: ChatGPT サインイン（Plus / Pro / Pro Lite）が必要。実験扱いで「数週間で既定化」予定
□ eval・分類・大量データ処理など「今すぐ返事が要らない処理」はあるか？
  → YES: Batch API に回す。標準レートの50%（入力 $5 / 出力 $25）、24時間以内に完了

──────────────────────────────
反映後の確認：
・簡単な質問を1つ投げて、usage の reasoning_tokens と total_tokens をメモする
・同じ質問を「以前の設定」でも試し、差を見る
・難タスクで品質が落ちたら、そのタスクだけステップ6で effort を上げる（全体は low のまま）
```

**ポイント**: 節約の目的は「安く済ませる」であって「安い設定で回す」ことではありません。難タスクまで low で回して失敗すると、作り直しで入力＋推論ぶんを二重に払うことになります。既定は low、難所だけ上げる——この形が結局いちばん安く付きます。

# 🎁 「会話は low・ここだけ high」configuration_update スニペット集

GPT-6 Astra 限定の `configuration_update` を、そのまま貼って動く形でまとめたコード集。会話全体は安い `low` で回し、失敗が許されない1問だけ一時的に `high` へ上げる——この型を最初から持っておくと、effort を上げっぱなしにして推論トークンを浪費する事故がなくなります。Responses API 版・Codex 版・戻し方・失敗パターンまで入っています。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 使っている言語・環境に合うブロックを丸ごとコピーし、`input` の中身とモデル ID を自分のコードに合わせて差し替えます。`configuration_update` は「次のユーザーメッセージの前」に置くのがルールです。

```text
================================================================
1) Responses API（Python）：会話は low、この1問だけ high
================================================================
from openai import OpenAI
client = OpenAI()
MODEL = "gpt-6-astra"

# 1手目：軽い依頼は low のまま
first = client.responses.create(
    model=MODEL,
    reasoning={"effort": "low"},
    text={"verbosity": "low"},
    input="このマイグレーション計画をざっと確認して。",
    store=True,
)
print(first.output_text)

# 2手目：ここだけ深く考えさせたい → configuration_update を差し込む
second = client.responses.create(
    model=MODEL,
    previous_response_id=first.id,
    reasoning={"effort": "low"},          # リクエスト側は low のまま据え置く（キャッシュ維持のため）
    input=[
        {"type": "configuration_update", "reasoning": {"effort": "high"}},
        {"role": "user",
         "content": "失敗しうる箇所を洗い出し、ロールバック手順まで具体化して。"},
    ],
    store=True,
)
print(second.output_text)

# 3手目：難所が終わったら low に戻す（戻さないと high が続く）
third = client.responses.create(
    model=MODEL,
    previous_response_id=second.id,
    reasoning={"effort": "low"},
    input=[
        {"type": "configuration_update", "reasoning": {"effort": "low"}},
        {"role": "user", "content": "では手順書のドラフトにまとめて。"},
    ],
    store=True,
)
print(third.output_text)


================================================================
2) Responses API（curl）：最小形
================================================================
curl https://api.openai.com/v1/responses \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -d '{
    "model": "gpt-6-astra",
    "previous_response_id": "resp_xxx",
    "reasoning": { "effort": "low" },
    "input": [
      { "type": "configuration_update", "reasoning": { "effort": "high" } },
      { "role": "user", "content": "この設計のボトルネックと対策を挙げて。" }
    ]
  }'


================================================================
3) store=false（履歴を自前で持つ）で使う場合
================================================================
# configuration_update は「元の位置」に置いたまま履歴を再生する。
history = [{"role": "user", "content": "リポジトリを見て、あやしいバグを指摘して。"}]

r1 = client.responses.create(model=MODEL, store=False,
        reasoning={"effort": "low"}, input=history)
history.extend(item.model_dump() for item in r1.output)   # 出力を全部残す

history.append({"type": "configuration_update", "reasoning": {"effort": "high"}})
history.append({"role": "user", "content": "根本原因を特定して、修正案を出して。"})

r2 = client.responses.create(model=MODEL, store=False,
        reasoning={"effort": "low"}, input=history)
print(r2.output_text)


================================================================
4) Codex（config.toml）：既定を絞る＋難所はセッション内で上げ下げ
================================================================
# ~/.codex/config.toml  （これが「重い既定」を止める1回の直し。API を叩かない人はここだけでよい）
model = "gpt-6-astra"
model_reasoning_effort = "low"       # 既定は low（minimal|low|medium|high|xhigh）
model_verbosity = "low"              # 返答を短く（説明が要る作業だけ medium に戻す）
model_reasoning_summary = "concise"  # 推論サマリを短縮（auto|concise|detailed|none）
# model_auto_compact_token_limit = 200000   # 自動コンパクションの発火しきい値（メモ保持に主導権を渡すなら上げる/外す）

[features.context_management]
experimental_mode = true             # メモ保持モード（要 ChatGPT サインイン・実験扱い・数週間で既定化予定）

# ── セッション内での effort 上げ下げ運用（config は既定値。都度の調整はセッション側で）──
# 会話ぜんたいは low のまま進める。
#   1. 難所に来たら  /model  → reasoning effort を high（必要なら xhigh）に切り替える
#   2. その1問（設計の詰め・根本原因の特定・こわい変更のレビュー）だけ high で通す
#   3. 片づいたら すぐ  /model  で low に戻す（戻し忘れると以降ずっと high で課金される）
# hide_agent_reasoning = true は「画面に推論を出さない」だけ。API/枠の課金は減らないので節約目的で入れない。


================================================================
5) やってはいけない（公式が明記している制約）
================================================================
NG-1: configuration_update を2つ隣接して置く
      [{"type":"configuration_update",...}, {"type":"configuration_update",...}]  ← APIが拒否

NG-2: 自動コンパクション／自動打ち切りと併用する
      configuration_update を含む履歴は /responses/compact でも拒否される。
      明示的に compaction_trigger で圧縮したあとは、
      改めて configuration_update を「次のユーザーメッセージの前」に置き直す。

NG-3: GPT-6 Astra 以外で使う
      configuration_update は Astra（standard・single-agent モード）専用。
      他モデルでは無視されるか、エラーになる。

NG-4: リクエスト側の reasoning.effort を high に書き換えて済ませる
      それだと会話全体が high になり、プロンプト接頭辞も変わってキャッシュが外れる。
      リクエスト側は low のまま、configuration_update で「その応答だけ」上げるのが要点。
```

**ポイント**: `configuration_update` の一番の価値は「リクエストレベルの設定を変えないまま」効きを上げられることです。だからプロンプトの先頭部分が保たれ、9割引のプロンプトキャッシュが効いたまま難所だけ深く考えさせられます。`high` にしたら、難所が終わり次第 `low` の `configuration_update` で戻すのを忘れずに。
