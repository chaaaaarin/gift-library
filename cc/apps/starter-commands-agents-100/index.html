001計画・設計
ここまでの会話で話した「作りたいもの」を、実装に入る前の計画書として整理して。

含める項目:
- 誰が使うのか（自分だけ／社内／外の人）
- いちばん困っている作業は何か（具体的な頻度・件数つきで）
- 最初の完成をどこに置くか（1機能だけのMVPの範囲を明記）
- 手元の環境（OS・メモリ・追加課金の可否）

計画を出したら、不明な点があれば質問して。情報が足りないうちは、あなたの推奨案を添えて。
002実装
今日の作業は「{機能名}」の実装だけに絞る。

他の未着手の機能やTODOには触れず、この1機能が単体で動く状態にすることだけを目標にして。
実装が終わったら、他に何を実装すべきかの提案はせず、まず動作確認のやり方だけ教えて。
003テスト
「{機能名}」を実装する前に、最低限これだけは確認すべきというテスト観点を
5〜8個の箇条書きで出して。正常系だけでなく、入力が空・上限を超える・二重送信などの
異常系も含めて、優先度順に並べて。
004レビュー・品質
ここまでで動いている「{機能名}」のコードを、公開する前提で点検して。

観点は3つだけ: (1)明らかなセキュリティの穴 (2)エラーで画面が真っ白になる箇所
(3)このまま残すと将来困る仮のコード。指摘は優先度つきで、直す価値が低いものは
「今は保留でよい」とはっきり伝えて。
005デバッグ
「{症状}」が何度も直しても再発する。表面的な対処ではなく、根本原因を
突き止めるところから始めて。

これまで試した対処があれば教えるので、それも踏まえたうえで、
「なぜ直しても再発するのか」の仮説を複数出し、検証手順を示して。
006リファクタリング
「{機能名}」のコードは動いているが、見た目が汚くなってきた。動作を一切変えずに、
読みやすく整理して。

整理が終わったら、変更前と変わっていないことを確認するための簡単な動作確認手順も
合わせて教えて。
007ドキュメント
ここまでの会話で決まった、このプロジェクト固有のルール・前提知識をCLAUDE.mdとして
まとめて。

含める項目: プロジェクトの目的（1〜2文）／よく使うコマンド／ディレクトリ構成／
毎回説明し直すのが面倒な前提知識。新しいセッションで初めて読む人にも伝わる書き方にして。
008Git・PR
ここまでの変更内容を確認して、分かりやすいコミットメッセージを作って。

1行目は変更内容の要約、必要であれば2行目以降に理由を書いて。
「fix」「update」だけのような曖昧な表現は避けて。
009デプロイ・公開
「{アプリ名}」を{Vercel等のサービス名}にデプロイする前の確認をして。

確認項目: 環境変数（鍵）がコードに直書きされていないか／無料枠の利用条件（個人・非商用等）に
違反していないか／ビルドが通るか。問題があれば、デプロイを止めるレベルかどうかも教えて。
010セキュリティ
プロジェクト全体を確認して、APIキー・パスワードなどの鍵情報が
コードやログに直書きされていないか調べて。

見つかった場合は、環境変数など安全な扱いに直す方法を教えて。
すでに公開リポジトリにpush済みの場合は、鍵の再発行が必要な旨も伝えて。
011パフォーマンス
「{アプリ名}」を開いてから最初の画面が表示されるまでが遅く感じる。
体感速度を改善する方法を、優先度順に3つまで提案して。

専門的な最適化理論ではなく、「何をどう変えると、体感でどれくらい速くなるか」を
分かる言葉で説明して。
012学習・振り返り
今日の作業内容を、次に開いたときすぐ再開できるように記録して。

含める項目: 今日やったこと／今つまずいている点／次にやること。
CLAUDE.mdか別のメモに残すか、こちらで選べるように両方の案を出して。

# 🎁 個人開発スターターキット（スラッシュコマンド60＋サブエージェント40）
Claude Codeで個人開発を進めるときに、そのまま `.claude/` に置いて使えるスラッシュコマンドとサブエージェントの定義集です。
**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。
**使い方**: コマンドは `.claude/commands/<名前>.md`、サブエージェントは `.claude/agents/<名前>.md` に保存してください（個人用は `~/.claude/commands/` `~/.claude/agents/`）。`{}` で囲んだ部分は自分の状況に置き換えてください。
---
## スラッシュコマンド60本

### 計画・設計

**1. /kick-off** — 作りたいものを話しただけの状態から、実装前の計画書に整える
保存先: `.claude/commands/kick-off.md`
```text
ここまでの会話で話した「作りたいもの」を、実装に入る前の計画書として整理して。

含める項目:
- 誰が使うのか（自分だけ／社内／外の人）
- いちばん困っている作業は何か（具体的な頻度・件数つきで）
- 最初の完成をどこに置くか（1機能だけのMVPの範囲を明記）
- 手元の環境（OS・メモリ・追加課金の可否）

計画を出したら、不明な点があれば質問して。情報が足りないうちは、あなたの推奨案を添えて。
```

**2. /similar-service** — 似ているサービスを名前で挙げて、仕組みごと仕様書にする
保存先: `.claude/commands/similar-service.md`
```text
「{サービス名}のようなものを自分用に作りたい」と伝えたときに使う。

{サービス名}が何を解決していて、どんな画面構成・データの持ち方をしているかを調べたうえで、
自分の用途に合わせた縮小版の設計案を出して。有料サービスでも、真似したい部分だけを言葉で説明する形にして、
著作権・利用規約に触れる要素（ロゴ・デザインの丸ごと模写等）は含めないで。
```

**3. /mvp-cut** — 盛りすぎた計画を、機能1つだけのMVPに削る
保存先: `.claude/commands/mvp-cut.md`
```text
直前に出した実装計画は、ほぼ確実に盛りすぎている前提で、まず動くものを最優先にした
「機能1つだけ」のMVP版に削り直して。

削るときの基準:
- 通知・共有・権限管理など「無くても最初の1回は動く」機能は全部後回し
- 残す1機能は、いちばん頻度の高い作業に直結するものを選ぶ
- 削った機能は「本縫い（Stage3）でどの順番に足すか」のリストとして別に残して
```

**4. /env-check** — 作業前に自分の環境を伝えて、動く構成を選んでもらう
保存先: `.claude/commands/env-check.md`
```text
実装に入る前に、次の環境情報を踏まえて、この環境で確実に動く技術構成を提案して。

OS: {Windows / Mac}
メモリ・空き容量: {具体的な数値}
追加課金の可否: {可 / 不可}
ローカルでAIモデルを動かす予定の有無: {あり / なし}

環境に合わない技術（例: メモリ不足でローカルLLMが動かない）を前提にした提案を避け、
代替案がある場合は理由つきで教えて。
```

**5. /second-check** — 1回目の回答を、もう一度最新情報で調べ直させる
保存先: `.claude/commands/second-check.md`
```text
直前の提案について、抜け漏れがないか、もう一度最新の情報を調べ直して。

特に確認してほしいこと:
- 使おうとしているライブラリ・APIに、より新しい代替や非推奨化の情報が出ていないか
- 料金・利用条件が変わっていないか
- 1回目の提案になかった選択肢が他にないか

調べ直した結果、1回目と違う結論になった場合は、何がどう変わったかを明記して。
```

保存先: `.claude/commands/talk-to-build.md`
```text
今から話す内容は、思いついたままの前提・背景・愚痴まじりの説明です。
まとめようとせず、そのまま受け取ったうえで、実装方針に変換して。

変換するときは、話の中の「余分な情報」（なぜそれが必要になったかの背景）も
```

**8. /hand-off-screen** — ブラウザの画面をそのまま渡して、その通りに直させる

```text
この画面の状態を見て、「{困っている見た目・挙動}」を直して。

何を確認すればよいか具体的に聞き返して。文章で症状を書き起こす必要はない。
```

**9. /raw-error** — エラーメッセージを丸ごと渡すだけで原因を切り分けさせる
保存先: `.claude/commands/raw-error.md`
```text
次のエラーをそのまま渡す。読み解く必要はなく、原因の切り分けと対処だけ教えて。

```
{エラーメッセージをそのまま貼る}
```

対処が複数考えられる場合は、可能性が高い順に並べて、どれから試すべきか教えて。
```

**10. /side-question** — 本筋を汚さずに、知らない用語だけ別会話で聞く
保存先: `.claude/commands/side-question.md`
```text
本筋の実装作業とは別に、この一言だけ答えて。

「{知らない用語}」とは何か。今回の実装文脈でどう関係するかも含めて、
専門知識がなくても分かるように短く教えて。この質問への回答は、本筋の会話には持ち込まないで。
```

```text
「{機能名}」の動作確認を自分の手でやるための手順を、番号つきで出して。
```

```text
ここまでで動いている「{機能名}」のコードを、公開する前提で点検して。

観点は3つだけ: (1)明らかなセキュリティの穴 (2)エラーで画面が真っ白になる箇所
```

**17. /split-review** — 見た目の改善と不具合の洗い出しを、別担当に同時に頼む
保存先: `.claude/commands/split-review.md`
```text
次の2つの作業を、別々の担当として同時に進めて。同じ場所を同時に書き換えないよう、
担当ごとに触る範囲を分けて。

担当A: 見た目の改善（{対象画面}のレイアウト・配色の見直し）
担当B: 不具合の洗い出し（{対象機能}を一通り触って、動かない箇所をリスト化）

両方終わったら、変更点をまとめて報告して。
```

**18. /naming-check** — 変数名・画面の文言が分かりにくくないか点検させる
保存先: `.claude/commands/naming-check.md`
```text

迷わないかという観点だけで点検して。

技術的な良し悪しではなく「言葉として伝わるか」に絞って、直したほうがよい箇所を

```

**19. /simplify-me** — 複雑になった実装を、今の目的に合わせて削る
保存先: `.claude/commands/simplify-me.md`
