# 🎁 まず1つだけ判定シート＋沼脱出プロンプト50
盛りすぎた要件を機能1つに削るための判定シートと、実装中に詰まったときにそのまま貼れる指示文50本です。
**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。
**使い方**: 判定シートは計画が出た直後に、沼脱出プロンプトは詰まった場面に応じて選んで貼ってください。`{}` の部分は自分の状況に置き換えてください。
---
## まず1つだけ判定シート
```text
【まず1つだけ判定シート】

■ ステップ1：今の計画を確認する
□ 返ってきた実装計画に、機能が3つ以上並んでいる
□ 「あったら嬉しい」機能（通知・共有・複数人対応等）が最初から入っている
→ YES: ステップ2へ進む
→ NO: そのまま着手してよい

■ ステップ2：一番効く1機能を選ぶ
□ 「これが無いと、そもそも最初の1回すら試せない」機能はどれか1つに絞れる
→ YES: その1機能だけを残し、他は「後回しリスト」に移す
指示例: 「まず動くものを作りたい。最初はもっと小さくていい。{選んだ1機能}だけに絞って計画を立て直して」

■ ステップ3：後回しリストを退避する
□ 削った機能を、忘れないようメモとして残せている
→ YES: ステップ4へ
→ NO: 「削った機能を、後で足す順番つきのリストにして」と伝える

■ ステップ4：1機能が動いたら判定する
□ その1機能を、自分で3回以上使ってみた
□ 使うたびに「便利」「また使いたい」と感じた
→ YES: ステップ5（次の1機能を後回しリストから選ぶ）へ
→ NO: 題材そのものを見直す（1章の「毎回だるい作業」に立ち返る）

■ ステップ5：足す機能を選ぶ基準
□ 次に足す機能は「使うたびに困ること」から選べている
□ 一度に2つ以上の機能を同時に足そうとしていない
→ YES: 1つずつ足して、都度ステップ4を繰り返す
指示例: 「動いているものは変えずに、{次の1機能}だけを追加して」

```

## 沼脱出プロンプト50本

### エラーが出た時

**1. エラーを丸ごと渡す**
```text
前提: 何のエラーか分からないまま、赤い文字がたくさん出て止まってしまった場面。
指示: 次のエラーメッセージを丸ごと渡すので、読み解く必要はなく、原因と対処法を教えて。「{エラーメッセージをここに貼る}」
出力形式: 原因の説明は3行以内。対処法は番号つきの手順で、どのファイルの何を直すかまで具体的に示して。
```

**2. 同じエラーが繰り返す**
```text
前提: 一度直したはずのエラーが、形を変えてまた出てくる場面。
指示: この症状は今回で{回数}回目。これまで試した対処（{これまでの対処を書く}）を踏まえたうえで、表面的な対処ではなく根本原因を探して。
出力形式: 「なぜ直しても再発するのか」の仮説を2〜3個挙げ、それぞれの検証方法をセットで示して。
```

**3. エラーが出ているのに動いているように見える**
```text
前提: 画面上は動いているように見えるが、開発者ツール等にエラーが出ている場面。
指示: 画面には出ていないが、裏側で起きているエラー「{エラー内容}」について、今すぐ直すべきか、後回しでよいかを判断して。
出力形式: 「今すぐ直すべき／様子を見てよい」を最初に結論として書き、理由を2〜3行で添えて。
```

**4. エラーメッセージが英語で分からない**
```text
前提: エラーメッセージが英語や専門用語ばかりで、何を言っているか分からない場面。
指示: 次のエラーを、専門知識がなくても分かる言葉で説明して。「{エラーメッセージをここに貼る}」
出力形式: 「要するに何が起きているか」を1文で、そのあとに直し方を3ステップ以内で示して。
```

**5. エラーの原因が複数考えられる**
```text
前提: エラーの原因が1つに絞れず、どこから手をつけていいか分からない場面。
指示: 「{症状}」について、考えられる原因を洗い出し、確認しやすい順番に並べ替えて。
出力形式: 原因ごとに「確認方法」と「かかる時間の目安」を添えた表形式で出して。
```

### 動きが遅い

**6. 体感で分かるレベルまで軽くする**
```text
前提: 専門的な最適化理論は分からないが、動きが遅いと感じている場面。
指示: 「{機能名}」の動きが遅く感じる。体感で分かるレベルまで軽くする方法を教えて。
出力形式: 優先度が高い順に3つまで、それぞれ「直すとどれくらい速くなるか」の目安を添えて。
```

**7. 特定の操作だけ遅い**
```text
前提: アプリ全体は普通だが、特定の操作だけ極端に遅い場面。
指示: 「{操作名}」をするときだけ、体感で{秒数}秒以上待たされる。原因を特定して。
出力形式: 原因の説明は3行以内。直す場合の影響範囲（他の機能に影響しないか）も添えて。
```

**8. 起動直後が遅い**
```text
前提: アプリを開いた直後、最初の画面が表示されるまでが遅い場面。
指示: 「{アプリ名}」を開いてから最初の画面が出るまでを速くしたい。何が原因で遅くなっているか調べて。
出力形式: 原因と対処法をセットで、体感速度がどれくらい改善するかの見込みも添えて。
```

**9. 手元の機械のスペックが原因かもしれない**
```text
前提: 自分の手元の機械（{OS・スペック}）が原因で遅いのか、実装の問題なのか分からない場面。
指示: 今の遅さが、手元の機械のスペックの問題か、実装側の問題かを切り分けて。
出力形式: 「機械の問題／実装の問題」のどちらが濃厚かを最初に書き、それぞれの場合の対処法を分けて示して。
```

**10. 処理をまとめてやるべきか迷う**
```text
前提: 操作のたびに毎回処理するのと、まとめて後で処理するのとで迷っている場面。
指示: 「{処理内容}」を、都度即座に処理すべきか、まとめて後でやるべきかを判断して。
出力形式: 判断基準を先に示し、今回のケースでの推奨案を理由つきで1つに絞って。
```

### 何をすればいいか分からない


**17. 計画を立て直してもらう**
```text

出力形式: 元の目的に対して「今も必要なもの」「もう不要なもの」を分けたうえで、新しい計画を出して。
```

**18. 優先順位をつけてもらう**
```text
前提: やりたいこと・直したいことが複数あり、どれからやればいいか分からない場面。
指示: 次のリストに優先順位をつけて。「{やりたいことのリスト}」
出力形式: 優先度（高・中・低）ごとに分け、高に分類した理由も一言添えて。
```

**19. 完成の基準を決めてもらう**
```text
前提: どこまで作り込めば「完成」とみなせるか分からず、いつまでも手を止められない場面。
指示: 「{アプリ名}」について、今の利用頻度（{目安}）を踏まえて、どこで完成とみなすべきかの基準を提案して。

```

**20. そもそも作る価値があるか判断してもらう**
```text
前提: ここまで作ってきたが、そもそも作る意味があったのか不安になった場面。
指示: 「{アプリ名}」について、これまでの利用実績（{使った回数・頻度}）から、続ける価値があるかを客観的に判断して。
出力形式: 判断とその理由を3行以内で。続ける場合・止める場合それぞれの次の一歩も添えて。
```

### 2. 公開前セキュリティ＆規約チェックリスト（チェックリスト）
# 作ったアプリを公開する直前に、5ステップで確認するチェックリストです。

# 🎁 公開前セキュリティ＆規約チェックリスト

作ったアプリを公開する直前に、5ステップで確認するチェックリストです。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 公開ボタンを押す前に、上から順にClaude Codeに確認させてください。

```text
【公開前セキュリティ&規約チェックリスト】

■ ステップ1：無料枠の利用条件を確認する
□ 使っているホスティング・APIサービスの無料枠が「個人の非商用利用」限定になっていないか確認した
□ 広告・アフィリエイト・有料提供など収益が絡む使い方をしていないか確認した
→ YES(条件を満たしている): ステップ2へ
→ NO(条件に違反しそう): 有料プランへの切り替えを検討する
指示例: 「このアプリが{サービス名}の無料枠の利用条件に違反していないか確認して」

■ ステップ2：鍵(APIキー等)の置き場所を確認する
□ APIキー・パスワードが画面側(フロントエンド)のコードに直書きされていないか確認した
□ 環境変数など、外部から見えない場所に置き直した
→ YES: ステップ3へ
→ NO: 鍵をコードから取り除き、環境変数に移す
指示例: 「プロジェクト全体を確認して、鍵がコードに直書きされていないか調べて」

■ ステップ3：他者の素材・データの規約を確認する
□ 使っている画像・音源・ライブラリの利用規約(商用利用・再配布の可否)を確認した
□ 規約に違反する使い方をしていない
→ YES: ステップ4へ
→ NO: 規約に沿った代替素材に差し替える
指示例: 「使っている素材・ライブラリの利用条件を確認して、商用公開に問題がないか教えて」

■ ステップ4：利用者データの扱いを確認する
□ 利用者が入力・保存するデータの種類を把握している
□ 不要なデータを保存していない、または保存する場合は理由を説明できる
→ YES: ステップ5へ
→ NO: 保存するデータの範囲を見直す
指示例: 「このアプリが利用者のどんなデータを、どこに、どれくらいの期間保存しているか棚卸しして」

■ ステップ5：公開後の連絡先を用意する
□ 不具合が見つかったときの連絡先・報告方法を用意した
□ 公開ページのどこかに、その連絡先を明記した
→ YES: 公開してよい
→ NO: 連絡先を用意してから公開する
指示例: 「不具合の報告先を明記した、利用者向けのお知らせ文を作って」
```

**ポイント**: 5ステップすべてがYESになってから公開する。無料枠は多くの場合「個人の非商用利用」が条件になっているため、収益が絡む場合は必ず有料プランへの切り替えを検討する。
