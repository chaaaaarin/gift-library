# AIニュース確度判定シート

読んだAIニュースが、どれくらい信頼できるかをその場で判定するためのチェックリストです。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 気になったニュース記事・投稿を見るたびに、このシートに沿って上から順にチェックしてください。

```text
【AIニュース確度判定シート】

■ ステップ1：情報源を特定する
□ 一次情報(公式発表・公式ブログ・公式SNSアカウント)から直接読んだか
→ YES: 確度✅の候補として次へ進む
□ 報道記事・まとめサイト・SNSの又聞き経由でしか読んでいないか
→ YES: ステップ2の裏取りを必ず行う

■ ステップ2：複数ソースで裏取りする
□ 独立した2つ以上のメディア・情報源で同じ内容が確認できるか
→ YES: 確度を1段階引き上げてよい
□ 情報源が1つしかない、またはすべて同じ発信元の転載か
→ YES: 確度は🔶(一次情報あり・単独ソースまたは二次報道)以下にとどめる
指示例: 「〇〇について、公式発表と、独立した2つ以上のメディア報道で内容が一致しているか確認して」

■ ステップ3：数字・固有名詞の出典を確認する
□ 金額・日付・パーセンテージなどの数字に出典が明記されているか
□ 企業名・人物名の表記が情報源間で一致しているか
→ YES(両方満たす): そのまま採用してよい
→ NO: 数字・固有名詞は「未確認」と注記した上で扱う

■ ステップ4：矛盾をチェックする
□ 情報源間で日付・数字・内容に食い違いがないか
→ YES(矛盾がある): 矛盾点を明記した上で両論併記する
→ NO(矛盾がない): 確度判定を確定してよい

■ ステップ5：確度マークを確定する
□ 公式発表+複数メディアで裏取り済み → ✅
□ 一次情報はあるが単独ソースまたは二次報道のみ → 🔶
□ 噂・推測の域を出ない、発信元が不明確 → ⚠️
指示例: 「このニュースリストの各項目に、上記の基準で✅🔶⚠️のいずれかを付けて、判定理由も1行で添えて」

■ 補足：確度が低いまま扱ってよい場合
□ 「未確認情報である」と明記した上で紹介する分には⚠️のまま使ってよい
□ 断定的な言い回し(「〜だ」「〜になる」)ではなく推測の言い回し(「〜と報じられている」「〜との見方もある」)にする
```

**ポイント**: 確度は「情報の面白さ」ではなく「裏取りの有無」だけで機械的に判定する。印象で✅を付けない。

# 新モデル乗り換え要否ジャッジシート

次々出てくる新モデルの発表に振り回されず、「今のモデルから乗り換えるべきか」を判定するためのシートです。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 気になる新モデルが発表されるたびに、このシートに沿って上から順に判定してください。

```text
【新モデル乗り換え要否ジャッジシート】

■ ステップ1：発表内容の実態を確認する
□ 「オープンウェイト」と謳っているが、実際に重みは公開されているか
□ ベンチマークは自社評価のみか、第三者による再現・評価もあるか
→ YES(重み未公開 or 自社評価のみ): 「野心表明」として一旦様子見に倒す
→ NO(重み公開済み・第三者評価あり): ステップ2に進む
指示例: 「〇〇モデルの発表ページと、Hugging Face/GitHubの実際の公開状況を照合して、発表と実態のズレがないか確認して」

■ ステップ2：自分の用途に必要な軸だけを比較する
□ 今の環境で困っている点(速度/精度/価格/コンテキスト長など)を1つに絞れているか
□ 新モデルはその1点で明確に上回っているか
→ YES: ステップ3に進む
→ NO: 乗り換えの動機が弱い。今回は様子見でよい

■ ステップ3：乗り換えコストを見積もる
□ プロンプト・ワークフローの書き換えはどの程度必要か
□ 既存のハーネス(周辺ツール・自動化・チェック体制)は新モデルでもそのまま動くか
→ YES(書き換えコストが小さい): 試験導入に進む
→ NO(書き換えコストが大きい): 得られる利得と天秤にかけて判断する
指示例: 「今使っているプロンプトとワークフローを〇〇モデル用に書き換えるとしたら、具体的にどこを直す必要があるか洗い出して」

■ ステップ4：小さく試す
□ 本番の全タスクではなく、一部のタスクだけ新モデルに切り替えて試したか
□ 失敗したときにすぐ元のモデルへ戻せる設計になっているか
→ YES: 段階的に切り替え範囲を広げてよい
→ NO: まずロールバック手段を用意してから試す

■ ステップ5：判断を確定する
□ 用途に必要な軸で明確に上回り、乗り換えコストが許容範囲内か
→ YES: 本格移行する
→ NO: 今のモデルを継続し、次の新モデル発表まで様子見する
指示例: 「このジャッジシートの基準に沿って、〇〇モデルへの乗り換えを検討した結果と、その理由を3行でまとめて」
```

**ポイント**: パラメータ数やベンチマーク順位だけで判断しない。「自分の用途の1点」で本当に上回っているかを基準にする。

## モデル・新機能速報チェック

### 1. 今週の新モデルリリース一括確認

```text
前提: 毎週決まった曜日に、主要AI企業の新モデル動向をまとめてチェックしたい。
指示: WebSearchで「(対象期間) AI model release」「(対象企業名) new model」を検索し、正式発表された新モデル・大型アップデートを日付つきで洗い出して。各項目は開発元・モデル名・主な特徴・公式発表URLをセットで挙げて。
出力形式: 表形式(日付/企業/モデル名/特徴/URL)。噂段階のものは「未確定」と明記して分けて。
```

### 2. ベンチマーク主張の裏取り

```text
前提: 新モデルの「〇〇を上回った」という発表を鵜呑みにせず、根拠を確認したい。
指示: 対象モデルの公式発表ページを開き、比較対象・使用したベンチマーク名・評価条件(自社評価か第三者評価か)を抽出して。第三者による再現・反論が出ていないかも合わせて検索して。
出力形式: 「主張」「根拠」「評価条件」「独立検証の有無」の4項目を箇条書きで。過大な誇張表現があれば指摘して。
```

### 3. オープンウェイト化の実態確認

```text
前提: 「オープンウェイト」と発表されたモデルが、実際に重みを公開しているか確認したい。
指示: 公式発表ページとHugging Face/GitHubの該当リポジトリを確認し、発表時点で重みファイルが実際にダウンロード可能かを調べて。ライセンス条件(商用利用可否・パラメータ数制限等)も確認して。
出力形式: 「発表内容」「実際の公開状況」「ライセンス条件」を分けて報告。まだ未公開なら公開予定時期も添えて。
```

### 4. 価格改定・値下げの整理

```text
前提: 主要AIモデルのAPI価格が頻繁に変わるので、最新の価格を一覧化したい。
指示: 対象モデル群の公式Pricingページを開き、入力/出力トークン単価の最新値を取得して。直近の値下げ・値上げがあれば変更前後を比較して。
出力形式: モデル名・入力単価・出力単価・直近の価格改定(あれば変更率)を表にまとめて。
```

### 5. マルチモーダル新機能の実力確認

```text
前提: 画像・動画・音声を扱う新機能が発表されたとき、実際に使えるレベルか判断したい。
指示: 公式発表と第三者レビューの両方を検索し、対応形式(画像/動画/音声)・生成可能な長さや解像度・既知の制限事項を整理して。実際に試したユーザーの反応もX等で確認して。
出力形式: 「公式スペック」「実測レビューでの評価」「既知の制限」を分けて。誇大広告の疑いがあれば注意喚起して。
```

### 6. 競合モデルの横並び比較

```text
前提: 似た時期に出た複数の新モデルを、同じ軸で比較検討したい。
指示: 指定したモデル群について、パラメータ規模・コンテキスト長・価格・対応マルチモーダル・オープン性の5軸で情報を集めて。
出力形式: 5軸×モデル数の比較表。情報源が取れなかった軸は「不明」と明記し埋め合わせで推測しない。
```

### 7. 旧モデルの廃止・非推奨スケジュール確認

```text
前提: 使っているモデルがいつ廃止されるか把握しておきたい。
指示: 対象企業の公式Deprecationページ・Release Notesを検索し、廃止予定のモデル名・廃止日・推奨される移行先モデルを抽出して。
出力形式: モデル名・廃止日・移行先・移行時の注意点を表形式で。日付が近い順に並べて。
```

### 8. 新機能のβ版/GA版の区別確認

```text
前提: 「発表された機能」が実際に誰でも使える状態か、まだ限定公開かを見分けたい。
指示: 公式発表文を精読し、Beta/Preview/GA(一般提供)のどの段階かを明記して。対象ユーザー(全員/特定プラン/ウェイトリスト)と利用開始方法も確認して。
出力形式: 「提供段階」「対象ユーザー」「利用開始方法」「正式GA予定時期(あれば)」の4項目で。
```

### 9. 週内の複数モデル発表を時系列整理

```text
前提: 1週間に複数の新モデル発表が重なったとき、時系列で流れを追いたい。
指示: 指定期間内の主要モデル発表をすべて洗い出し、発表日時順に並べて。互いに競合を意識した対抗発表になっていないか(タイミングの近さ)も注記して。
出力形式: 日時順のタイムライン形式。同日・近接日の発表には「対抗発表の可能性」を付記。
```

### 10. 次世代モデルの噂・ロードマップ収集

```text
前提: まだ正式発表されていない次期モデルの情報を、噂と公式情報を区別して集めたい。
指示: 対象企業のロードマップ公式言及と、業界メディア・関係者リークの噂を分けて検索して。噂情報は必ず発信元と信頼度を明記して。
出力形式: 「公式が言及した事実」と「未確認の噂(発信元つき)」を明確に分けたセクション構成で。噂を事実として書かない。
```
