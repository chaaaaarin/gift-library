# 🎁 autoMode環境設定コピペテンプレート50選

Claude CodeのAuto Modeは、`autoMode.environment`に「あなたの環境が何を信頼してよいか」を書くほど、誤ブロックが減って賢く動きます。ただし公式ドキュメントは「平易な英語の文章で書く」としか教えてくれず、白紙から書くのは大変です。業種・インフラ構成・チーム規模・特殊ケースの4カテゴリ×計50パターンを用意したので、一番近いものを選んで`~/.claude/settings.json`に貼るだけで使えます。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 1. 自分の状況に近いテンプレートを選ぶ → 2. `~/.claude/settings.json`（個人）または管理設定に貼る → 3. `< >`で囲んだ箇所を自分の環境名に置き換える → 4. `claude auto-mode config`で反映を確認する。

## A. 業種別（15）

```text
1. SaaS企業（BtoB向けWebサービス）
前提: 複数の顧客企業にサービスを提供するBtoB SaaSで、顧客ごとの環境を誤って混同されたくない。
設定例:
{
  "autoMode": {
    "environment": [
      "$defaults",
      "Organization: <会社名>。Primary use: BtoB SaaSプロダクトの開発・運用",
      "Source control: github.com/<org名> 配下の全リポジトリ",
      "Sensitive data locations & audiences: 顧客テナントのDB・S3バケットは各社の契約範囲内のみで共有可、社外には出さない"
    ]
  }
}
ポイント: マルチテナント特有の「顧客Aのデータを顧客Bの文脈で使わない」という注意点は、後述のD特殊ケース11番と組み合わせると安全性が上がる。
```

**使い方**: 上から順番にチェックしてください。□の項目でYESなら→の行動を、迷ったら「指示例」をそのままClaude Codeに貼って確認できます。

```text
【Auto Mode安全導入ロールアウトチェックリスト】

■ ステップ1：切り替わる前に、今の状態を確認する
□ 自分（または組織）は、既に手動で別のデフォルトモードをピン留め設定していないか？
→ YES: 8/14になっても自動では切り替わらない（設定は維持される）。切り替えたい場合だけ手動で変更する。
→ NO（何も設定していない）: 8/14以降、新規セッションから自動的にAuto Modeがデフォルトになる。ステップ2に進む。
指示例: 「今のClaude Codeの権限モードの設定を確認して、Auto Modeが既に有効か、それとも他のモードがピン留めされているか教えてください」

□ 自分が今、公開リポジトリと非公開リポジトリのどちらで作業しているか把握しているか？
→ YES: リポジトリの可視性に応じて、機密情報の扱い基準が変わることを意識してステップ2へ。
→ NO: まず対象リポジトリがpublicかprivateかを確認してから先に進む。
指示例: 「このリポジトリはpublicとprivateのどちらですか。GitHub上の設定を確認して教えてください」

■ ステップ2：最小構成でAuto Modeを試す（狭い範囲から）
□ まずは低リスクな作業（コードの読み取り・テスト実行・ドキュメント編集など）だけでAuto Modeを試したか？
→ YES: 大きな問題がなければステップ3の観察期間へ進む。
→ NO: 本番デプロイや大量データ操作を伴う作業からいきなり始めない。まずは日常的な開発タスクで様子を見る。
指示例: 「Auto Modeを試したいので、まずは既存のテストコードを実行して結果を報告するところから始めてください」

□ `autoMode.environment`に、自分の組織名・使っているクラウド・信頼できる社内ドメインを最低限書いたか？
→ YES: 誤ブロックが減った状態で試せる。ステップ3へ。
→ NO: 何も書かないと、自社のGitHub組織やクラウドバケットへの操作まで「環境外」として頻繁にブロックされる。
指示例: 「~/.claude/settings.jsonのautoMode.environmentに、$defaultsを残したまま、私の会社名と使っているクラウドプロバイダを追加してください」

■ ステップ3：観察期間を設ける（最低数日〜1週間の目安）
□ `/permissions`の「Recently denied」タブを定期的に見て、何がブロックされているか確認したか？
→ YES: ブロックの傾向（誤検知か、正しい防御か）を把握できている。ステップ4へ。
→ NO: 何がブロックされているか知らないまま設定を広げると、必要な防御まで緩めてしまうリスクがある。
指示例: 「直近でAuto Modeにブロックされた操作の一覧を確認する方法を教えてください」

□ 同じ種類の操作が繰り返しブロックされていないか（＝分類器が文脈を誤解している兆候）確認したか？
→ YES: 繰り返しブロックされるものは、正当な業務であればenvironmentに追加候補としてメモする。
→ NO: 1回だけのブロックと繰り返しのブロックを区別せず一律で緩めると、本来防ぐべきものまで緩めてしまう。
指示例: 「〇〇という操作が何度もブロックされています。これは正当な業務なので、環境設定に追加すべきか判断を手伝ってください」

■ ステップ4：環境設定を段階的に広げる
□ 観察期間で見つかった「正当なのに毎回ブロックされる」操作を、`autoMode.environment`または`allow`に追加したか？
→ YES: 誤ブロックが減り、実務での使い勝手が上がる。ステップ5へ。
→ NO: 不便なまま放置すると、確認疲れが逆戻りして「とりあえず全部許可」のような雑な設定に流れやすい。
指示例: 「先ほど繰り返しブロックされていた〇〇の操作を、autoMode.allowに追加する設定文を書いてください」

□ 逆に、自社特有の危険な操作（例: 特定の本番データベースへの直接アクセス）を`soft_deny`や`hard_deny`に追加したか？
→ YES: デフォルトのルールだけではカバーしきれない自社固有のリスクにも対応できている。
→ NO: 標準のルールは一般的な危険操作しかカバーしない。業界・自社特有のリスクは自分で言語化して追加する必要がある。
指示例: 「私たちの会社で特に注意が必要な操作（例: 顧客DBへの直接書き込み）を、autoMode.soft_denyに追加する文章を一緒に考えてください」

■ ステップ5：人間が必ず確認する境界線を固定する
□ 本番デプロイ・課金設定変更など「絶対に人間の目を通したい操作」に、`permissions.ask`ルールを設定したか？
→ YES: Auto Modeが有効でも、この操作だけは必ずプロンプトが出る状態になっている。
→ NO: 「一応気をつける」という口頭の意識だけでは、セッションが長くなるほど忘れられやすい。設定として固定する。
指示例: 「git pushとgh pr createの前には必ず確認を求めるように、permissions.askのルールを設定してください」

□ その確認ルールが、チームの他のメンバーにも共有・展開されているか（個人設定で終わっていないか）？
→ YES: チーム全体で同じ安全基準が保たれている。
→ NO: 個人のsettings.jsonだけに書いても他のメンバーには反映されない。管理設定（Managed settings）での展開を検討する。
指示例: 「今設定したautoMode.environmentとpermissions.askのルールを、チーム全体に展開するには何を管理設定に移せばいいか教えてください」

■ ステップ6：運用として定着させる
□ 新しくチームに加わったメンバーに、Auto Modeの設定方針を説明する手順があるか？
→ YES: 属人化せず、チームの標準運用として引き継げる。
→ NO: 設定した本人しか理由を知らないと、時間が経つと「なぜこの設定になっているか」が分からなくなる。
指示例: 「今のautoMode設定の内容と、それぞれ何のために設定したのかを、新メンバー向けのドキュメントとしてまとめてください」

□ 月1回など定期的に、`claude auto-mode config`で実際に適用されているルールを再確認する習慣があるか？
→ YES: バージョンアップでデフォルトルールが変わっても、意図とのズレに早く気づける。
→ NO: 設定は一度書いたら見直さないことが多い。定期確認をカレンダーに入れておく。
指示例: 「claude auto-mode configを実行して、今のautoMode設定が意図通りに反映されているか確認してください」
```
