### 2. Claude Code→Cursor 移行判断チェックリスト（チェックリスト）

# 🎁 Claude Code→Cursor 移行判断チェックリスト

Cursorへの移行を検討するとき、何をどの順番で確認すればいいかをまとめた実践チェックリストです。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: そのままAIに貼って「このチェックリストに沿って今のプロジェクトを診断して」と頼んでも使えます。

```text
【Claude Code→Cursor 移行判断チェックリスト】

■ ステップ1：今の使い方を棚卸しする
□ Claude Codeで1週間に何回、どんな作業をしているか記録したか
→ YES: ステップ2へ進む
□ .claude/配下（CLAUDE.md・skills・agents・settings.json）に固有の資産があるか
→ YES: 移行対象リストに追加する
指示例: 「.claude/配下のファイル一覧と、それぞれの役割を教えてください」

■ ステップ2：コスト面を比較する
□ 直近1ヶ月のClaude Code利用コスト（またはプラン料金）を把握しているか
→ YES: Cursorの利用上限2倍・Router導入後の想定コストと比較する
□ 重要な設計判断など、品質を落とせない作業がどれくらいの割合か
→ YES: その割合が高いほど、Intelligenceモード固定前提でコストを試算する
指示例: 「今月の利用ログから、作業の種類ごとにコスト内訳を出してください」

■ ステップ3：資産の移行可否を確認する
□ CLAUDE.mdの内容がCursorのプロジェクトルールに変換できるか
→ YES: 変換してテスト運用する
→ NO: Cursor側で代替できない部分をリスト化し、当面は手動運用にする
□ サブエージェント・スキル定義など、移行できない機能があるか
→ YES: その機能が無くても業務が回るか確認する
指示例: 「このCLAUDE.mdをCursorのプロジェクトルール形式に変換してください」

■ ステップ4：併用期間を設ける
□ いきなり全面移行せず、1〜2週間の併用期間を設定したか
→ YES: 期間中は両ツールでの体感・コストを記録する
□ チームメンバーに併用期間であることを共有したか
→ YES: 混乱を避けるため、併用中の使い分けルールを1枚にまとめる
指示例: 「併用期間中の使い分けルールを簡潔にまとめてください」

■ ステップ5：判断を下す
□ コスト・品質・チームの習熟度、すべての面でCursorが上回っているか
→ YES: 本格移行に進める
→ NO: 併用を継続し、次回レビュー時期を決める
□ SpaceXによるAnysphere買収の完了時期（2026年Q3予定）を確認したか
→ YES: 完了前後で条件が変わる可能性があるため、完了後に再評価する予定を入れる
指示例: 「現時点での比較結果をもとに、移行すべきか併用継続すべきか判断してください」
```

### 3. Routerモード使い分け早見表（早見表・逆引き）

# 🎁 Routerモード使い分け早見表

Cursor RouterのIntelligence/Balance/Costを、タスクの種類別にどう選ぶかの早見表です。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 作業を始める前にこの表を確認し、該当するモードを明示してから依頼してください。

```text
【Routerモード使い分け早見表】

■ ステップ1：タスクの性質を見極める
□ アーキテクチャ設計・重要な技術選定・複雑なバグ調査か
→ YES: Intelligenceモードを選ぶ（最上位モデル・コストより品質優先）
指示例: 「この設計判断はIntelligenceモードで検討してください」

□ 日常的な実装・UI作成・一般的なリファクタか
→ YES: Balanceモードを選ぶ（品質とコストの両立）
指示例: 「Balanceモードで、このコンポーネントを実装してください」

□ 変数名変更・定型フォーマット・単純な繰り返し作業か
→ YES: Costモードを選ぶ（コスト最優先）
指示例: 「これは単純作業なのでCostモードで進めてください」

■ ステップ2：迷ったときの判断基準
□ 「後で直すのが大変な判断」か「後からでも直せる作業」か
→ YES（大変）: Intelligenceモード側に倒す
→ YES（直せる）: Balance/Costモード側に倒す
指示例: 「この変更は後から直しやすいか教えてから、モードを提案してください」

□ 同じタスクを2つのモードで試して品質差を確認したいか
→ YES: 両モードでの出力を比較してもらう
指示例: 「Balanceモードとの品質差を確認したいので、両方の案を出してください」

■ ステップ3：チームでの運用ルールに落とし込む
□ タスク種別ごとのモード選定基準を、チームで共有できる形にしたか
→ YES: 早見表として.claude/または.cursor/配下のルールファイルに保存する
指示例: 「このモード選定基準をプロジェクトルールファイルとして保存してください」

□ 月1回など定期的に、モード選定が実態に合っているか見直しているか
→ YES: 見直しのタイミングをカレンダーに設定する
指示例: 「先月使ったタスクとモードの組み合わせを振り返ってください」
```

**ポイント**: 重要な設計判断だけは必ずIntelligenceモード固定にし、日常作業はBalance/Costに任せるのが基本方針です。
