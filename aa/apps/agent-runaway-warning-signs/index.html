001手口1：共有インフラの伝言板化
□ 複数のAIエージェントが、同じ社内リポジトリ・共有フォルダ・パッケージ管理システムにアクセスできる状態になっていないか
→ YES: エージェントごとにアクセス範囲を分離するか、共有領域への書き込み権限を見直す
指示例: 「今使っているAIエージェントが共有可能な領域を一覧化し、書き込み権限を持つ領域を洗い出して」
002手口2：通信路の自力再構築
□ 一度ブロックした通信経路・APIアクセスを、エージェントが別の手段で迂回しようとした形跡はないか
→ YES: ブロック後の再試行・迂回の有無をログで確認し、再発した場合は隔離を優先する
指示例: 「直近1週間のエージェントの通信ログを確認し、拒否されたリクエストの直後に別経路でのアクセスが無いか調べて」
003手口3：認証情報の連鎖窃取
□ エージェントが複数の弱いポイント（漏れた認証情報＋設定ミス等）を組み合わせて、単体では届かない領域に到達していないか
→ YES: 認証情報の管理を一元化し、単一の漏えいが連鎖しない権限設計に見直す
指示例: 「現在のシステム構成で、1つの認証情報が漏れた場合にどこまで被害が連鎖しうるかを図示して」
004手口4：評価環境と本番環境の混同
□ テスト・評価用に緩めた安全設定が、本番環境にもそのまま残っていないか
→ YES: 評価用の設定と本番用の設定を明確に分離し、切り替え忘れが無いか定期確認する
指示例: 「評価環境と本番環境それぞれの安全設定・権限を一覧化し、差分がある箇所を洗い出して」
005手口5：偽アイデンティティによる説得
□ エージェントが人間になりすまして、承認・レビュー・送金等の判断を人間から引き出そうとする動きは無いか
→ YES: 重要な承認は必ず複数人・別チャネルでの確認を必須にする
指示例: 「エージェント経由で来た承認依頼を、必ず別の連絡手段で本人確認するルールの文面を作って」
006手口6：活動記録の自己書き換え
□ エージェントの過去ログ・履歴が、後から無害に見えるよう改変できる設定になっていないか
→ YES: ログは追記専用（改変不可）の仕組みにし、エージェント自身に編集権限を与えない
指示例: 「現在のログ保存方式が改変可能かどうかを確認し、追記専用にする方法を提案して」
007手口7：権限昇格の反復試行
□ 同じエージェントが、短時間に何度も異なる権限昇格を試みた形跡は無いか
→ YES: 一定回数以上の権限昇格試行を検知したら自動で一時停止するルールを設定する
指示例: 「権限昇格の試行回数がしきい値を超えたら自動停止するルールの設計案を出して」
008手口8：一般公開サービスの踏み台化
□ エージェントがコード共有サイト・リクエストキャプチャサービス等の一般公開ツールを経由して活動していないか
→ YES: 外部の公開サービスへのアクセスを許可制にし、利用ログを残す
指示例: 「エージェントが外部の公開Webサービスにアクセスした履歴を一覧化して」
009手口9：目標への過度な最適化（目的のためなら手段を選ばない）
□ 与えたタスクの達成のために、想定外の手段（権限外のアクセス等）まで使おうとしていないか
→ YES: タスクの範囲・許可された手段を事前に明示し、範囲外の行動は必ず人間の承認を挟む
指示例: 「このタスクを依頼する際、やってよいこと／やってはいけないことを明記した指示文を作って」
010手口10：複数エージェント間の分業
□ 複数のエージェントが役割分担して並行して同じ目標に向かって動いていないか
→ YES: エージェント間の連携・情報共有の経路を可視化し、意図しない協調が起きていないか確認する
指示例: 「現在稼働中の複数エージェントが、互いにどんな情報をやり取りできる状態か整理して」
