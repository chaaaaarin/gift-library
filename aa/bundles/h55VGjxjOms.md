# 🎁 自作アプリの種 100本（採寸プロンプトつき）

「これ自作できる」題材を職種別に100本。1行の“痛み”と、そのまま話せる採寸プロンプト（前提・指示・出力形式）が付いています。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 自分の状況に近い項目を探し、プロンプトの `◯◯` を自分の言葉に置き換えて、Codexに音声入力で話しかけてください。返ってきた計画は必ず1機能に削ってから作らせます。

```text
■ 動画編集・クリエイター

1. 素材サイト横断検索
痛み: 効果音やBGMを探すたびに複数サイトを開き直し、同じ検索語を打ち直している。
前提: 動画編集をしていて、効果音とBGMを毎回3〜5つのフリー素材サイトで探し回っている。1本の動画で10回以上この往復が起きる。
指示: 自分がよく使う素材サイトの掲載ページ情報だけを横断して検索できるWebアプリを作りたい。素材ファイル自体は持たず、掲載ページへのリンクだけを扱う。各サイトの利用規約は先に読ませ、禁止されている扱い方（音源の直リンク・再生ページの自作など）は設計から外す。
出力形式: 最初の完成は「キーワードを入れると候補が一覧に出て、クリックすると元の掲載ページが開く」だけでいい。お気に入り登録・履歴・タグ編集は作らない。

2. サムネ案の比較ボード
痛み: サムネイル案を並べて比較するのに毎回スライドを作り直している。
前提: YouTubeのサムネイル案を3〜5枚作り、どれがいいかを人に見せて意見をもらう場面が毎週ある。今はスライドに貼って共有している。
指示: 画像を並べて表示し、それぞれに「良い点・直す点」を書き込めるWebアプリを作りたい。画像は自分の端末から選ぶだけで、サーバーに保存しなくてよい。
出力形式: 最初の完成は「画像を複数選ぶと横並びに表示され、各画像の下にメモを書ける」だけ。共有リンク・ログイン・保存機能は後回しにする。

3. テロップ表記ゆれチェッカー
痛み: 同じ動画内で「AI」「Ai」「エーアイ」が混ざり、あとで直すのに時間がかかる。
前提: 字幕・テロップの原稿を書いたあと、固有名詞や記号の表記ゆれを目で探して直している。1本あたり20分ほどかかっている。
指示: テキストを貼ると、あらかじめ登録した表記ルール（NG表記→OK表記の対応表）に反する箇所を全部並べて見せてくれるツールを作りたい。ルールは自分で足せるようにする。
出力形式: 最初の完成は「テキストを貼る → 違反箇所と行番号の一覧が出る」だけ。自動置換や履歴管理は作らない。

4. 案件の進行ボード
痛み: 案件ごとの進行状況が頭の中とチャットに散らばっている。
前提: 動画編集を複数本並行して受けており、初稿提出・修正待ち・納品済みの区別がチャットを遡らないと分からない。
指示: 案件名と締切、いまの状態（作業中／確認待ち／修正中／納品済み）だけを管理できるボードを作りたい。データは自分の端末の中だけに保存する。
出力形式: 最初の完成は「案件を追加して、状態を4つのどれかに切り替えられる」だけ。通知・共有・グラフは後回し。

5. 撮って出しの尺計算メモ
痛み: 尺の配分を毎回電卓とメモ帳で計算している。
前提: 動画の構成を組むとき、章ごとの目標尺を足し引きして全体の長さに収める作業を毎回手計算している。
指示: 章の名前と目標秒数を入れると合計と残り時間を自動計算し、目標尺を超えたら色で知らせてくれるツールを作りたい。
出力形式: 最初の完成は「行を追加して秒数を入れると合計が出る」だけ。テンプレート保存や書き出しは作らない。

6. 納品ファイル名の一括生成
痛み: 納品ファイル名の規則をクライアントごとに覚えていられない。
前提: クライアントごとに納品ファイル名の規則（日付の形式・案件コード・版数の付け方）が違い、毎回過去の納品物を見に行って確認している。
指示: クライアントを選んで日付と案件名と版数を入れると、その規則どおりのファイル名を組み立ててコピーできるツールを作りたい。規則は自分で追加・編集できるようにする。
出力形式: 最初の完成は「クライアントを選ぶ → 項目を入れる → 完成した名前をコピーできる」だけ。実ファイルのリネーム機能は作らない。

7. BGM使用履歴の記録
痛み: どの動画でどのBGMを使ったか分からず、同じ曲を続けて使ってしまう。
前提: 複数のチャンネルの動画を編集しており、同じBGMを直近で使ったかどうかを思い出せない。クレジット表記が必要な曲の管理も曖昧になっている。
指示: 動画タイトル・使用した曲名・提供元・クレジット表記が必要かどうかを記録し、曲名で検索できる一覧を作りたい。
出力形式: 最初の完成は「記録を1件追加できる／曲名で検索できる」だけ。集計や自動取り込みは作らない。

8. 修正依頼の書き起こしメモ
痛み: 口頭やボイスメモの修正依頼を、作業前に文字に落とすのが面倒。
前提: クライアントから音声や長文チャットで修正依頼が来て、そのまま作業に入ると抜けが出る。毎回自分で箇条書きに整理している。
指示: 長い文章を貼ると「何を・どこを・どう直すか」の3項目に分けた箇条書きに整理してくれるツールを作りたい。整理後は作業のチェックリストとして印を付けられるようにする。
出力形式: 最初の完成は「文章を貼る → 箇条書きに整理される → 各項目にチェックが付けられる」だけ。音声の取り込みは後回し。

9. 参考動画の切り抜きメモ
痛み: 参考にしたい演出の場所を覚えておけない。
前提: 参考にしたい動画の「この演出のこの秒数」をメモしたいが、ブックマークだと後から見つけられない。
指示: 動画のURLと秒数と一言メモを登録すると、その秒数から再生できるリンクを作って一覧にしてくれるツールを作りたい。タグで絞り込めるようにする。
出力形式: 最初の完成は「URL・秒数・メモを登録 → 一覧から該当秒数のリンクを開ける」だけ。タグ機能は次の段階に回す。

10. 編集前チェックリスト
痛み: 編集を始める前の確認事項を毎回思い出せない。
前提: 編集前に確認すべきこと（納品形式・尺・テロップ規則・NGワード・BGMの可否）がクライアントごとに違い、毎回抜けが出る。
指示: クライアントを選ぶと、そのクライアント専用の確認事項リストが出てきて、順番に印を付けられるツールを作りたい。リストは自分で編集できるようにする。
出力形式: 最初の完成は「クライアントを選ぶ → チェックリストが出る → 印を付けられる」だけ。履歴の保存は後回し。

■ 営業・商談

11. 商談メモから議事録
痛み: 商談後の議事録づくりに毎回30分かかっている。
前提: 商談中は箇条書きの走り書きしか取れず、あとで社内共有用の議事録に整える作業に毎回30分かかっている。
指示: 走り書きを貼ると「決まったこと／持ち帰り／次回までの宿題／期限」の4項目に整理してくれるツールを作りたい。宿題には担当者名を付けられるようにする。
出力形式: 最初の完成は「メモを貼る → 4項目に整理された文章が出る → コピーできる」だけ。保存や共有は後回し。

12. 提案書の使い回し検索
痛み: 過去の提案書のどこに何を書いたか探せない。
前提: 過去の提案書が大量にあり、似た業種の案件で使える部分を探すのに毎回フォルダを漁っている。
指示: 提案書の要点（業種・課題・提案内容・金額帯・結果）を1件ずつ登録しておき、業種や課題で検索できる台帳を作りたい。実ファイルへのリンクも持たせる。
出力形式: 最初の完成は「1件登録できる／業種で絞り込める」だけ。ファイル本体の解析や自動登録は作らない。

13. 見積の概算計算
痛み: 見積の概算を出すたびに表計算ファイルを探している。
前提: 商談中に概算を出す必要があるが、料金体系が複雑で表計算ファイルを開かないと計算できず、その場で答えられない。
指示: 項目と数量を選ぶだけで概算金額を計算し、内訳つきで表示するツールを作りたい。単価は自分で更新できるようにする。
出力形式: 最初の完成は「項目を選んで数量を入れる → 合計と内訳が出る」だけ。PDF書き出しや保存は後回し。

14. 追客リマインダー
痛み: 追いかけるべき見込み客を忘れる。
前提: 商談後の追客タイミング（3日後・2週間後・1か月後）を管理できず、機会を逃していると感じている。
指示: 見込み客名と最終接触日を登録すると、次に連絡すべき日を自動計算して「今日連絡すべき人」の一覧を出すツールを作りたい。
出力形式: 最初の完成は「登録 → 今日連絡すべき人が一覧で出る」だけ。メール送信や通知は作らない。

15. よくある質問の返答集
痛み: 同じ質問に毎回文章を書き直している。
前提: 問い合わせで来る質問の8割は同じ内容だが、そのたびに文章を書き直しており、担当者ごとに回答の質もばらついている。
指示: 質問をキーワードで検索すると、確認済みの回答文が出てきてそのままコピーできるツールを作りたい。回答文は自分で追加・修正できるようにする。
出力形式: 最初の完成は「キーワード検索 → 回答文が出る → コピーできる」だけ。承認フローや権限は作らない。

16. 競合比較の一枚表
痛み: 競合との比較を聞かれるたびに口頭で答えている。
前提: 商談で必ず競合との違いを聞かれるが、比較材料が個人の頭の中にあり、担当者によって説明がぶれる。
指示: 自社と競合数社を項目ごとに比較した表を作り、商談中に画面で見せられるようにしたい。項目と内容は自分で更新できるようにする。
出力形式: 最初の完成は「比較表を画面で表示できる／項目を編集できる」だけ。印刷用レイアウトは後回し。

17. 訪問ルートのメモ
痛み: 1日に複数訪問する日の順番決めが手間。
前提: 1日に3〜5件訪問する日があり、順番と移動時間の見積もりを毎回手で組んでいる。
指示: 訪問先の名前と希望時間帯を入れると、無理のない順番の案を出してくれるツールを作りたい。地図連携はせず、時間帯の整合だけを見る。
出力形式: 最初の完成は「訪問先を入れる → 時間帯が矛盾しない順番の案が出る」だけ。移動時間の自動計算は後回し。

18. 失注理由の記録と集計
痛み: 失注の理由が個人の記憶にしか残らない。
前提: 失注した案件の理由を振り返る機会がなく、同じ理由で落ち続けていても気づけない。
指示: 失注案件の理由を選択式（価格／時期／機能／競合／担当者不在）＋一言メモで記録し、理由ごとの件数を数えられるツールを作りたい。
出力形式: 最初の完成は「1件記録できる／理由ごとの件数が出る」だけ。グラフや期間比較は次の段階に回す。

19. お礼メールの下書き生成
痛み: お礼メールの文面を毎回考えている。
前提: 商談後のお礼メールを毎回ゼロから書いており、時間が空くと送らないまま流れてしまう。
指示: 相手の名前・話した内容・次のステップを入れると、そのままの丁寧さで送れるお礼メールの下書きを作るツールを作りたい。定型の言い回しは自分で登録できるようにする。
出力形式: 最初の完成は「3項目を入れる → 下書きが出る → コピーできる」だけ。メール送信機能は作らない。

20. 商談前の相手情報まとめ
痛み: 商談前の下調べに時間がかかる。
前提: 商談前に相手企業の公開情報を調べるのに毎回20〜30分かかり、準備が薄いまま臨むこともある。
指示: 会社名を入れると、自分で決めた確認項目（事業内容・規模・直近の発表・想定される課題）を埋める枠が出て、そこにメモを溜められるツールを作りたい。
出力形式: 最初の完成は「会社名を入れる → 確認項目の枠が出る → メモを保存できる」だけ。自動収集は作らない。

■ 事務・総務

21. 備品の貸出台帳
痛み: 誰が何を借りているか分からなくなる。
前提: 社内の備品（ノートパソコン・カメラ・プロジェクター）の貸出をノートで管理しており、返却漏れが起きている。
指示: 備品名・借りた人・貸出日・返却予定日を記録し、返却予定を過ぎたものを目立たせる台帳を作りたい。
出力形式: 最初の完成は「貸出を1件登録できる／期限超過が色で分かる」だけ。QRコードや通知は作らない。

22. 郵便物の受け渡し記録
痛み: 誰宛の郵便を誰に渡したか記録がない。
前提: 郵便物や宅配を受け取って社内の担当者に渡す作業をしているが、記録がないため「届いていない」と言われたときに確認できない。
指示: 受け取った日時・差出人・宛先の担当者・渡した日時を1件ずつ記録し、担当者名で検索できるツールを作りたい。
出力形式: 最初の完成は「受け取り記録を1件登録できる／担当者名で検索できる」だけ。写真の添付は後回し。

23. 会議室の空き確認
痛み: 会議室の空き状況が壁の紙でしか分からない。
前提: 会議室の予約を紙の表で管理しており、自席から空き状況が分からないため何度も見に行っている。
指示: 日付と部屋を選ぶと時間帯ごとの空き状況が見え、そのまま予約を書き込める表を作りたい。データは1つの場所に保存する。
出力形式: 最初の完成は「日付を選ぶ → 時間帯の表が出る → 空き枠に名前を書き込める」だけ。承認や通知は作らない。

24. 社内問い合わせの振り分けメモ
痛み: 同じ問い合わせを毎回別の人が答えている。
前提: 総務への問い合わせが口頭・チャット・メールに分散し、誰がどこまで対応したか分からなくなる。
指示: 問い合わせ内容・依頼者・状態（受付／対応中／完了）を記録し、未完了のものだけを絞り込める一覧を作りたい。
出力形式: 最初の完成は「1件登録できる／未完了だけを絞り込める」だけ。担当者の自動割り当ては作らない。

25. 入退社手続きの進行表
痛み: 入社手続きの抜けが毎回発生する。
前提: 入社・退社のたびに必要な手続きが多く（アカウント発行・備品・保険・座席）、抜けが出ると本人に迷惑がかかる。
指示: 入社日を入れると必要な手続きの一覧が自動で並び、済んだものに印を付けられる進行表を作りたい。手続きの項目は自分で編集できるようにする。
出力形式: 最初の完成は「入社日を入れる → 手続き一覧が出る → 印を付けられる」だけ。担当者への通知は後回し。

26. 押印申請の記録
痛み: 押印の申請と履行が紙でしか残らない。
前提: 押印の申請を紙で受け、押した記録も紙のため、あとから「いつ誰の依頼で押したか」を探すのに時間がかかる。
指示: 申請者・書類名・押印日・保管場所を記録して検索できる台帳を作りたい。書類名の一部でも検索できるようにする。
出力形式: 最初の完成は「1件記録できる／書類名で部分検索できる」だけ。承認フローは作らない。

27. 社内マニュアルの検索窓
痛み: マニュアルがどこにあるか分からず毎回聞かれる。
前提: 社内マニュアルが複数のフォルダとチャットに散らばっており、「あれどこ？」の質問が毎日来る。
指示: マニュアル名・置き場所のリンク・要約1行を登録した一覧を作り、キーワードで探せるようにしたい。
出力形式: 最初の完成は「1件登録できる／キーワードで探せる」だけ。ファイル本体の中身検索は作らない。

28. 経費の立替記録
痛み: 立替経費の申請漏れが出る。
前提: 小口の立替経費を後回しにして忘れ、月末に領収書だけが残って何の費用か分からなくなる。
指示: 日付・金額・目的・支払先を1件ずつ記録し、未申請のものだけを合計できるツールを作りたい。
出力形式: 最初の完成は「1件記録できる／未申請の合計が出る」だけ。領収書の写真取り込みは後回し。

29. 受付の来客記録
痛み: 来客の記録が紙のノートだけ。
前提: 来客の記録を紙のノートで取っており、あとから「いつ誰が来たか」を調べるのに時間がかかる。
指示: 来訪日時・会社名・氏名・訪問先の担当者を記録し、日付と会社名で検索できるツールを作りたい。個人情報を扱うので保存先は自分の管理下に限る。
出力形式: 最初の完成は「1件記録できる／日付で絞り込める」だけ。入館証の発行は作らない。

30. 定期タスクの棚卸し表
痛み: 毎月やる作業の抜けに気づけない。
前提: 月次・週次でやる決まった作業が20件ほどあり、忙しい月に抜けが出ても後になって気づく。
指示: 作業名と頻度（毎日／毎週／毎月）を登録すると、今月やるべき作業の一覧が出て、済んだ印を付けられるツールを作りたい。
出力形式: 最初の完成は「登録 → 今月やるべき一覧が出る → 印を付けられる」だけ。翌月への自動繰越は次の段階に回す。

■ マーケティング・SNS

31. 投稿ネタの在庫管理
```

# 🎁 仮縫い判定シート＋沼脱出プロンプト50

盛りすぎた要件を機能1つに削る判定シートと、詰まったときにそのまま貼る指示文50本のセットです。

```text

□ その作業を、先月10回以上やったか

□ 返ってきた計画に、機能が4つ以上並んでいないか
→ YES(4つ以上ある): 削る。最初は1つだけにする
□ 「これが動かないなら作る意味がない」と言える機能はどれか
→ 1つに絞れた: それが仮縫いの対象
□ その1つの中に、ログイン・通知・権限・共有が混ざっていないか
→ YES(混ざっている): 全部外す。後から足せる
指示例: まず動くものを作りたいので、初期版はもっと小さくしてください。◯◯だけができる状態にして、それ以外は後のフェーズに回してください。

■ ステップ3：完成の線を先に引く
□ 「これができたら仮縫い完成」と1文で言えるか
→ YES: その1文を計画の冒頭に書き残させる
□ 完成の判定を自分で確認できるか（画面を見れば分かるか）
→ YES: そのまま進める
→ NO: 判定できる形に言い換える（数字・画面の見え方で言う）
指示例: この初期版の完成条件を、私が画面を見て確認できる形で3行以内に書いてください。

■ ステップ4：作らせる前の最終確認
□ 自分の環境（パソコンの種類・使えるメモリ・追加課金の可否）を伝えたか
→ NO: 伝える。ここを飛ばすと動かない技術を前提に進む
□ 似ているサービスの名前を挙げたか
→ NO: 挙げる。「あれっぽいもの」は最短の仕様書になる
□ 承認の仕方（毎回確認するか、危険な操作だけ確認するか）を決めたか
→ NO: 決める。まずは危険な操作だけ確認する設定が扱いやすい
指示例: 私の環境は◯◯です。追加課金なしで完結させたいので、その条件で使える構成を選んでください。

■ ステップ5：動いた後にやること
□ 自分で1週間、毎日使ったか
→ YES: 機能追加に進む
→ NO: 題材選びが外れている可能性。ステップ1に戻る
□ 使っていて毎回引っかかる箇所を3つ挙げられるか
→ YES: その3つが次に足す機能。順番もその通りにする
□ 使わなかった機能はあるか
→ YES: 消す。増やすだけだと自分に合わなくなる
指示例: 1週間使って毎回引っかかった3点を伝えます。優先順位を付けて、1つずつ直してください。

■ 作りたいものが定まらないとき

1. 頭の中の不満を作業の名前にする
用途: 「なんとなく面倒」を、作れる形の言葉に変える。
前提: 自作したい気持ちはあるが、何を作ればいいか言葉にできていない。手元にあるのは「あの作業が面倒」という感覚だけ。
指示: 私がこれから話す愚痴を聞いて、その中から「毎回発生している具体的な作業」を抽出してください。抽象的な感想は作業の名前に言い換え、発生頻度と1回あたりの所要時間を私に質問して埋めてください。
出力形式: 抽出した作業を「作業名／頻度／1回の所要時間／自作で削れそうな時間」の表にして、削れる時間が大きい順に並べてください。

2. 似ているサービスから仕様を起こす
用途: 「あれっぽいもの」を出発点にする。
前提: 作りたいものに近い既存サービスがあるが、自分の用途には合わない部分がある。その差分を言葉にできていない。
指示: これから挙げるサービスについて、公開されている情報から主な機能と仕組みを調べてください。そのうえで、私の用途に必要な機能と不要な機能を私に質問しながら振り分けてください。
出力形式: 「そのサービスにあって自分にも必要な機能」「あるが不要な機能」「ないが自分には必要な機能」の3つに分けた一覧を出してください。

3. 使う人を1人に決める
用途: 対象を広げすぎて設計が膨らむのを防ぐ。
前提: 作ろうとしているものの想定利用者が「自分と、あわよくば同僚と、できれば社外の人」と曖昧なままで、機能が膨らみそうになっている。
指示: 想定利用者を1人に絞る前提で、対象を「自分だけ」「社内数人」「社外を含む」にした場合それぞれで必要になる機能・考慮事項・作業量の差を比べてください。
出力形式: 3案を比較表にし、それぞれの作業量を「初期版までの目安時間」で示してください。最後にあなたの推奨を1案だけ挙げてください。

4. 要件の抜けを質問で埋めさせる
用途: 自分が答える側になる。
前提: 作りたいものの概要は話したが、細部が決まっていないまま作り始めそうになっている。
指示: この内容で計画を立てる前に、決まっていない点を重要な順に質問してください。1回の質問は3つまでにし、私が答えたらそれを踏まえて次の質問に進んでください。推奨がある選択肢には推奨と理由を添えてください。
出力形式: 質問がすべて終わったら、確定した内容だけをまとめた要件の一覧を出してください。私が答えていない点は「未確定」と明記してください。

5. 2回目の調査で情報を更新する
用途: 1回目の70〜80点を埋める。
前提: 使う技術の候補を出してもらったが、それが最新の選択肢かどうか分からない。
指示: 先ほど挙げてもらった技術候補について、抜け漏れがないか、より新しく適した選択肢が出ていないかを、もう一度調べ直してください。特に直近数か月に公開されたものを重点的に確認してください。
出力形式: 1回目の候補と2回目で見つかった候補を並べた比較表を出し、変更を推奨する箇所には理由を添えてください。

6. 自分の環境を前提に置き直す
用途: 動かない構成を最初に外す。
前提: 提案された構成が、自分の手元の環境で動くかどうか確認できていない。
指示: 私の環境（機械の種類・世代・使えるメモリ・空き容量・追加課金の可否）をこれから伝えます。その条件で動かない選択肢を除外し、残った候補だけで構成を組み直してください。
出力形式: 除外した候補は理由付きで一覧にし、残った構成を「必要なメモリ・容量・見込みの動作速度」の目安つきで示してください。

7. 作らないものを先に決める
用途: 膨張を初手で止める。
前提: 機能の候補が多く、どこまで作るかの線を引けていない。
指示: この計画のうち、初期版で「作らないもの」を先に決めたいです。作らない候補と、それを後回しにしても初期版が成立する理由を挙げてください。後回しにすると後で作り直しになる部分があれば、それは初期版に含めるよう指摘してください。
出力形式: 「初期版に含める」「後回しにできる」「後回しにすると作り直しになる」の3分類で一覧にしてください。

8. 完成条件を自分で確認できる形にする
用途: 判定できない完成を避ける。
前提: 初期版の完成条件が「ちゃんと動く」のように曖昧で、自分では判定できない。
指示: 初期版の完成条件を、私が画面を見るだけで判定できる形に書き直してください。判定に専門知識が必要な項目は、専門知識なしで確認できる代わりの確認方法に置き換えてください。
出力形式: 確認手順を3〜5個の箇条書きにし、それぞれ「どこを見て、何が見えていれば合格か」を書いてください。

9. 先に権利と規約を確認する
用途: 作った後で使えなくなる事故を防ぐ。
前提: 外部のサイトやサービスのデータを扱うものを作ろうとしているが、規約を確認していない。
指示: これから扱う予定の対象について、公開されている利用規約のうち「してはいけない扱い方」を洗い出してください。そのうえで、禁止事項を避けた設計案を提案してください。
出力形式: 「禁止されている行為」「それを避ける設計」「それでも残るリスク」の3項目で整理し、規約の該当箇所へのリンクを添えてください。

10. 既にあるなら作らない判断をする
用途: 自作しない選択も残す。
前提: 作りたいものと同じものが既に無料で存在する可能性があり、自作の是非を判断したい。
指示: 私がこれから説明する用途を満たす既存の選択肢を、無料・有料を問わず調べてください。そのうえで、自作した場合と既存品を使う場合の差（費用・自由度・維持の手間）を比較してください。
出力形式: 比較表を出し、最後に「自作を推奨する／既存品を推奨する」のどちらかを理由付きで1つ選んでください。

■ 作り始めで止まったとき

11. 計画から先に進まないとき
用途: 計画づくりが目的化するのを止める。
前提: 計画の議論が長引き、作り始められないまま時間が経っている。
指示: 議論を止めて、いま確定している内容だけで動くものを作ってください。未確定の部分は最も単純な形で仮に決め、決めた内容を後で見返せるように一覧に残してください。
出力形式: 「仮に決めた内容の一覧」と「動いたものの確認手順」の2つを出してください。仮決めした箇所は後から変えられるかどうかも書いてください。

12. 何をされているか分からないとき
用途: 作業内容を追える形にさせる。
前提: 作業が進んでいるが、何をしているのか分からず不安になっている。
指示: いま何をしていて、次に何をするつもりなのかを、専門用語を使わずに3行で説明してください。以降も大きな作業の前に、同じ形式で一言先に知らせてください。
出力形式: 「いまやっていること／次にやること／これが終わると何ができるようになるか」の3行で書いてください。

13. 知らない言葉が出てきたとき
用途: 調べもので作業を止めない。
前提: 説明の中に知らない専門用語が出てきて、内容を判断できない。
指示: この用語を、プログラミングを知らない人向けに説明してください。日常の作業にたとえた説明を先に置き、そのあとで正確な説明を短く添えてください。この用語を私が知らなくても進められるかどうかも教えてください。
出力形式: 「たとえるなら」「正確には」「私が判断すべきこと（あれば）」の3段で書いてください。

14. 提案された技術が不安なとき
用途: 選定理由を検証する。
前提: 提案された技術構成が自分には判断できず、それで進めていいか不安。
指示: この構成を選んだ理由を、代替案と比べる形で説明してください。あわせて「この選択で将来困る可能性」を正直に挙げてください。私の用途（後で伝えます）に対して過剰な部分があれば指摘してください。
出力形式: 「選んだ理由／代替案との違い／将来困る可能性／過剰な部分」の4項目で書いてください。

15. 動いたか分からないとき
用途: 確認手順を明示させる。
前提: 作業が完了したと言われたが、自分で確認する方法が分からない。
指示: 完成したものを私が確認する手順を、打つコマンドや開く画面まで含めて具体的に書いてください。専門知識のいらない確認方法を優先してください。うまくいっていない場合に見える症状も添えてください。
出力形式: 「手順（番号付き）／成功時に見えるもの／失敗時に見えるもの」の3項目で書いてください。

16. 途中で方向がずれたとき
用途: 軌道を戻す。
前提: 作業が進むうちに、当初やりたかったことと違う方向に進んでいる気がする。
指示: いまの成果物と、最初に決めた完成条件を突き合わせて、ずれている点を挙げてください。そのうえで、当初の条件に戻すために必要な作業と、戻さずに今の方向で進める場合の得失を比べてください。
出力形式: 「ずれている点／戻す場合の作業／今の方向で進める場合の得失」の3項目で書いてください。

17. 作業が長時間終わらないとき
用途: 止めるか待つかを判断する。
前提: 作業が想定よりずっと長く続いており、待つべきか止めるべきか判断できない。
指示: いまの進行状況を、全体の何割まで進んだかと残り作業の見込みで教えてください。残りが長い場合は、途中の成果だけを残して一区切りにする案も出してください。
出力形式: 「進捗の割合／残りの見込み／一区切りにする案（残るもの・失うもの）」の3項目で書いてください。

18. 成果物の置き場所が分からないとき
用途: 手元のどこにあるかを確定させる。
前提: 作ってもらったものが自分の機械のどこにあるか分からず、開けない。
指示: 作成したファイルの置き場所を、私の環境での完全な位置と、それを開く手順で教えてください。フォルダを開く操作とファイルを実行する操作を分けて書いてください。
出力形式: 「置き場所／フォルダを開く手順／動かす手順」の3項目で、コマンドはそのまま貼れる形で書いてください。

19. 最初から作り直したいとき
用途: 捨てる判断を整理する。
前提: いまの作りかけが自分の想定と大きく違い、作り直したいが判断できない。
指示: いまの成果物のうち「残せる部分」と「捨てるべき部分」を分けてください。そのうえで、作り直す場合の手順と、いまのものを直す場合の手順を、それぞれの見込み時間つきで比べてください。
出力形式: 「残せる部分／捨てる部分／作り直す案／直す案」の4項目で、各案に見込み時間を添えてください。

20. 依頼の粒度が分からないとき
用途: 1回の依頼量を決める。
前提: 1回にどれくらいの分量を頼めばいいか分からず、頼みすぎて混ざったり、細かすぎて回数が増えたりしている。
指示: これから作る機能の一覧を渡します。1回の依頼として適切な単位に分割し、依頼する順番を決めてください。分割の基準（同時に触ると壊れる箇所は分ける等）も説明してください。
出力形式: 「依頼1、依頼2…」の順序付きリストにし、各依頼に「含む作業」「終わったら何が確認できるか」を書いてください。

■ エラー・不具合が出たとき

21. エラーを丸ごと渡す
用途: 読めなくても原因を切り分けさせる。
前提: 画面にエラーが出て止まったが、書かれている内容が読めない。
指示: これから貼るエラーの文面をもとに、原因の候補を可能性の高い順に挙げてください。私が判断できるように、それぞれ「どの操作が引き金になったか」を添えてください。そのうえで、最も可能性の高い原因の対処を実行してください。
出力形式: 「原因の候補（可能性順）／今から試す対処／対処後に私が確認すること」の3項目で書いてください。

22. 同じエラーが繰り返すとき
用途: その場しのぎを止める。
前提: 同じエラーが直したはずなのに何度も再発している。
指示: この不具合が再発している理由を、これまでの対処内容を踏まえて分析してください。表面だけを直していた場合は、根本にある原因を特定してから対処してください。再発を防ぐための確認を仕組みとして追加してください。
出力形式: 「これまでの対処が効かなかった理由／根本原因／今回の対処／再発を防ぐ仕組み」の4項目で書いてください。

23. 画面が思った通りにならないとき
用途: 見た目のずれを画面で伝える。
前提: 画面の表示が想定と違うが、どこがどう違うかを言葉で説明しづらい。
指示: いまの画面を取り込んで、私が指摘する箇所を確認してください。指摘は「この部分がこうなってほしい」の形で伝えます。直す前に、どの部分をどう変えるつもりかを1行で先に教えてください。
出力形式: 「変更する箇所／変更後の見え方／影響が出る他の画面（あれば）」の3項目で書いてください。

24. 動くけど結果が違うとき
用途: 正しさの基準を作る。
前提: 処理は動いているが、出てくる結果が期待と違う。どこで狂っているか分からない。
指示: 期待する結果と実際の結果を私が示します。その差から、処理のどの段階で狂っているかを切り分けてください。切り分けのために途中の値を確認できる形にしてから、原因を特定してください。
出力形式: 「期待と実際の差／狂っている段階／原因／修正内容」の4項目で書いてください。

25. 直したら別の場所が壊れたとき
用途: 巻き戻して原因を絞る。
前提: 修正を入れたら、これまで動いていた別の箇所が動かなくなった。
指示: 直前の修正が原因かどうかを確認するため、変更内容を洗い出してください。原因が特定できたら、元の不具合と新しい不具合の両方が成立する直し方を探してください。それが難しい場合は、いったん修正を戻してから別の方法を提案してください。
出力形式: 「変更内容の一覧／壊れた原因／両立する直し方（なければ代替案）」の3項目で書いてください。

26. 環境の違いで動かないとき
用途: 手元固有の問題を切り分ける。
前提: 以前は動いていたのに、環境を変えたら動かなくなった。
指示: 動いていた環境と今の環境の違いを洗い出してください。そのうえで、環境差に起因する問題かどうかを切り分け、環境差であれば今の環境で動く形に直してください。私が確認できる形で違いを説明してください。
出力形式: 「環境の違い／原因が環境差かどうかの判断／直した内容」の3項目で書いてください。

27. 時々しか起きないとき
用途: 再現条件を先に固める。
前提: 不具合が毎回ではなく、時々しか起きないため原因を追えない。
指示: この不具合が起きるときと起きないときの違いを、私への質問で洗い出してください。再現条件が絞れたら、必ず再現する手順にまとめてから原因を特定してください。再現できない場合は、記録を残す仕組みを先に入れてください。
出力形式: 「絞り込んだ再現条件／再現手順／原因（分かれば）／記録を残す仕組み」で書いてください。

28. 遅くて使えないとき
用途: どこが遅いかを測ってから直す。
前提: 動くが遅すぎて実用にならない。どこが遅いのか分からない。
指示: 処理のどの段階に時間がかかっているかを測ってください。推測ではなく実際の時間を計測し、遅い順に並べてください。そのうえで、最も効果の大きい1箇所だけを先に改善してください。
出力形式: 「段階ごとの所要時間／最も遅い箇所／改善内容／改善後の所要時間」の4項目で書いてください。

29. 外部サービスが原因のとき
用途: 自分側と相手側を切り分ける。
前提: 外部サービスと連携している部分で失敗するが、自分の作り方が悪いのか相手側の問題か分からない。
指示: 失敗の原因が自分側にあるか外部サービス側にあるかを切り分けてください。相手側の問題であれば、その場合の対処（待つ・回数を減らす・別の方法にする）を提案してください。相手に負荷をかけすぎる作りになっていないかも確認してください。
出力形式: 「切り分けの結果／根拠／対処案／相手への負荷の見直し点」の4項目で書いてください。

30. 何を直したか分からなくなったとき
用途: 変更の履歴を取り戻す。
前提: 何度も修正を重ねた結果、どこをどう直したか分からなくなった。
指示: これまでの変更内容を、時系列で一覧にしてください。それぞれ「何のために変えたか」を添えてください。不要になった変更や、目的が重複している変更があれば指摘してください。
出力形式: 「時系列の変更一覧（目的つき）／不要になった変更／整理の提案」の3項目で書いてください。

■ 使いにくさを直すとき

31. 毎回引っかかる場所を直す
用途: 使ってから出てくる不満を拾う。
前提: 1週間使ってみて、毎回引っかかる箇所が3つほど見えてきた。
指示: これから3つの引っかかりを伝えます。それぞれを直す作業に分解し、効果が大きく手数が少ない順に並べてください。1つずつ直し、直すたびに私が確認する手順を示してください。
出力形式: 「作業の一覧（優先順）／1つ目の修正内容／確認手順」の3項目で書いてください。

32. 操作の手数を減らす
用途: 回数の多い操作を最短にする。
前提: よく使う操作に手数が多く、毎回の小さな手間が積み上がっている。
指示: 私が最も頻繁に行う操作をこれから伝えます。その操作に必要なクリック数と入力数を数え、最短手順に組み替えてください。他の機能を犠牲にしないことを条件にしてください。
出力形式: 「現在の手数／組み替え後の手数／変更内容／他機能への影響」の4項目で書いてください。

33. 見た目を整える
用途: 情報の優先順位を画面に反映させる。
前提: 画面に情報が並んでいるだけで、どこを見ればいいか分からない。
指示: この画面で最も重要な情報と、二番目に重要な情報を私が伝えます。それに合わせて文字の大きさ・配置・余白を整えてください。派手な装飾は加えず、優先順位が伝わることだけを目的にしてください。
出力形式: 「変更点の一覧／変更後の見え方／変更しなかった箇所とその理由」の3項目で書いてください。

34. 入力の手間を減らす
用途: 毎回同じ入力をやめる。
前提: 使うたびに同じ情報を入力しており、それが面倒で使う頻度が落ちている。
指示: 毎回同じ値を入れている項目を洗い出し、初期値として保持する仕組みを入れてください。保持する場所は私の端末の中だけに限り、外部に送らない作りにしてください。値を変えたいときは上書きできるようにしてください。
出力形式: 「初期値にする項目／保持する場所／上書きの操作／外部に送らないことの確認方法」で書いてください。

35. 間違いを防ぐ
用途: 取り返しのつかない操作に確認を置く。
前提: 誤操作で消してしまう危険があり、使うのが怖い。
指示: 取り消せない操作を洗い出し、それぞれに確認の一手間か、取り消せる仕組みを追加してください。頻繁に使う安全な操作には確認を付けないでください。
出力形式: 「取り消せない操作の一覧／それぞれの対処（確認か取り消しか）／確認を付けない操作」で書いてください。

36. 表示件数が多すぎるとき
用途: 見る量を絞る。
前提: 一覧の件数が増えて、目的のものを見つけられなくなってきた。
指示: 一覧の絞り込みと並べ替えを追加してください。私が実際に使う絞り込み条件をこれから伝えます。それ以外の条件は追加せず、画面が複雑にならない形にしてください。
出力形式: 「追加する絞り込み／並べ替えの基準／画面の変更点」の3項目で書いてください。

37. スマホで使いにくいとき
用途: 小さい画面での使用に寄せる。
前提: パソコンでは使えるが、スマホで開くと文字が小さく操作しづらい。
指示: 小さい画面での表示を整えてください。横スクロールが発生する箇所をなくし、押しにくいボタンの大きさを見直してください。パソコンでの見た目は崩さないことを条件にしてください。
出力形式: 「直した箇所／小さい画面での確認手順／パソコン表示への影響」の3項目で書いてください。

38. 説明がないと使えないとき
用途: 画面の中で分かる形にする。
前提: 自分は使えるが、他の人に渡すと使い方を聞かれる。
指示: 初めて開いた人が説明なしで使えるように、画面の中に必要な案内を入れてください。長い説明文は置かず、入力欄の例示や1行の補助文で伝える形にしてください。
出力形式: 「追加した案内の一覧／それぞれの置き場所／削った説明文」の3項目で書いてください。

39. 使わない機能があるとき
用途: 減らして自分に合わせ直す。
前提: 勢いで足した機能のうち、1か月使っていないものがある。
指示: 1か月使っていない機能をこれから伝えます。それらを削除した場合の影響を確認し、他の機能に支障がなければ取り除いてください。将来また使う可能性がある場合は、戻せる形で外してください。
出力形式: 「削除する機能／影響の確認結果／戻し方（必要なら）」の3項目で書いてください。

40. データが増えて重いとき
用途: 溜まる前提で作り直す。
前提: 使い続けてデータが増え、開くのが遅くなってきた。
指示: データ量の増加が原因かどうかを確認し、原因であれば増えても遅くならない扱い方に変えてください。過去のデータを別に分ける案も含めて検討してください。既存のデータを失わないことを条件にしてください。
出力形式: 「原因の確認結果／変更する扱い方／既存データの移行手順／変更後の速度」で書いてください。

■ 最後の2割と公開

41. どこで完成にするか決める
用途: 終わらない改善を止める。
前提: だいたい動くようになったが、細かい不満が尽きず、いつまでも直し続けている。
指示: 残っている不満をこれから全部伝えます。それぞれを「実用に支障がある／気になるだけ」に分類してください。支障があるものだけを直す前提で、作業の順番と見込み時間を出してください。気になるだけのものは記録に残して、いったん止めます。
出力形式: 「支障があるもの（作業順・見込み時間）／気になるだけのもの（記録）／完成としてよい判断の理由」で書いてください。

42. 精度を上げる前に測る
用途: 感覚ではなく数字で改善する。
前提: 出力の精度が今ひとつだが、どこがどれくらい悪いのか測っていない。
指示: 精度を測る簡単な方法を先に作ってください。私が正解を用意できる形にし、実行すると誤りの割合が数字で出るようにしてください。そのうえで、誤りの種類を分類して、多い順に対処してください。
出力形式: 「測り方／現在の誤り率／誤りの種類（多い順）／最初に対処する1つ」で書いてください。

43. 後処理で弱点を補う
用途: 1段で無理なら2段にする。
前提: 処理の精度が足りないが、根本を作り直す時間はない。
指示: 処理を2段に分けて、1段目の弱点を2段目で補う構成に変えられないか検討してください。速度が落ちすぎない範囲で、よくある誤りだけを補正する形にしてください。補正の内容は私が編集できるようにしてください。
出力形式: 「2段構成の案／補正する誤りの種類／速度への影響／補正内容の編集方法」で書いてください。

44. 秘密の情報を分ける
用途: 鍵を画面側に置かない。
前提: 外部サービスの鍵（APIキー）を使う作りになっているが、置き場所が正しいか分からない。
指示: 鍵や秘密の情報が、公開したときに外から見える場所に置かれていないか確認してください。見える場所にある場合は、見えない場所へ移してください。公開前に確認すべき箇所の一覧も作ってください。
出力形式: 「確認結果／移動した内容／公開前チェックの一覧」の3項目で書いてください。

45. 公開の条件を確認する
用途: 無料枠の条件を先に読む。
前提: 作ったものを公開したいが、使う予定の公開サービスの条件を読んでいない。
指示: これから使う公開サービスの利用条件を調べ、私の用途（後で伝えます）が条件の範囲内かを判断してください。特に商用利用の扱い、含まれる転送量、上限を超えた場合の挙動を確認してください。
出力形式: 「条件の要点／私の用途が範囲内かの判断／範囲外なら必要な対応／条件のリンク」で書いてください。

46. 他人が使える状態にする
用途: 自分専用から一歩出す。
前提: 自分は使えるが、他の人が開いたときに動かない可能性がある。
指示: 私以外の人が初めて開いたときに動かなくなる箇所を洗い出してください。私の環境に依存している設定や、私の端末にしかないデータを前提にしている部分を特定し、依存を外してください。
出力形式: 「依存している箇所／外した内容／他の人が開いたときの確認手順」の3項目で書いてください。

47. 使われ方を見られるようにする
用途: 改善の材料を残す。
前提: 公開したが、実際に使われているのか分からない。
指示: 誰がどう使ったかを記録する仕組みを、最小限で入れてください。個人が特定される情報は残さず、機能ごとの利用回数と発生したエラーだけを見られる形にしてください。記録の保存場所と保存期間も決めてください。
出力形式: 「記録する項目／記録しない項目／保存場所と期間／確認方法」で書いてください。

48. 決め事を残して次に活かす
用途: 同じ説明を繰り返さない。
前提: 作業のたびに同じ前提を説明し直しており、毎回の手間になっている。
指示: このプロジェクトの決め事（使う技術・命名の規則・やってはいけないこと・確認の手順）を1枚の指示書にまとめてください。次回以降はその指示書を読んで作業してください。内容は私が読んで分かる平易な言葉にしてください。
出力形式: 指示書の内容をそのまま貼れる形で出し、最後に「置き場所」と「更新のタイミング」を添えてください。

49. 引き継げる形にする
用途: 自分以外でも直せるようにする。
前提: 自分しか直せない状態になっており、忙しくなると更新が止まる。
指示: 他の人が引き継げるように、動かし方・直し方・詰まったときの調べ方をまとめた手引きを作ってください。前提知識のない人が読んで動かせるレベルまで具体的に書いてください。
出力形式: 「動かす手順／よくある作業の直し方／詰まったときの調べ方」の3章立てで、コマンドはそのまま貼れる形で書いてください。

50. 次に作るものを決める
用途: 1本目の学びを2本目に渡す。
前提: 1本作り終えたので、次に作るものを決めたい。
指示: この1本を作る過程で分かったこと（うまくいった進め方・時間がかかった工程・使わなかった機能）を振り返ってください。そのうえで、私が挙げる次の候補を、今回の学びを踏まえて評価してください。
出力形式: 「振り返りの要点／候補の評価（作業量と効果）／次に作るものの推奨1つ」で書いてください。

以上、判定シート1本＋プロンプト50本です。内訳は 作りたいものが定まらないとき 10本／作り始めで止まったとき 10本／エラー・不具合が出たとき 10本／使いにくさを直すとき 10本／最後の2割と公開 10本 の合計50本。
```

**ポイント**: 詰まったときは、状況を自分で要約せずそのまま渡すのがいちばん速いです。エラー文は省略せず全部貼ってください。

# 🎁 公開前チェックリスト（無料公開の落とし穴つき）

作ったものを人に使ってもらう前に、一度だけ通す確認表です。無料枠の条件・素材の規約・鍵の置き場所・利用者データの扱いを5ステップで潰します。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 公開作業に入る直前に、上から順に □ を埋めてください。`指示例:` の行はそのままAIに貼れます。

```text
【公開前チェックリスト：無料公開の落とし穴を先に潰す】

■ ステップ1：公開先の条件を読む
□ 使う公開サービスの無料枠は「個人の非商用」に限定されていないか
→ YES(限定されている): 収益が絡む予定なら有料プランに切り替える
□ 広告・アフィリエイト・有料提供・業務利用のどれかを行う予定があるか
→ YES: そのサービスの商用利用の定義を読み、該当するなら有料プランへ
□ 含まれる転送量・実行回数を超えたときの挙動を確認したか
→ NO: 確認する（停止するのか課金されるのかで対処が変わる）
指示例: これから使う公開サービスの利用条件を調べ、私の用途が無料枠の範囲内か判断してください。商用利用の定義と、上限超過時の挙動を必ず含めてください。

■ ステップ2：他人のデータと素材を確認する
□ 外部サイトのデータを扱っているか
→ YES: そのサイトの規約で禁止されている扱い方を洗い出す
□ 素材ファイル自体を保存・再配布していないか
→ YES: 保存をやめて、掲載ページへのリンクだけを扱う形に変えられないか検討する
□ クレジット表記が必要な素材を使っていないか
→ YES: 表記が必要な提供元を画面に明示する
□ 規約を確認した日付を記録したか
→ NO: 記録する（規約は変わるため、次回の確認時期の目安になる）
指示例: 扱う予定の外部サイトの規約から「してはいけない扱い方」を洗い出し、それを避けた設計案を提案してください。

■ ステップ3：秘密の情報を分ける
□ 外部サービスの鍵（APIキー）を使っているか
→ YES: 公開したときに外から見える場所に置いていないか確認する
□ 鍵を画面側のコードに直接書いていないか
→ YES: 見えない場所に移す
□ 公開用のファイル一覧を目で確認したか
→ NO: 確認する（設定ファイル・メモ・下書きが混ざりやすい）
指示例: 鍵や秘密の情報が公開時に外から見える場所にないか確認し、見える場所にあるものは移してください。公開前に見るべき箇所の一覧も作ってください。

■ ステップ4：利用者のデータの置き場所を決める
□ 利用者が入力したデータをどこに保存するか決めたか
→ 端末の中だけ: 外部に送らないことを画面に明記する
→ 外部に保存: 保存先・保存期間・削除方法を決めて明記する
□ 個人情報や連絡先を扱っていないか
→ YES: 本当に必要か再検討する。不要なら項目自体を削る
□ 記録するものと記録しないものを分けたか
→ NO: 分ける（機能ごとの利用回数までに留めるのが扱いやすい）
指示例: 利用者のデータの保存先と保存期間を整理し、外部に送らない項目については画面上にその旨を明記してください。

■ ステップ5：他人が開いても動くか確かめる
□ 自分の環境にしかない設定やデータに依存していないか
→ YES: 依存を外す
□ 初めて開いた人が、説明なしで最初の操作にたどり着けるか
→ NO: 入力欄の例示や1行の補助文を足す
□ 動かなかったときの連絡先や戻り道を用意したか
→ NO: 用意する（うまくいかない人がそのまま離れるのを防ぐ）
□ 公開したURLを自分の別の端末で開いて確認したか
→ NO: 確認する（自分の機械では動くという事故がいちばん多い）
指示例: 私以外の人が初めて開いたときに動かなくなる箇所を洗い出し、私の環境への依存を外してください。確認手順も示してください。
```

**ポイント**: 「自分の機械では動く」が最も多い事故です。ステップ5の別端末での確認だけは必ず行ってください。
