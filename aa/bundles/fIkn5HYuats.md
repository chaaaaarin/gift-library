# 経営層向け：AIベンダー信頼性審査シート

OpenAIがDaybreak Red（GPT-5.6-Cyber）の提供先を審査する際に使っている基準（SSO・多要素認証・ログ管理・インシデント対応文書・SOC2認証等）を、逆に「自社が導入するAIツール・ベンダーを見極める側」の質問リストとして転用したシートです。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: 新しいAIツール・ベンダーの導入を検討する際、上から順に確認してください。導入済みのツールの定期点検にも使えます。

```text
【経営層向け：AIベンダー信頼性審査シート】

■ ステップ1：基本的なセキュリティ体制の確認
□ ベンダーはSOC 2 Type IIやISO 27001等の第三者セキュリティ認証を取得しているか
□ 過去にセキュリティインシデントが公表されている場合、対応・開示のプロセスは適切だったか
→ YES: 導入検討を継続する
→ NO: 認証取得予定の有無、代替の保証手段（監査レポート等）を確認する
指示例: 「このベンダーの公開情報から、セキュリティ認証の取得状況と過去のインシデント公表履歴を調べて」

■ ステップ2：アクセス制御・認証の確認
□ SSO（シングルサインオン）・多要素認証に対応しているか
□ 利用者ごとにロール（役割）ベースのアクセス制御ができるか
→ YES: 自社の権限設計に組み込む準備を進める
→ NO: 全員が同じ権限になるリスクを踏まえ、利用範囲を限定する
指示例: 「このツールの管理画面で設定できるアクセス制御の種類を一覧化して」

■ ステップ3：ログ・監視体制の確認
□ 利用ログ（誰が・いつ・何をしたか）を管理者が確認できるか
□ 異常な利用パターンを検知するアラート機能はあるか
→ YES: 定期的なログ確認の担当・頻度を決めて運用に組み込む
→ NO: 自社側で利用状況を記録する代替手段を用意する
指示例: 「このツールで取得できる利用ログの項目と、保存期間を確認して」

■ ステップ4：インシデント対応体制の確認
□ ベンダー側に文書化されたインシデント対応プロセスがあるか
□ インシデント発生時に自社へ通知される契約条項があるか
→ YES: 自社の緊急連絡フローとベンダーの窓口を紐づけておく
→ NO: 契約前に通知義務の追加を交渉する
指示例: 「このベンダーとの契約書（案）に、インシデント発生時の通知義務が明記されているか確認して」

■ ステップ5：データの取り扱い・退出条件の確認
□ 入力したデータの保存期間・学習利用の有無・削除方法は明確か
□ 契約終了時にデータを完全に削除・返却してもらえるか
→ YES: 機密情報を扱う業務にも段階的に利用範囲を広げられる
→ NO: 機密情報の入力は避け、一般的な業務のみに利用範囲を限定する
指示例: 「このツールの利用規約から、データの保存期間と契約終了時の削除条件を抜き出して」

■ ステップ6：スコープ限定・契約条件の確認
□ 利用範囲（社内利用限定か、顧客向けサービスへの組み込み可否）が契約上明確か
□ APIキー・アカウントの管理者を限定し、利用できる人を絞れる設計になっているか
→ YES: 導入を正式決定してよい
→ NO: 利用範囲の明確化を契約条件に加えるまで保留する
指示例: 「この契約条件で、社内利用限定なのか顧客向けサービスにも使えるのか明記されているか確認して」
```

**ポイント**: どれか1つでも「NO」が続く場合は、導入自体を止める必要はありませんが、利用範囲を「機密情報を扱わない業務」に限定するなど、リスクに応じた段階的な導入を検討してください。

### 1. 使い回しパスワードの棚卸し

```text
前提: 自分が複数のサービスで同じ、または似たパスワードを使い回していないか不安。

出力形式: 手順を番号付きで5〜7ステップ。各ステップに「なぜ危険か」を1行添えて。実際のパスワードは絶対に入力させない前提で書いて。
```

### 2. 多要素認証の導入優先順位

```text
前提: 多要素認証(MFA)をどのサービスから設定すべきか分からない。
指示: メール・クラウドストレージ・SNS・金融系サービスの4カテゴリで、MFA導入の優先順位とその理由、代表的な設定方法(認証アプリ/SMS/セキュリティキー)の違いを整理して。
出力形式: 優先度(高中低)付きの表。各カテゴリに推奨MFA方式とその理由を1行で添えて。
```

### 3. パスワードマネージャー選定基準

